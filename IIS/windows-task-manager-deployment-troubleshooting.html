1QA 環境：問題與解法時間軸

設定選擇

1.1 setup.ps1 的 Scope 該選 Machine 還是 User？

現象：執行 setup.ps1 Step 3 詢問 Scope，不確定選哪個。

原因：User 層級只對登入使用者生效，IIS 應用程式集區是系統服務身分，讀不到。

解法：一律選擇 Machine（需系統管理員身分執行）。

版本檢查

1.2 Hosting Bundle 版本確認

Get-ItemProperty HKLM:\Software\Microsoft\Windows\CurrentVersion\Uninstall\*, HKLM:\Software\Wow6432Node\Microsoft\Windows\CurrentVersion\Uninstall\* |
  Where-Object { $_.DisplayName -like "*Hosting Bundle*" -or $_.DisplayName -like "*ASP.NET Core*" } |
  Select-Object DisplayName, DisplayVersion

現象：機器只裝了 ASP.NET Core 3.1.32，但專案是 net8.0，版本不符會導致 500.30 / 502.5。

解法：

winget install --id Microsoft.DotNet.HostingBundle.8 -e
iisreset
IIS 站台

1.3 同一台機器多個 IIS Sites，如何讓網域指到正確站台？

原因：IIS 用「IP : Port : Host Header」組合判斷路由。

解法：使用 Host Header 區隔，多個 Site 共用 Port 80，內部 DNS 需有一筆記錄指向本機 IP。

Resolve-DnsName windows-task-manager.my.91dev.tw
根本原因

1.4 Google OAuth 登入失敗：redirect_uri_mismatch（錯誤 400）

原因：程式碼回呼路徑是 /LoginCallback（非預設 /signin-google）：

var redirectUrl = Url.Page("/LoginCallback");
var properties = new AuthenticationProperties { RedirectUri = redirectUrl };
return Challenge(properties, GoogleDefaults.AuthenticationScheme);

改用 Host Header 網域存取後，實際 redirect_uri 變成 http://windows-task-manager.my.91dev.tw/LoginCallback，但 Google Console 只登記了 localhost 版本。

解法：Google Cloud Console → 憑證 → 編輯 OAuth Client → 新增：

http://windows-task-manager.my.91dev.tw/LoginCallback
同一組 Client ID / Secret 可同時登記多筆 redirect URI，不需每個環境都建立新 Client。
根本原因

1.5 排程清單「權限不足：Access is denied (0x80070005)」

根本原因：appsettings.QA.json 的 IPAddress 填了機器自己的實際 IP，而非 localhost。

if (config.IPAddress == "localhost" || config.IPAddress == "127.0.0.1")
{
    ts = new TaskService();              // 本機模式：直接用執行身分做本機 COM 呼叫
}
else
{
    ts = new TaskService(config.IPAddress, ...);  // 遠端模式：強制走網路驗證
}

即使目標就是自己，只要填實際 IP，就會走「遠端」分支，觸發 Windows 對「用網路方式驗證自己」的 Loopback 限制，跟帳密正確與否無關。

最終解法：IPAddress 維持填實際 IP/網域（不改成 localhost），改從 App Pool 執行身分下手，見 1.6。

權限設定

1.6 最終解法：App Pool Identity 改為 LocalSystem

原因：走「遠端」分支時，App Pool 執行身分（ApplicationPoolIdentity）在網路驗證自己時權限不足，導致列舉任務失敗或「安靜地看不到」，不會顯示成錯誤。

實際採用的解法：IIS 管理員 → Application Pools → Advanced Settings → Identity → LocalSystem；或用 PowerShell：

Set-ItemProperty IIS:\AppPools\WindowsTaskManagerPool -Name processModel.identityType -Value LocalSystem

LocalSystem 對應 NT AUTHORITY\SYSTEM，對外網路驗證時會用機器帳號憑證，繞過 Loopback 限制，同時具備列舉本機排程任務所需的權限。

重要：變更身分後一定要 Recycle App Pool，因為 Access Token 在處理程序啟動當下就決定好，舊 worker process 不會自動感知新的身分設定。
Restart-WebAppPool -Name "WindowsTaskManagerPool"
風險提醒：LocalSystem 權限等同系統層級，屬於權限最大化做法；若有資安強化需求，可評估改用「加入 Administrators 群組」或更精細的最小權限服務帳號設計。

2Production 環境：問題與解法時間軸

設定同步

2.1 appsettings.Production.json 的 IPAddress 設定

沿用 1.5/1.6 的結論，Production 機器監控自己時 IPAddress 一樣維持填實際 IP/網域，存取權限問題同樣以 App Pool Identity 改為 LocalSystem 解決，QA 與 Production 作法一致。

前置需求

2.2 這台 Production 機器發現連 IIS 都還沒安裝

解法（UI）：伺服器管理員 → 管理 → 新增角色及功能 → Server Roles 勾選 Web Server (IIS) → Role Services 使用預設勾選 → 安裝。

精靈最後一頁若沒勾選「自動重新啟動目的地伺服器」，不會自動重開機，可放心安裝。
⚠️ 關鍵坑 · 根本原因

2.3 Hosting Bundle 裝在 IIS 之前 → ANCM 模組沒有正確註冊

這是本次 Production 部署耗費最多時間排查的問題，完整記錄如下：

現象：網站可連到（IIS 存取記錄有紀錄），但外部瀏覽器顯示通用 500 - Internal server error。改在伺服器本機瀏覽後才看到詳細錯誤：

Error Code   0x8007000d
Module       IIS Web Core
Config File  \\?\D:\windows-task-manager\web.config

排查過程：

  1. 先懷疑是 web.config 的 XML 語法問題，逐一修正（見 2.4）後 XML 已完全合法，錯誤依舊。
  2. 進一步確認 IIS 是否真的註冊了 aspNetCore 設定區段： 
    Test-Path "$env:windir\System32\inetsrv\config\schema\aspnetcore_schema.xml"
    結果回傳 False —— 確認 ANCM 模組根本沒有整合進 IIS。

根本原因：這台機器是「先裝 Hosting Bundle → 後裝 IIS」。Hosting Bundle 安裝當下 IIS 還不存在，導致無法把 AspNetCoreModuleV2 與 aspNetCore schema 正確登記進 applicationHost.config。單純重新執行安裝程式（非 repair 流程）不會補回這個註冊動作。

解法：解除安裝後在 IIS 已裝好的狀態下重新安裝：

winget uninstall --id Microsoft.DotNet.HostingBundle.8
winget install --id Microsoft.DotNet.HostingBundle.8 -e
iisreset

驗證修復成功：

Test-Path "$env:windir\System32\inetsrv\config\schema\aspnetcore_schema.xml"
# 應回傳 True
關鍵教訓：IIS 角色必須先安裝完成，Hosting Bundle 一定要在 IIS 裝好「之後」才安裝。順序顛倒會導致模組沒有正確註冊，且錯誤代碼 0x8007000d 本身不會直接指出「模組未註冊」，需額外用 Test-Path 驗證 schema 檔案才能確認根因。
web.config

排查 2.3 過程中，手動編輯 web.config 時曾出現以下問題（也會造成同樣的 0x8007000d，但非最終根因）：

問題修正方式
重複的結尾標籤 </aspNetCore></aspNetCore>刪除多餘的一個，確保開始/結尾標籤數量對稱

除錯技巧

2.5 IIS 預設只在「本機」顯示詳細錯誤

現象：即使加了 ASPNETCORE_DETAILEDERRORS=true，外部瀏覽器仍只顯示通用 500 訊息。

原因：IIS httpErrors 預設 errorMode="DetailedLocalOnly"，只有從伺服器「本機」瀏覽才顯示詳細內容，遠端一律顯示通用訊息（安全機制）。

解法：透過遠端桌面連進主機，在主機本機瀏覽器開啟網址查看詳細錯誤。

除錯技巧

2.6 如何確認外部請求真的有打到這台機器

  • 確認 DNS 解析：Resolve-DnsName <網域> 比對是否為本機 IP
  • 查 IIS 存取記錄：C:\inetpub\logs\LogFiles\W3SVC<id>\
  • 放置測試檔案：wwwroot 底下建立含 hostname 的 txt 檔，外部瀏覽器開啟驗證
  • 本機模擬外部 Host Header 請求：Invoke-WebRequest -Uri "http://localhost" -Headers @{Host="<網域>"}

3完整正確部署 SOP（去蕪存菁版）

  1. 安裝 IIS 角色（伺服器管理員 → 新增角色及功能 → Web Server (IIS)）
  2. 確認 IIS 安裝完成後，才安裝 .NET 8 ASP.NET Core Hosting Bundle：winget install --id Microsoft.DotNet.HostingBundle.8 -e → iisreset
  3. 驗證 ANCM 模組正確註冊：Test-Path "$env:windir\System32\inetsrv\config\schema\aspnetcore_schema.xml"（應為 True）
  4. dotnet publish 專案，並將 publish 資料夾複製到目標主機
  5. 確認 appsettings.{Environment}.json 裡 ServersConfig.Servers[].IPAddress：填實際 IP/網域即可，不需改成 localhost
  6. 建立 Application Pool：.NET CLR Version = No Managed Code，Start Mode = AlwaysRunning
  7. 將 App Pool Identity 改為 LocalSystem：Set-ItemProperty IIS:\AppPools\<PoolName> -Name processModel.identityType -Value LocalSystem
  8. 建立網站：Physical Path 指向 publish 資料夾，Binding 用 Host Header 綁定對應網域
  9. 建立 logs 資料夾並給寫入權限
  10. 確認 web.config：stdoutLogEnabled 若為 true 必須搭配 stdoutLogFile；標籤需完整配對
  11. 執行 setup.ps1（系統管理員身分），Scope 選 Machine
  12. Google OAuth：新增對應網域的 /LoginCallback 回呼 URL（可與其他環境共用同一組 Client）
  13. Recycle App Pool 讓所有設定生效：Restart-WebAppPool -Name "<PoolName>"
  14. 驗證：DNS 解析、IIS 存取記錄、首頁可開啟、登入流程正常、伺服器卡片「連線正常」且任務數量非 0

4安全性提醒

  • appsettings.*.json 內若填入帳密／Client Secret，不應提交進版控，考慮加入 .gitignore 或改用機器層級環境變數
  • 診斷用的 ASPNETCORE_DETAILEDERRORS=true 與 httpErrors errorMode="Detailed" 僅供臨時排查，確認問題後務必移除
  • 任何密碼／Client Secret 曾明碼出現在聊天記錄、Log 等非受控管道，應盡快到來源重新產生（Reset），視為已外洩處理
  • App Pool Identity 選用 LocalSystem 屬於權限最大化做法，QA 與 Production 兩環境目前皆採用此方式；日後有資安強化需求可評估改為「加入 Administrators 群組」或更精細的最小權限設計

5常用診斷指令速查

# 確認 Hosting Bundle / ASP.NET Core 版本
Get-ItemProperty HKLM:\Software\Microsoft\Windows\CurrentVersion\Uninstall\*, HKLM:\Software\Wow6432Node\Microsoft\Windows\CurrentVersion\Uninstall\* |
  Where-Object { $_.DisplayName -like "*Hosting Bundle*" -or $_.DisplayName -like "*ASP.NET Core*" } |
  Select-Object DisplayName, DisplayVersion

# 確認 ANCM 模組是否正確註冊進 IIS
Test-Path "$env:windir\System32\inetsrv\config\schema\aspnetcore_schema.xml"

# 確認目前環境變數（Machine 層級）
[System.Environment]::GetEnvironmentVariable("ASPNETCORE_ENVIRONMENT", "Machine")
[System.Environment]::GetEnvironmentVariable("Authentication__Google__ClientId", "Machine")

# 確認 App Pool Identity 目前設定
Get-ItemProperty IIS:\AppPools\<PoolName> -Name processModel.identityType

# 設定 App Pool Identity 為 LocalSystem
Set-ItemProperty IIS:\AppPools\<PoolName> -Name processModel.identityType -Value LocalSystem

# Recycle App Pool
Restart-WebAppPool -Name "<PoolName>"

# 確認 DNS 解析
Resolve-DnsName <網域>

# 查最新的 IIS 存取記錄
Get-ChildItem "C:\inetpub\logs\LogFiles" -Recurse -Filter "*.log" | Sort-Object LastWriteTime -Descending | Select-Object -First 5

# 本機模擬外部 Host Header 請求
Invoke-WebRequest -Uri "http://localhost" -Headers @{Host="<網域>"} -UseBasicParsing

# 查詢實際排程任務（跟 App 顯示結果比對）
Get-ScheduledTask | Where-Object { $_.TaskPath -notlike "\Microsoft\*" } | Select-Object TaskName, TaskPath, State

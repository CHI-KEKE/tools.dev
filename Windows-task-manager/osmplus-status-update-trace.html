1. 兩層狀態機總覽

OSMPlus 的每一次 ETL Flow 執行都有 兩層物件 在追蹤狀態：EtlFlowTask（整個流程實例）與 EtlFlowTaskSlave（流程內每一個步驟）。兩者的狀態欄位分別存在 EtlFlowTask_Status 與 EtlFlowTaskSlave_Status。

2. 正常成功路徑

進入 DoProcess()
UpdateTaskStatusToRunning：設定 StartDateTime、ExecutionCount + 1、Task 狀態 → Running；同時 isExecuteFlow = true
逐一走訪 TaskSlave（流程步驟）
每個步驟開始前 UpdateTaskSlaveStatusToRunning，執行 Service 的 DoProcess 成功後 UpdateTaskSlaveStatusToFinish，並寫入一筆 EtlFlowTaskLog（狀態 Finish）
全部步驟跑完，且未被中斷
UpdateTaskStatusToFinish：Task 狀態 → Finish，寫入 Task 層 EtlFlowTaskLog（Finish）。這是整個 Task 判定「成功」的唯一路徑
若中途有步驟回傳 IsStopFlowProcess = true（主動中斷，例如判斷本次無資料可處理），流程不算失敗：該步驟仍 Finish，其餘尚未執行的步驟會被標記為 Pass，Task 最終狀態也是 Pass 而非 Finish。
EtlFlowControlService.cs L106-480、L949-1051

3. 失敗路徑（單一步驟拋出例外）

TaskSlave 執行中拋出例外
被 catch (Exception ex) 攔截（DoProcess L329），在同一個 TransactionScope 內同時：
UpdateTaskSlaveStatusToError
該步驟狀態 → Error，寫入 TaskSlave 層 EtlFlowTaskLog（Error）
UpdateTaskStatusToError
整個 Task 狀態 → Error，同時設定 BookingDateTime = Now + RetryInterval；寫入 Task 層 EtlFlowTaskLog（Error）
組 Slack 錯誤訊息（若非 debug mode）
內容含 ex.ToString() 完整 stack trace、ShopId / TaskId / ServiceName / TaskSlaveId，附上紅色色條 Color = "#ff6666"，呼叫對應的 Slack Webhook 告警群組
throw;
例外原樣往外拋，交給呼叫端（Program.cs）的重試迴圈處理
另外兩種「還沒開始跑 TaskSlave」就失敗的情況，一樣會走 UpdateTaskStatusToError + InsertTaskLog(Error)：
① 該 Task 完全沒有任何 TaskSlave（flowServiceTasks.Any() == false）
② Flow 驗證失敗 DoFlowValidation（例如步驟間輸入輸出型別對不上）
EtlFlowControlService.cs L161-190、L310-448

4. 外層重試機制（Program.cs ExecuteFlowId）

DoProcess 拋出例外後，並不會直接結束，而是回到呼叫端的 while(true) 迴圈由它決定要不要重試：

計算目前重試次數
retryCount = etlTask.ExecutionCount - 1（ExecutionCount 在每次 UpdateTaskStatusToRunning 都會 +1）
若 retryCount < ShopEtlFlow_RetryCount 且非 debug mode
Slack 通知「等待重新執行」→ Thread.Sleep(RetryInterval * 1000)（同一個 process 原地等待，不是靠排程器重新啟動一個新進程）→ 重新 GetTask 拿最新資料 → continue 回到迴圈頂端再次呼叫 DoProcess
若重試次數已用盡
Slack 通知「發生錯誤」→ throw; 往上拋給 Main
重點：DB 上暫時出現的 Error 狀態，只要重試次數還沒用完，下一輪 DoProcess 一開始就會被 UpdateTaskStatusToRunning 覆蓋成 Running。最終狀態只會是 Finish／Pass（成功），或是耗盡重試後停在 Error（真正失敗）。
RunFlowById\Program.cs L248-296

5. 最外層 Main 的兜底處理

情況isExecuteFlow是否寫 ProgramException Log原因
已經進入過 DoProcess（哪怕馬上失敗） true 否 Flow 內部已經寫過 EtlFlowTaskLog 且 DB 狀態已更新為 Error，不需要重複紀錄
連 DoProcess 都還沒進去就例外（CLI 參數錯誤、CreateFlowTask 失敗、GetFlowIdByOptions 找不到 Flow…） false 是 此時 DB 連 Task 記錄都還沒建立，只能靠 WriteProgramExceptionLog 寫入當日共用的 ProgramException 檔案

Windows Task Scheduler 監控 — 本機測試操作手冊

本文件記錄如何在本機建立測試用排程任務、模擬各種真實情境（正常、心跳型、執行失敗、漏排）， 以及如何用 GUI 或 PowerShell 手動驗證結果，搭配 WindowsTaskManager.Monitor 觀察告警行為。

1測試任務總覽

全部建立在 Task Scheduler 的 \WTMTest\ 資料夾下，Action 統一寫入 C:\91APP\AI_Devs\taskmanager\test-logs\，方便事後比對。

任務名稱模擬類型Trigger 設計用途
TypeA-WeeklyA - Weekly每週（本週當天）09:58 觸發一次驗證單次事件型 + Weekly Trigger 判斷
TypeB-DailySingleB - Daily 單次每天 09:58 觸發一次驗證單次事件型 + Daily Trigger 判斷
TypeC-HeartbeatC - 心跳型指定時間起，每 2 分鐘重複一次，持續 1 小時驗證 Repetition 判斷為心跳型，走 gap 計算模型
TypeD-MultipleTriggersD - 多組獨立 Trigger三組獨立 Daily Trigger（間隔 3 分鐘）驗證 GetRunTimes 能正確合併多組 Trigger 的候選時間
TypeE-Failure執行失敗Daily 觸發一次Action 執行後主動 exit /b 1，驗證「有跑但失敗」告警分支
TypeF-Missed漏排（該跑沒跑）Daily 觸發一次 + RunOnlyIfIdle 條件觸發時間到但因閒置條件不滿足被跳過，驗證「漏排」告警分支
清理提醒：測試完畢後記得移除全部測試任務： 
Get-ScheduledTask -TaskPath "\WTMTest\" | Unregister-ScheduledTask -Confirm:$false

2第三方雜訊任務排除機制

實測時發現 OneDrive、GoogleUpdater、MicrosoftEdgeUpdateTask 等系統內建第三方任務會被誤判為心跳型並產生大量無意義告警，因此新增可設定的排除規則。

設計方式：路徑萬用字元清單

在 MonitorOptions 新增 ExcludedTaskPathPatterns（字串陣列，支援 * 萬用字元），設定於 appsettings.json：

"ExcludedTaskPathPatterns": [
  "\\OneDrive*",
  "\\GoogleSystem\\*",
  "\\GoogleUpdateTaskMachine*",
  "\\MicrosoftEdgeUpdateTask*",
  "\\Lenovo\\*",
  "\\LenovoUpdate*"
]

實作重點

  • SchedulerReader 建構子注入 IOptions<MonitorOptions>，啟動時把萬用字元 pattern 預先編譯成 Regex（Compiled、忽略大小寫），避免每輪巡檢重複解析字串。
  • GetEnabledTasks() 在既有「排除 \Microsoft\ 系統任務」判斷之後，新增「排除自訂規則」判斷，兩者各自獨立計數，統計 log 一併呈現。
  • 之後若再遇到新的雜訊任務，只要在設定檔加一行 pattern，不需要重新編譯部署。

3「執行失敗」案例：設計與手動驗證

最容易模擬的情境——讓 Action 確實執行，但回傳非 0 的結果碼。

建立方式

$actionFail = New-ScheduledTaskAction -Execute "cmd.exe" `
    -Argument '/c echo [%date% %time%] TypeE-Failure ran >> "...\TypeE-Failure.log" & exit /b 1'
$triggerFail = New-ScheduledTaskTrigger -Daily -At (Get-Date).AddMinutes(3)
Register-ScheduledTask -TaskName "TypeE-Failure" -TaskPath "\WTMTest\" `
    -Action $actionFail -Trigger $triggerFail -Force

方法一：PowerShell 快速確認

Get-ScheduledTaskInfo -TaskName "TypeE-Failure" -TaskPath "\WTMTest\" |
    Select-Object LastRunTime, LastTaskResult, NextRunTime

實測結果：LastTaskResult = 1，log 檔確實有寫入內容 → 代表 Action 有執行，但回傳失敗。

方法二：直接查 Event Log（跟程式邏輯一致）

Get-WinEvent -LogName "Microsoft-Windows-TaskScheduler/Operational" `
    -FilterXPath "*[System[(EventID=200 or EventID=201)]] and *[EventData[Data[@Name='TaskName']='\WTMTest\TypeE-Failure']]" `
    -MaxEvents 10 | Select-Object TimeCreated, Id, Message

查到兩筆事件：

EventID 200  Task Scheduler launched action "cmd.exe" ...
EventID 201  Task Scheduler successfully completed task ... with return code 2147942401.

方法三：GUI（工作排程器 + Event Viewer）

  1. 執行 taskschd.msc，左側展開「工作排程器程式庫 → WTMTest」，找到 TypeE-Failure。
  2. 清單畫面「上次執行結果（Last Run Result）」欄位直接顯示 (0x1)（其他正常任務會顯示「操作順利完成 (0x0)」）。
  3. 點選任務後，下方「歷程記錄（History）」分頁——若顯示「已停用」，需先按右側「動作」欄的啟用所有工作歷程記錄。
  4. History 分頁可看到事件序列：100 Task Started → 200 Action started → 201 Action completed (Operational Code 2) → 102 Task completed (Operational Code 2)。
    Operational Code 顯示 (2) 而非 (0)，即代表結果非成功。
判斷依據一致性：GUI 清單欄位 (0x1) + History 的 Operational Code (2) + PowerShell 查到的 ResultCode 2147942401，三者都指向同一個「失敗」結論，只是呈現層級不同（詳見第 4 節的進位制說明）。

4結果碼數字辨識：0x1 是什麼意思？

同一個失敗結果，會在不同工具、不同層級用完全不同的數字格式呈現，容易造成誤解。

0x 開頭代表十六進位（hexadecimal），不是二進位。 這是 Windows / 程式設計裡標準的十六進位前綴寫法。

三種呈現方式其實是同一件事

顯示位置數值說明
工作排程器 GUI「Last Run Result」欄0x1直接顯示 Task Scheduler 記錄的原始 exit code（16 進位）
Event Log EventID 201 的 ResultCode（16 進位）0x80070001Win32 exit code 包裝成標準 HRESULT 格式
Event Log ResultCode（十進位顯示）2147942401上面 HRESULT 直接轉成十進位數字（PowerShell/程式常見顯示方式）

HRESULT 0x80070001 拆解

組成結構

  • 8：Severity bit，代表這是一個 Error
  • 007：Facility code FACILITY_WIN32，代表這個錯誤是從 Win32 API 錯誤碼轉換而來
  • 0001：真正的原始錯誤碼，也就是你設定的 exit /b 1

驗證換算

PS> "{0:X}" -f 2147942401
80070001

十進位 2147942401 換算成十六進位確實是 80070001，兩者是同一個數字的不同進位表示。

為什麼我們的程式不會被格式差異搞混？

SchedulerReader.GetHistory() 判斷成功與否的邏輯很寬鬆，只認固定幾種「0」的寫法：

var isSuccess = resultCode is "0" or "0x0" or "0x00000000";

只要不是這三種表示法，一律視為失敗——不管數字是 1、0x80070001 還是 2147942401，只要不是 0，就會被正確判定為 IsSuccess = false，不受呈現格式差異影響。

5「漏排」案例：設計與手動驗證

漏排不能用「停用任務」模擬——停用的任務本來就會被監控排除，不算漏排。真正的漏排是「任務仍是 Enabled、Trigger 時間到了，但因某種條件不滿足而被 Task Scheduler 跳過」。

建立方式：RunOnlyIfIdle 條件

$settingsMiss = New-ScheduledTaskSettingsSet `
    -RunOnlyIfIdle `
    -IdleDuration (New-TimeSpan -Hours 1) `
    -IdleWaitTimeout (New-TimeSpan -Hours 2)

Register-ScheduledTask -TaskName "TypeF-Missed" -TaskPath "\WTMTest\" `
    -Action $actionMiss -Trigger $triggerMiss -Settings $settingsMiss -Force

三個關鍵參數

參數作用
-RunOnlyIfIdle開啟「僅在電腦閒置時啟動這項工作」條件開關（對應 GUI「條件」分頁的閒置設定）
-IdleDuration電腦必須連續閒置多久才算符合閒置條件（設 1 小時）
-IdleWaitTimeoutTrigger 時間到了之後，願意等待閒置條件成立的最長時間（設 2 小時），超過還沒閒置就直接放棄、跳過這次執行
因為操作機器時 Windows 判定的「閒置」（滑鼠鍵盤無動作）不會累積到 1 小時，Trigger 時間到了之後，Task Scheduler 會在 IdleWaitTimeout 期間內持續檢查、始終不滿足條件，最終這次觸發就被跳過。 任務本身仍是 Enabled，Trigger 排程邏輯也正常，只是「執行條件」擋住了它——這正是最貼近真實世界「該跑卻沒跑」的情境。

GUI 手動設定位置

工作排程器 → 該任務內容 → 條件 分頁 → 勾選「僅當電腦閒置以下時間時啟動此工作」。

驗證結果

實測截圖中 TypeF-Missed 這一列：

  • Last Run Time：1999/11/30 上午 12:00:00 ← Task Scheduler 用這個「從未執行」的預設佔位時間表示尚未跑過
  • Last Run Result：工作尚未執行 (0x41303) ← 明確代表 Trigger 有設定，但從未真正被執行

對照之下，GetRunTimes 依然會把 Trigger 定義的候選時間算出來（因為它是純粹依 Trigger 排程規則計算理論時間，不考慮執行條件），但 GetHistory 查 Event Log 完全找不到對應紀錄——兩者的落差正是「漏排」判斷的核心依據。

6三種案例快速比對

✅ 正常執行

LastRunTime ≈ 候選時間，LastTaskResult = 0

GUI 顯示「操作順利完成 (0x0)」

❌ 執行失敗

LastRunTime ≈ 候選時間，LastTaskResult ≠ 0

GUI 顯示 (0x1) 等非零結果碼；History 有完整 200/201/102 事件但 Operational Code 非 0

⚠️ 漏排

LastRunTime 遠早於候選時間（或仍是 1999/11/30 預設值）

GUI 顯示「工作尚未執行 (0x41303)」；Event Log 對應時間點完全查無 200/201 事件

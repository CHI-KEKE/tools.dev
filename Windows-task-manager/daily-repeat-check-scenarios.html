類型 C · Daily + 高頻重複 Trigger（心跳模式）

「每 30 分鐘巡檢一次」下，永久性高頻心跳任務的監控設計

Trigger 範例：Daily, Start 2:01:52 PM, Repeat every 5 min for a duration of 1 day。 因為 Duration（1天）剛好等於 Daily 的 Recur 間隔（1天），這個重複區間會無縫銜接下一次的 Daily 觸發， 實務上等於是永久性、不間斷每 5 分鐘觸發一次的心跳，起始時間的幾點幾分只是相位，不具監控意義。 採用策略：放棄「起始時間 / 視窗查詢」模型，改用 gap = now − task.LastRunTime 心跳比對， GapThresholdMinutes=10，巡檢頻率 CheckIntervalMinutes=30。

1基本設定回顧 —— 為什麼改用「心跳模式」取代起始時間 / 視窗查詢

項目說明
Trigger 本質Daily Start=2:01:52 PM + Repeat every 5min, Duration=1day → Duration 剛好等於 Recur 間隔，重複區間無縫銜接下一次 Daily 觸發，等於永久不間斷心跳
❌ 方案一：只檢查起始時間只要起始時間有觸發就結案，之後永遠不再檢查 → 若起始成功、但後續心跳中途整個停止，完全偵測不到（本文件先前版本的缺陷）
❌ 方案二：固定視窗查詢（如「往前拉10分鐘查 GetHistory」）視窗與巡檢間隔（30分鐘）沒有對齊時，兩次巡檢的視窗之間會出現查詢死角（例如視窗10分鐘、間隔30分鐘 → 中間20分鐘無人查詢），屬於離散片段覆蓋，設計上不直觀且容易抓錯參數
✅ 採用方案：心跳 Gap 比對直接讀取 Task Scheduler 內建屬性 task.LastRunTime（每次任一次重複實例觸發都會更新），用連續數值 gap = now − LastRunTime 與閾值比較，不受視窗覆蓋問題影響
核心概念：心跳型任務要監控的重點不是「哪一個時間點該執行」，而是「心跳有沒有持續在跳」。 用連續遞增的 gap 取代離散的時間點比對，任何時刻中斷都必然反映在 gap 變大上，不會有查詢死角。 
// 心跳模式：不需要 GetRunTimes / GetHistory，直接讀 Task 屬性
GapThresholdMinutes = 10      // 允許心跳延遲的容忍值（跑1~2次的緩衝）
CheckIntervalMinutes = 30     // 巡檢頻率（沿用原設定，不影響心跳判斷）

for task in enabledTasks:
    if task.Trigger 不是心跳型（無 Repetition 或 Duration≠Recur間隔）:
        continue  // 交由類型A/B/C(單次)邏輯處理

    gap = now - task.LastRunTime

    if gap <= GapThresholdMinutes:
        正常（心跳持續）
        if task.LastTaskResult != 0:
            告警「最近一次心跳執行失敗」
    else:
        告警「心跳已停止，距離最後一次執行已 {gap} 分鐘」
邊界防護：若 Duration 到期後心跳循環自然結束（如任務被改為只跑固定一段時間）， 應先確認 now 是否仍落在 Trigger 的有效範圍內（StartBoundary ≤ now ≤ EndBoundary），避免循環正常結束後被誤判為心跳停止。

6小結：類型 C 心跳模式設計總覽

面向類型 C（心跳模式，本版）類型 A/B（單次事件模式）
判斷依據gap = now − task.LastRunTime（連續數值）GetRunTimes 展開的離散候選時間點 T
是否需要 GetHistory 視窗查詢不需要，直接讀 LastRunTime / LastTaskResult 屬性需要，GetHistory(taskPath, T−Tolerance, T+Tolerance)
是否需要時間閘門等待不需要，gap 超標即是既定事實，立即告警需要，now ≥ T+Tolerance 才能下結論
是否需要 resolved 去重不需要，每輪巡檢都是獨立評估同一個持續狀態需要，避免 Lookback 重疊造成同一筆 T 被重複告警
閾值設定GapThresholdMinutes，依任務心跳頻率個別調整ToleranceMinutes=30 / LookbackMinutes=90，全類型共用
邊界防護需確認 now 落在 Trigger 有效範圍內，避免循環自然結束被誤判需確認跨日/跨週邊界的候選歸屬正確
結論：心跳型任務（Duration＝Recur間隔、無縫銜接的高頻重複）本質上是「持續運作中的狀態」， 不適合套用單次事件模型（起始時間檢查 / 視窗查詢）。改用 gap = now − LastRunTime 直接比對， 邏輯更簡單、沒有查詢死角，且能同時涵蓋「從未啟動」與「啟動後中途停止」兩種情況，不需要額外的前處理（清空 Repetition）或去重機制。

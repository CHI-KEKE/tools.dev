EtlDB Monitor 告警 SQL 白話解說

拆解目前 Grafana Dashboard 用來偵測 ETL Flow「失敗」與「漏排」並發送 Slack 告警的 T-SQL 查詢，逐段說明它在做什麼、為什麼這樣寫

1. 一句話總結

這段 SQL 會針對「登記在監控清單裡的每一個 ETL Flow」，檢查它最近有沒有在該有的執行週期內跑過一次、而且跑的結果不是失敗；只要「沒跑」或「跑了但失敗」，就輸出一個 0（異常），其餘輸出 1（健康），交給 Grafana 依照這個 0/1 訊號畫圖並在持續異常時發 Slack 告警。

2. 整體資料流（4 個階段）

① 決定要監控誰
從 EtlFlowMonitor 設定表，篩出「這台伺服器」＋「這個告警群組」底下登記要監控的 Flow 清單，並取得每個 Flow 自己的「應該多久跑一次（Frequency）」
→
② 找每個 Flow 最近一次執行
在「Frequency + 10 分鐘緩衝」的時間窗內，找該 Flow 最新一筆 EtlFlowTask；找不到就是 NULL（代表沒跑過 = 漏排嫌疑）
→
③ 判斷健康或異常
狀態是 Finish/Pass/Ready/Running 且有資料 → 健康(1)；狀態是 Error，或窗口內完全查無資料 → 異常(0)
→
④ 輸出成 Grafana 時間序列
把 0/1 結果、時間、Flow Id/Name 包裝成 Grafana 看得懂的格式，讓 Grafana Alert Rule 去判斷「持續異常多久」就發送 Slack

3. 逐段拆解

Step 1：篩選監控名單 白名單機制

-- 找出這個告警群組要監控的 Flow
SELECT DISTINCT EtlFlowMonitor_ShopEtlFlowId
FROM EtlFlowMonitor
WHERE ShopEtlFlow_AlertGroups = @alertGroups

-- 再篩出跑在這台伺服器的
WHERE EtlFlowMonitor_Server = @serverName

EtlFlowMonitor 是一張「登記表」：每一列代表「某個 Flow 需要被監控、屬於哪個團隊(AlertGroups)負責、跑在哪台機器、預期多久跑一次(Frequency)」。這一步就是先把「不歸這次告警群組/伺服器管」的 Flow 排除掉，只留下要檢查的清單，並隨身帶著每個 Flow 自己的 Frequency（單位：秒）。

白名單的好處：不是每個 Flow 都要被監控告警（有些是一次性任務、測試用途），所以要先在 EtlFlowMonitor 手動登記才會被這套邏輯檢查到。

Step 2：找每個 Flow 最近一次執行紀錄 漏排偵測的關鍵

WHERE EtlFlowTask_CreatedDateTime >= DATEADD(SECOND, -Frequency - 600, GETDATE())
  AND EtlFlowTask_CreatedDateTime <= DATEADD(SECOND,  Frequency + 600, GETDATE())

白話翻譯：「找這個 Flow 在過去 (應有週期 + 10分鐘緩衝) 這段時間內有沒有建立過任何一次執行紀錄」。10 分鐘緩衝是為了容忍排程本身的延遲抖動，避免誤判。

重點在後面用 RIGHT JOIN #tmpMonitorFlow（監控名單）去接 EtlFlowTask（實際執行紀錄）：就算這個時間窗內完全沒有任何一筆執行紀錄，這個 Flow 依然會出現在結果中，只是欄位全部是 NULL。這正是偵測「漏排」最直接的寫法——用 join 的方向去保留「查無資料」的那一列，而不是額外寫一段「有沒有漏排」的判斷式。

如果同一個時間窗內有多筆執行紀錄（例如同一個 Flow 短時間內跑了兩次），會取 StatusUpdatedDateTime 最新的那一筆代表目前狀態。

Step 3：健康 / 異常判斷 把「失敗」和「漏排」合併成同一個訊號

CASE WHEN FlowStatus IN ('Finish','Pass','Ready','Running')
      AND UpdatedDateTime IS NOT NULL
     THEN 1   -- 健康
     ELSE 0        -- 異常
END
結果值什麼情況會出現意義
1（健康） 窗口內找得到執行紀錄，且狀態是 Finish／Pass／Ready／Running 已完成、被中斷但非失敗、正在排隊等執行、正在執行中 — 都不算異常
0（異常，原因A） 狀態是 Error 真的執行失敗
0（異常，原因B） 窗口內完全沒有任何執行紀錄（UpdatedDateTime IS NULL） 該跑的時候沒有跑 = 漏排

這就是這段 SQL 最聰明的地方：不需要寫兩套告警規則分別處理「失敗」和「漏排」，通通壓縮成同一個 0/1 訊號，Grafana 那邊只要盯著這個訊號就好。

Step 4：包裝成 Grafana 看得懂的格式

SELECT
    status_value AS value,
    event_time   AS time,
    CONCAT('id=',   EtlFlowId)   AS tag1,
    CONCAT('name=', EtlFlowName) AS tag2

value／time 是 Grafana 時間序列圖表要的標準欄位；tag1／tag2 把 Flow 的 Id 和名稱編碼成字串，讓 Grafana 依照 tag 把每個 Flow 拆成獨立的一條線。之後 Grafana 的 Alert Rule 只要設定「當某條線的 value 持續等於 0 超過 N 分鐘」就觸發，並透過 Alertmanager 發送到 Slack。

4. 圖解：一個 Flow 被判定「漏排」的流程

Flow 登記在 EtlFlowMonitor，Frequency = 3600 秒（應該每小時跑一次）
屬於 sg-es 告警群組、跑在 SG-HK-PushWK11
實際上這個 Flow 已經 2 小時沒有跑了
可能是 Windows Task Scheduler 本身沒有觸發、或前置條件不滿足被跳過
SQL 檢查「過去 (3600+600) 秒內」有沒有 EtlFlowTask
完全查無資料 → UpdatedDateTime = NULL
判定 status_value = 0，event_time = 現在時間
輸出給 Grafana；因為每次重新查詢都會用「現在時間」當作這個 0 的時間點，這條線會持續往右延伸，直到 Grafana 判斷「已經異常超過設定的持續時間」才真正發出告警

5. 值得留意的幾個限制

限制說明
重試中的暫時 Error 可能被誤判 如果 Flow 正在自動重試中途（尚未耗盡重試次數），DB 上會短暫顯示 Error，這段 SQL 沒有特別排除這種暫時態，會馬上輸出 0；實務上要靠 Grafana Alert 的「持續 N 分鐘才觸發」機制去吸收這種短暫抖動
緩衝時間固定 600 秒，不管每個 Flow 重試設定多長 如果某個 Flow 的重試間隔設定超過 10 分鐘，有可能在它還在合理重試中就被判定漏排/異常
只看 Flow 整體層級 看不出是哪一個步驟(TaskSlave)失敗，要進一步除錯還是得回頭查 EtlFlowTask_Id 的詳細記錄

01 新增功能 建立 Slack 告警通知機制 ▶
問題
原本只有 Log Error 記錄漏排/執行異常的排程，維運人員需要主動去看 Log 才會知道，無法即時通知團隊。
解法
  • 新增 SlackOptions 設定（Webhook URL、Enabled、TimeoutSeconds）
  • 新增 SlackAlertNotifier，透過 HttpClient 呼叫 Slack Incoming Webhook
  • 新增 CompositeAlertNotifier，讓 Log 記錄與 Slack 通知並行、互不影響（其中一個失敗不影響另一個）
涉及檔案：Options\SlackOptions.cs Services\SlackAlertNotifier.cs Services\CompositeAlertNotifier.cs Program.cs
02 體驗優化 告警訊息資訊太少，補齊完整排程資訊 ▶
問題
第一版告警訊息只有「任務名稱、預期執行時間、狀態」，資訊量太少，無法判斷問題。且使用 :rotating_light: 警燈 emoji 不適合表達「漏排」的感覺。
解法
  • 新增 TaskDetailInfo（排程名稱、位置、建立者、描述、觸發條件、執行動作）並在告警時一併讀取顯示
  • 「漏排告警」emoji 從 :rotating_light: 改為 :ghost:，更貼近「漏掉／不見」的感覺
  • 失敗/異常告警同樣套用完整資訊格式，維持一致體驗
涉及檔案：Models\MonitoredTask.cs Services\SchedulerReader.cs（GetTaskDetail）Services\SlackAlertNotifier.cs
03 體驗優化 Slack 訊息左側加上顏色分類線 ▶
問題
參考截圖範例（如 CyberSource Payment 告警），希望 Slack 訊息左側有一條顏色線美化告警訊息、快速分辨告警類型。第一次嘗試在 blocks 格式下加 color 無效。
解法
  • 查證發現 Slack 規則：attachment 一旦使用 blocks 格式，color 屬性就會失效
  • 改用 Slack 舊式 classic attachment 格式（fields + pretext），才能正確顯示左側顏色線
  • 依告警類型上色：漏排 #8E44AD 紫、失敗 #E01E5A 紅、心跳停止 #ECB22E 黃
涉及檔案：Services\SlackAlertNotifier.cs（BuildAttachment）
04 釐清說明 「執行動作」內容顯示「...」被以為是省略 ▶
問題
告警訊息中執行動作顯示 cmd.exe /c echo ... & exit /b 1，使用者以為系統把內容截斷省略了。
解法
確認 ExecAction.ToString()（Microsoft.Win32.TaskScheduler 套件）本身沒有任何截斷邏輯，「...」只是測試時手動輸入的示意文字，並非程式實際輸出，無需修改程式碼。
05 新增功能 告警訊息加上市場／環境提示，並可透過 Config 調整 ▶
問題
多個市場/環境（如 HK／QA）同時監控時，收到告警無法立即分辨來源，需要能方便修改的設定。
解法
  • 新增 SlackOptions.Market / SlackOptions.Environment 設定值
  • 告警訊息第一個欄位顯示 :globe_with_meridians: 市場 HK／環境 QA（任一有設定才顯示）
  • 純 Config 調整，不需改程式碼
涉及檔案：appsettings.json Options\SlackOptions.cs
06 Bug 修復 誤判「執行失敗」：ResultCode 267009 其實是正常執行中 ▶
問題
Prod 實測收到 DispatchInActiveConversationNotification 執行失敗告警（ResultCode=267009），但網站歷史紀錄顯示 38/38 全部成功，完全看不出是哪一筆失敗。
解法
根本原因：267009（0x00041301）是 Windows 的 SCHED_S_TASK_RUNNING，屬於「目前仍在執行中」的資訊性代碼，並非真正的失敗。
  • 新增 IsGenuineFailureResultCode()，將已知的 SCHED_S_* 資訊性代碼（267009 執行中、267010 已停用、267011 尚未執行等）排除在「真正失敗」判斷之外
  • 刻意保留 267014（SCHED_S_TASK_TERMINATED，強制終止）仍視為失敗，因為這種情況仍值得告警
涉及檔案：Workers\TaskMonitorWorker.cs
07 Bug 修復 Prod 執行 Console 顯示「實際納入監控 0 個」，不合理 ▶
問題
在 Prod 直接執行 Monitor Console，Log 顯示總計 103 個任務全被判定為系統任務、實際納入監控 0 個，但截圖顯示 Task Scheduler 裡明明有許多自訂排程資料夾（ETL Service、Member、OTM 等）。
解法
根本原因：經典 UAC 權限問題 — Console 若未以「系統管理員身分執行」，Task Scheduler COM API 會「無異常地」只回傳過濾後 Token 可見的任務（通常只有 \Microsoft\...），看起來像是掃描乾淨、但其實是權限不足。
  • 掃描開始時記錄目前可見的頂層資料夾清單，只有 Microsoft 時給出提示
  • 新增 IsRunningElevated() 檢查，未提升權限時記錄明確 Warning，建議以系統管理員身分執行或部署為 Windows Service
涉及檔案：Services\SchedulerReader.cs
08 新增功能 告警連結網域可設定化 ▶
問題
告警訊息中提供的歷史紀錄連結網域是寫死在程式碼中的，無法因應不同市場/環境切換。
解法
新增 SlackOptions.WebsiteBaseUrl 設定，BuildHistoryUrl 改為依此參數組出連結；未設定時顯示提示文字而非產生無效連結，不需改程式碼即可切換網域。
涉及檔案：appsettings.json Services\SlackAlertNotifier.cs
09 體驗優化 網站 History 頁面：無 Event Log 紀錄時容易誤判「沒執行過」 ▶
問題
\Order\SE_Order_ETL_ElemisOfflineOrder 顯示「沒有執行歷史記錄」，但實際上 OSM Log 檔案確實存在，維運人員需要手動觸發「Log 查詢」才能發現，容易誤判為漏排。
解法
  • 在 History 頁面加上提示：Event Log 是環狀緩衝區，可能已遺失紀錄，需要進一步確認 Log 檔案
  • 當 ETL 任務沒有 Event Log 歷史時，網頁載入即自動帶入 3 天區間並自動觸發既有的「Log 查詢（依時間窗精準比對）」功能，直接顯示 OSM Log 證據，不需要再手動操作
涉及檔案：Pages\Tasks\History.cshtml（WindowsTaskManager 網站專案）
10 Bug 修復（核心） Monitor 誤發漏排告警：心跳型任務未考慮觸發器「作用時間窗」 ▶
問題
同一個問題再次確認後，發現真正的 Bug 是 Monitor 本身誤發告警，而非網站顯示問題。\Order\SE_Order_ETL_ElemisOfflineOrder 每天固定被誤發「心跳已停止」告警。
解法
根本原因：該任務觸發器是「每天 11:08 PM 開始，每 30 分鐘重複一次，持續 3 小時」— 也就是只在 23:08~02:08 這 3 小時內是「心跳作用中」，之後自然安靜 21 小時到隔天。原本的判斷只看「現在時間 - 最後執行時間 > 閾值」，完全沒有意識到觸發器只在特定時間窗內才會重複，導致整個安靜期每 30 分鐘都誤發一次告警。
  • 新增 TaskMonitorPlan.IsWithinHeartbeatWindow，透過 Task.GetRunTimes() 查詢目前是否仍在觸發器的重複時間窗內
  • CheckHeartbeatTask() 判斷 gap 超過閾值時，若已不在心跳作用視窗內，判定為「正常（心跳視窗外的安靜期）」，直接跳過、不告警
  • 邊界情況處理：查詢範圍取 max(最後執行時間, 現在-閾值) 並只採計「大於最後執行時間」的時間點，避免視窗剛結束瞬間仍誤判一次
涉及檔案：Models\MonitoredTask.cs Services\SchedulerReader.cs Workers\TaskMonitorWorker.cs
11 釐清說明 確認心跳型判斷邏輯：仍需檢查時間窗內是否有應執行時間點 ▶
問題
使用者提問確認：即使判定為心跳型任務，是否仍需要確認檢查時間窗內有應執行的時間點才會告警？
解法
確認邏輯為「兩個條件同時成立」才會告警：① gap（距上次執行的時間差）超過閾值，且 ② 目前時間仍在觸發器的重複作用視窗內。任一條件不成立就不告警。
12 新增功能 失敗原因 ResultCode 不易讀懂 + 加上負責團隊 Slack Tag ▶
問題
1. 失敗告警顯示如「有執行紀錄但結果為失敗（3762504530）」，維運人員看不懂這串數字代表什麼。
2. 希望告警標題可以像 :x: 排程執行失敗告警，請 xxx 團隊協助確認 一樣，直接 tag 負責團隊。
解法
  • 新增 ResultCodeFormatter，將原始 ResultCode 轉換成 0xXXXXXXXX（友善說明） 格式（例如 0xE0434352 = .NET 未捕捉例外），邏輯移植自網站既有的 GetFriendlyErrorMessage
  • 新增 SlackOptions.Teams（團隊清單：G11N、SG ECom RDs、SG OMO RDs 及對應 Slack User Group ID）與 TaskTeamMappings（任務路徑萬用字元 → 團隊名稱對應規則）
  • 比對成功時在標題後方加上真正的 Slack User Group @mention（<!subteam^ID|@handle>），會實際觸發通知給該團隊所有成員
涉及檔案：Services\ResultCodeFormatter.cs（新增）Options\SlackOptions.cs Services\SlackAlertNotifier.cs appsettings.json
13 釐清說明 確認：沒比對到負責團隊時維持原樣，不加提示文字 ▶
問題
確認當 TaskTeamMappings 沒有比對成功時，標題不應該加上「請 xxx 協助確認」這句話。
解法
確認既有實作已符合需求：FindResponsibleTeam 找不到對應團隊時回傳 null，此時 teamMentionText 為空字串，標題完全維持原樣，無需修改程式碼。
14 Bug 修復 加上團隊 @mention 後，標題粗體效果失效 ▶
問題
實測發現有 tag 團隊時，Slack 訊息標題變成「排程執行失敗告警，請 @sg-ecom 協助確認」，「排程執行失敗告警」這幾個字沒有正常套用粗體。
解法
根本原因：粗體標記 *text* 結尾緊接全形標點「，」、中間沒有空白時，Slack mrkdwn 會判斷邊界失敗而不套用粗體。修正為在星號結尾與後面文字之間加一個半形空白（*標題* ，請...），確保粗體正常顯示。
涉及檔案：Services\SlackAlertNotifier.cs（BuildAttachment，pretext 組字邏輯）
15 Bug 修復 ResultCode 3762504530 仍顯示原始數字，格式化沒生效 ▶
問題
即使已加上 ResultCodeFormatter，實測訊息仍顯示「有執行紀錄但結果為失敗（3762504530）」，格式化沒有生效。
解法
根本原因：3762504530 超過 int.MaxValue（約 21 億），原本用 int.TryParse 解析十進位字串會直接失敗，導致邏輯掉到「無法解析、原樣回傳」的分支。修正為改用 long 承接十進位字串、再安全轉型為 uint，涵蓋完整的 ResultCode 範圍（0~4294967295）。修正後正確顯示為 0xE0434352（.NET 程式丟出未捕捉的例外（CLR Exception））。
涉及檔案：Services\ResultCodeFormatter.cs
16 新增功能 每日健康回報：固定時間發送「監控服務仍正常運作」訊息 ▶
問題
希望每天固定時間確認 Monitor 監控服務今天有持續正常運作、沒有中斷或當機，並主動發訊息到頻道告知團隊「今日 ETL 監控排程順利執行完成」，且時間點要能透過 Config 隨時調整。
解法
  • 新增 SlackOptions.DailyHeartbeat 設定：Enabled（是否啟用）、SendTime（每天發送時間，格式 HH:mm，目前設為 17:00，可隨時修改）、Message（訊息文字，可自訂）
  • 搭上既有巡檢週期（每 30 分鐘一輪）判斷：當天尚未發送過，且現在時間已到達或超過設定時間，就發送一次並記錄「今天已發送」
  • 新增 SlackAlertNotifier.NotifyDailyHeartbeat()，獨立於一般告警邏輯，發送綠色 :white_check_mark: 訊息，同樣附帶市場/環境資訊
涉及檔案：Options\SlackOptions.cs（DailyHeartbeatOptions）Services\SlackAlertNotifier.cs Workers\TaskMonitorWorker.cs（CheckDailyHeartbeat）appsettings.json

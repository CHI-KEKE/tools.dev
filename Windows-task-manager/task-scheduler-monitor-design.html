1排程任務的啟用/停用與執行狀態判斷

對應 Microsoft.Win32.TaskScheduler 函式庫的兩個核心屬性

Enabled — 是否允許被觸發（靜態設定）

對應 Task.Enabled 屬性（底層為 COM IRegisteredTask.Enabled / XML 定義中的 <Settings><Enabled>true/false</Enabled>）。這是使用者手動設定的旗標，代表任務 是否被允許觸發執行，與目前有沒有在跑無關。

State — 目前實際執行狀態（動態值）

對應 Task.State（TaskState enum），由 Windows 依任務目前實際運行情形決定：

狀態值意義
Unknown無法判斷
Disabled任務被停用
Queued已排入佇列，等待執行
Ready已啟用，等待下次觸發時間
Running正在執行中
關鍵重點：Enabled 是「是否允許被觸發」的靜態設定值，State 是「目前實際狀態」的動態值。 兩者有關聯（停用時 State 一定是 Disabled），但不完全等價 —— 啟用的任務 State 仍可能是 Ready（閒置）或 Running（執行中）。

2「該跑卻沒跑」的判斷邏輯設計

如何事後確認排程在特定時間該執行卻沒有執行

單純篩選 State == Ready 並不足夠，需要結合 Trigger 定義與實際執行歷史來判斷：

1. 排除 Disabled 任務
→
2. 用 Trigger 算出應執行時間
→
3. 比對實際執行紀錄
情境判斷條件結論
漏排 LastRunTime < expectedLastRun（或為 null） 該跑沒跑
執行失敗 LastRunTime ≈ expectedLastRun 但 LastTaskResult != 0 有跑但失敗
卡死（v1 暫不實作） State 持續 Running 超過預期執行時長 可能卡死佔用

技術關鍵：如何計算「理論上應執行時間」

Microsoft.Win32.TaskScheduler 提供內建方法 Task.GetRunTimes(DateTime start, DateTime end, uint count)， 可直接算出某個時間區間內「理論上應該觸發的所有時間點」，不需要自行解析 Trigger 的週期規則（每日/每週/Cron 等）。

技術關鍵：如何取得「實際執行結果」

透過 Windows Event Log 頻道 Microsoft-Windows-TaskScheduler/Operational， 解析 EventID 200（Action started）與 EventID 201（Action completed，含 ResultCode）， 按時間配對成一筆筆執行紀錄，比單純讀取 COM API 的 LastRunTime/LastTaskResult 更可靠。

3告警系統的宿主方案比較

監控巡檢邏輯要跑在哪裡？三種方案的取捨

方案 A：掛在既有網站的 BackgroundService

  • 開發成本最低，共用 DI/Logging
  • 生命週期綁定網站，IIS Recycle / Idle Timeout 會中斷
  • 與網站共用資源，可能互相影響
  • 多 instance 時需額外處理重複執行

方案 B：單次觸發型 Console App

  • 邏輯簡單，跑完即結束
  • 仍需依賴 Windows Task Scheduler 觸發（等於用排程器監控排程器）
  • 告警去重狀態需要額外落地儲存

方案 C：獨立 Worker Service

  • 不依賴網站生命週期，也不依賴外部排程觸發
  • 內部自帶 PeriodicTimer 常駐巡檢
  • 可註冊成 Windows Service，開機自動啟動、當機自動重啟
  • 資源與部署完全獨立於網站
觀念釐清：BackgroundService 是 Microsoft.Extensions.Hosting 的概念， 跟 ASP.NET Core／網站沒有必然關係。Worker Service（dotnet new worker）本質上就是一個 「純背景服務用的 Console 程式」—— 沒有網站、沒有 Kestrel，只有 Generic Host + 你的 BackgroundService。

// SchedulerReader.cs — 計算理論上最後一次應觸發時間
public DateTime? GetExpectedLastRunTime(string taskPath, DateTime windowStart, DateTime windowEnd)
{
    using var ts = new TaskService();
    var task = ts.GetTask(taskPath);
    if (task == null) return null;

    // GetRunTimes 直接回傳區間內所有應觸發時間點，取最後一筆
    var runTimes = task.GetRunTimes(windowStart, windowEnd, 1000);
    return runTimes.Length > 0 ? runTimes[^1] : null;
}
// TaskMonitorWorker.cs — 判斷漏排 / 失敗
var expectedLastRun = _schedulerReader.GetExpectedLastRunTime(taskPath, windowStart, now);
if (expectedLastRun == null) return;               // 區間內無應觸發時間

var deadline = expectedLastRun.Value + tolerance;
if (now < deadline) return;                          // 尚未超過容錯緩衝

var matched = history.FirstOrDefault(近似 expectedLastRun 的執行紀錄);

if (matched == null)              → 漏排告警 (Missed)
else if (!matched.IsSuccess)       → 失敗告警 (Failed)

6部署為 Windows Service

概念說明：什麼是「註冊成 Windows Service」

把 Worker 的執行檔交給 Windows 的服務管理員（Service Control Manager, SCM）接管， 使其成為像「Print Spooler」一樣可在服務清單中看到、開機自動啟動、不需登入帳號即可常駐執行的程式。

現況（dotnet run）註冊成服務後
前景 process，關閉終端機即結束 背景常駐，出現在 services.msc
需手動啟動 可設定開機自動啟動（Automatic）
當機需手動重啟 可設定 Recovery：當機自動重啟
需要使用者登入才能執行 不需登入 Windows 也能背景執行

部署指令（需系統管理員權限）

dotnet publish -c Release -o C:\Services\WindowsTaskManager.Monitor

New-Service -Name "WindowsTaskManager.Monitor" `
  -BinaryPathName "C:\Services\WindowsTaskManager.Monitor\WindowsTaskManager.Monitor.exe" `
  -DisplayName "Windows Task Manager - 排程監控" `
  -StartupType Automatic

Start-Service -Name "WindowsTaskManager.Monitor"
注意：此步驟會在機器上實際安裝系統服務，需要系統管理員權限，且會持續在背景執行、消耗資源， 直到手動移除。建議先於測試環境驗證告警邏輯與門檻值符合預期後，再於正式伺服器部署。

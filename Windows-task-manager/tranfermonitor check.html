用途定位
這是一支「排程巡檢／同步工具」：掃描 Windows 工作排程器（Task Scheduler），把跟 ETL 流程相關的排程資訊同步進監控資料表，並附帶對 Grafana 做健康檢查。

2主流程 (Main)

1

啟動檢查 CheckAppSetting()

讀取 ServerName、WindowsTaskScheduler.Enable，任一缺漏或格式錯誤就丟出 ApplicationException 直接中止程式。

2

列舉所有 Windows Task Scheduler 工作

透過 TaskService.FindAllTasks(x => true) 取得本機所有排程工作，並先查詢 EtlFlowMonitor 現有清單、（可選）查詢 WindowsTaskScheduler 現有有效清單，作為後續比對基準。

3

逐一處理每個排程工作

對每個 Task：若啟用 WindowsTaskScheduler 同步，先呼叫 DoWindowsTaskScheduler() 存檔詳細設定；接著檢查 IsActive / Enabled，取出 ExecAction.Arguments 並解析出 ShopEtlFlowId。

4

組裝並 Upsert 監控資料

計算執行頻率 Frequency = NextRunTime - LastRunTime（秒），查出 FlowName，資料合法則新增或更新 EtlFlowMonitor 紀錄。

5

軟刪除失效的監控項目

比對「原本資料庫已有」與「本次有效更新到」的 FlowId 差集，將不再存在的排程監控紀錄軟刪除（ValidFlag = 0）。

6

CheckGrafanaHealth()

對 Grafana 健康檢查端點發送 GET，若非 2xx 或請求失敗，組出 JSON 訊息 POST 到 Slack Webhook 發送告警。

例外處理策略
單一 Task 處理失敗只記錄 Error log 並繼續下一筆（不中斷整體流程）；但最外層若出現未預期例外，會記錄 Fatal log 並以 Environment.Exit(1) 結束整支程式。

3關鍵邏輯細節

如何從 ExecAction.Arguments 解析出 ShopEtlFlowId

取出排程工作第一個 ExecAction 的 Arguments，以空白切割成陣列後判斷格式：

參數格式判斷條件解析方式
--FlowId 123 第一段包含 --FLOWID 直接 long.TryParse 第二段當作 FlowId
--FlowName xxx 第一段包含 --FLOWNAME 呼叫 GetEtlFlowId() 依名稱查 ShopEtlFlow 表換回 FlowId（找不到或重複則丟例外）
4 段參數（其他排程包裝格式） 參數長度剛好為 4 視第 3 段是否為 --FLOW-ID，解析第 4 段為 FlowId
純數字（舊格式） 不符合上述任何 Option 條件 第一段直接當數字 FlowId；若有第二段須包含目前 ServerName，否則視為主機不符丟例外

DoWindowsTaskScheduler()：Task Scheduler 詳細設定備份

針對每個排程工作，蒐集下列資訊並整理成實體物件：

  • Task 基本屬性：名稱、狀態、Enable、IsActive、上次/下次執行時間、上次執行結果、註冊者、註冊時間、說明、執行帳號、資料夾路徑
  • 所有 Trigger（Event / Time / Daily / Weekly / Monthly / MonthlyDOW / Registration / Boot / Logon / SessionStateChange / Custom 等 10 種類型皆有對應欄位映射）
  • 所有 Action（僅處理 Execute 類型，記錄執行路徑、參數、工作目錄）

比對資料庫中是否已有相同 Name + HostName + FolderPath 的紀錄：無則標記 INSERT，有則標記 UPDATE，最後一併交給 WindowsTaskSchedulerService.RecordWindowsTaskSchedulerInformation() 批次寫入。

4資料庫互動

EtlDB（透過 EtlServices）

  • GetEtlFlowName / GetEtlFlowId — 查 ShopEtlFlow 表（ValidFlag=1）
  • IsMonitorExists — 依 FlowName 檢查 EtlFlowMonitor 是否已存在
  • InsertFlowMonitor INSERT — 新增監控紀錄
  • UpdateFlowFrequency UPDATE — 更新頻率、遞增 UpdatedTimes（0~255 循環）
  • DeleteEtlFlowMonitor SOFT DELETE — 設 ValidFlag=0
  • 皆使用 Dapper + 參數化查詢，無 SQL Injection 疑慮

ExceptionLogDB（透過 WindowsTaskSchedulerService）

  • FindValidScheduler — 依主機名稱查現有有效排程清單
  • RecordWindowsTaskSchedulerInformation — 用暫存表（#tmpInsertTask、#tmpUpdateTask、#tmpAction、#tmpTigger）批次交易寫入 Task / Action / Trigger 三張表
  • 流程：先刪除該 Task 對應的舊 Action/Trigger 明細，再整批重新插入
  • 本次執行未再出現的舊排程，會被批次軟刪除（ValidFlag=0）

5Grafana 健康檢查與 Slack 告警

  1. 檢查 Grafana.HealthCheckUrl 與 Slack.WebhookUrl 是否皆有設定，缺一則跳過檢查。
  2. 對健康檢查端點發送 GET（Timeout 5 秒），HTTP 狀態碼落在 200~299 視為正常。
  3. 若請求例外或狀態碼非 2xx，組出如下 JSON 訊息並 POST 到 Slack Webhook：
{"text": ":sos: *[<ServerName> ETL Monitor]*\nGrafana 服務異常，請立即檢查！\n<HealthCheckUrl>"}

6風險與建議

⚠ SQL Injection 風險

WindowsTaskSchedulerService 在組批次 SQL 時，是用自訂的 SqlString / SqlGuid 手動字串轉義並直接拼接組成 INSERT ... VALUES (...) 的暫存表語法，而非透過 Dapper 參數化。若排程名稱、說明、路徑等來源字串包含特殊字元且轉義不完整，存在 SQL Injection 疑慮，建議改為參數化查詢或 Table-Valued Parameter。

其他觀察
  • 連線字串（含帳密）與 Slack Webhook URL 直接寫在 app.config 明碼中，建議搭配金鑰保管機制。
  • ServerName 比對用 text.ToUpper().Contains(_serverName.ToUpper())，屬字串包含比對，若主機名稱是另一主機名稱的子字串可能誤判。
  • Grafana 健康檢查失敗時僅發 Slack 告警，沒有重試或退避機制。

7總結

TaskSchedulerSyncToFlowMonitor 是一支排程巡檢工具，核心任務有三：

  1. 掃描本機 Windows Task Scheduler，把工作執行參數中夾帶的 ShopEtlFlowId 同步進 ETL 監控表（新增／更新頻率／軟刪除失效項目）。
  2. （可選）把 Task Scheduler 完整設定（工作、觸發條件、執行動作）備份寫入 ExceptionLogDB 供稽核查詢。
  3. 對 Grafana 服務做健康檢查，異常時透過 Slack Webhook 即時告警。

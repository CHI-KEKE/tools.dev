類型 A · Weekly Trigger

「每 30 分鐘巡檢一次」下，Weekly 任務的各種情境

目前採用的最終設定：IntervalMinutes = 30、ToleranceMinutes = 30、LookbackMinutes = 90， 判斷邏輯採用「以 Trigger 時間為中心」的接受窗 + 時間閘門模型。以「每週二 2:30 PM」這個 Weekly Trigger 為例， 逐一檢視：正常結案、漏排告警、延遲但成功、跨週邊界、多個 Weekly 任務併存等情境。

1基本設定回顧

參數設定值說明
IntervalMinutes30每 30 分鐘巡檢一次（例如 2:00, 2:30, 3:00…）
ToleranceMinutes30Trigger 時間前後 30 分鐘內都算合理範圍；也決定「最晚容許時刻」= Trigger + 30分
LookbackMinutes90每次巡檢用 GetRunTimes(now-90分, now) 抓候選時間點。90 分鐘故意大於 Interval(30分)，讓相鄰巡檢視窗重疊 60 分鐘，並滿足 Lookback ≥ Tolerance + Interval = 60 的安全公式（見第8節），留有 30 分鐘餘裕
每次巡檢的核心演算法（每一筆候選 Trigger 時間點 T 都套用）： 
for T in GetRunTimes(now - 90分, now):
    if (task, T) 已經 resolved: continue          // 已下過結論，跳過

    history = GetHistory(taskPath, T - 30分, T + 30分) // 先鎖定任務(taskPath)，再鎖定以 T 為中心的接受窗

    if history 有找到成功或失敗紀錄:
        下結論（成功 → 結案 / 失敗 → 告警）並標記 resolved   // 有證據，不用等閘門
    else if now >= T + 30分:                       // 閘門已開，且仍查無紀錄
        判定「漏排」，發出告警，並標記 resolved
    else:
        continue                                   // 閘門未開、也還查無紀錄 → 略過，下一輪再看
重點：只要查到 History 紀錄（成功或失敗），可以立刻下結論，不需要等時間閘門；時間閘門只用來守住「查無紀錄時，要等多久才能確定是漏排」，避免任務還沒到期就被誤判。

容易誤判的地方：如果每次查詢用「日曆週」切割區間（例如固定抓「本週一 00:00 到現在」再從結果裡挑最後一筆）， 在週一 00:00 剛跨過去的瞬間，程式邏輯上「這週」跟「上週」的判斷容易出錯，導致週日 23:30 這筆被誤判成上週的資料而漏算，或被跨週重複計算兩次。
正確做法：不要用「日曆週」或固定回顧區間去切，永遠用以現在時間為終點、往前推 90 分鐘的滑動窄視窗 —— GetRunTimes(now-90分, now)。 因為視窗是跟著「現在時間」走，不是跟著日曆的週一/週日切，所以不管巡檢當下是週日 23:00 還是跨過午夜到週一 00:00， 只要視窗本身連續銜接、且視窗長度(90分) ≥ 安全公式要求，週日 23:30 這筆必然剛好落在某一次巡檢的視窗內，不會漏抓，重複抓到也會被 resolved 去重擋掉。

7小結：目前設定對 Weekly 類型的影響

面向目前設定（30/30/90）更密集巡檢（例如10~15分鐘）
發現成功執行的延遲最快幾乎即時，最慢約 30 分鐘（下一輪巡檢查到紀錄）最快幾乎即時，最慢約 10~15 分鐘
確認漏排的延遲閘門開啟時間 = Trigger+30分；因剛好與 Interval 對齊，通常在閘門開啟的第一次巡檢就會確認，約 30 分鐘閘門開啟後很快就會被下一輪巡檢確認，約 10~15 分鐘
對 Weekly 任務是否足夠足夠。一週才觸發 1 次，30 分鐘的確認延遲影響很小更即時，但對 Weekly 這種低頻任務其實過度密集
系統資源消耗低（每 30 分鐘才跑一次 GetRunTimes/GetHistory）較高（同樣邏輯跑更多次）
安全性要求LookbackMinutes(90) ≥ Tolerance(30) + Interval(30) = 60，有 30 分鐘餘裕（見第8節）相同公式，但因 Interval 變小，所需 Lookback 也可以跟著變小
結論：目前 Interval=30 / Tolerance=30 / Lookback=90 這組設定，配合「先查History、查無才看閘門」的判斷順序， 能穩定判斷 Weekly 任務的成功、失敗、漏排三種結果，且不受巡檢時機影響。若日後要監控類型 C（高頻重複型，如每5分鐘一次）的任務， 這組偏低頻的巡檢間隔可能就太粗，需要依任務類型分層設計巡檢頻率。

8模型修正：Lookback ≠ Interval，判斷改用「以 Trigger 為中心」

討論 ToleranceMinutes = 30、IntervalMinutes = 30 這組設定時發現的邊界問題，修正後的正確模型如下。

8.1　抓取範圍（Lookback）刻意大於巡檢間隔（Interval），製造重疊冗餘

設計用意：Lookback（90分鐘）故意比 Interval（30分鐘）長很多，讓相鄰兩次巡檢的視窗互相重疊達 60 分鐘。 即使某一次巡檢因程式重啟、機器忙碌而delay或整輪漏跑，甚至連續兩輪都delay，下一次巡檢的視窗仍然涵蓋得到，不會真的漏掉這個 Trigger。 同一筆 Trigger 會被多次視窗重複抓到，這是預期內的行為，交給 _alertedKeys 去重即可，不影響判斷正確性。

Step 1 － 時間閘門（何時可以下結論）： 現在時間 ≥ Trigger時間 + ToleranceMinutes 成立後，才代表已經到了「最晚容許時刻」，可以開始下結論； 如果現在時間還沒到這個界線，代表任務可能還在合理範圍內、還沒真正到期，不該急著判定漏排（此時應略過，等下一輪巡檢再看）。
Step 2 － 歷史查詢（結論是什麼）： 時間閘門通過後，才呼叫 GetHistory(taskPath, Trigger − Tolerance, Trigger + Tolerance)： 查到成功紀錄 → 結案；查到失敗紀錄 → 失敗告警；完全查無紀錄 → 漏排告警。
套用到 Interval = 30 分鐘、Tolerance = 30 分鐘的情境： 2:30 PM 觸發後，時間閘門要等到 3:00 PM（2:30+30分）才會打開；因此 3:00 PM 這次巡檢是第一個「有資格下結論」的巡檢點， 不會出現「還沒到期卻被誤判漏排」的狀況，也不會因為巡檢時機不同而算出不同的時間差 —— 這組 30/30 設定在這個修正後的模型下是可行且穩定的。

8.4　安全公式：Lookback 必須 ≥ Tolerance + Interval，而非只是 Lookback > Tolerance

為什麼要多加一個 Interval？ 因為巡檢不是連續發生的，而是每隔 Interval 分鐘才執行一次。 最差情況下，「閘門剛好打開（現在 ≥ Trigger + Tolerance）」的那一刻，會卡在兩次巡檢中間，要等到下一次巡檢才真正被檢查到 —— 這會再拖上將近一個 Interval 的時間。 所以要保證這筆 Trigger 在「閘門打開、可以下結論」的那次巡檢裡，仍然還落在 Lookback 視窗內，安全公式必須是： 
Lookback ≥ Tolerance + Interval

範例（本文情境）：Interval = 30 分鐘，Tolerance = 30 分鐘
　→ 需要 Lookback ≥ 60 分鐘（臨界值）
　→ 已採用 Lookback = 90 分鐘 → 高於臨界值 60 分鐘，多出 30 分鐘安全餘裕
臨界值的風險（若沿用 60 分鐘）：剛好等於臨界值時，任何微小的時間誤差（例如程式啟動延遲、系統時間漂移、巡檢本身執行耗時）都可能讓這筆 Trigger 在閘門打開前就先滑出視窗，導致永遠不會被下結論、直接消失在系統裡，是最危險的組態方式。改用 90 分鐘後，即使巡檢延遲、漂移，也還有 30 分鐘的緩衝空間可以吸收。

8.5　修正方向的取捨：拉長 Lookback vs 縮短 Interval

方向好處代價 / 風險
拉長 Lookback（已採用：90分鐘） 增加安全邊界，不需更動 Interval／Tolerance 這類會影響業務容錯行為的參數 同一筆 Trigger 會在更多輪巡檢中被重新撈到（候選次數變多），但只要有 resolved 去重機制，查到已處理過就直接跳過，不會造成重複告警，只是多一點點輕量的查表判斷
縮短 Interval 巡檢更頻繁，離散誤差變小，理論上可以用更小的 Lookback 系統資源消耗直接變高（GetRunTimes/GetHistory 呼叫次數變多）；若巡檢邏輯耗時較長，可能出現上一輪還沒跑完、下一輪就開始的重疊執行，需要額外加鎖處理
已採用設定：IntervalMinutes = 30、ToleranceMinutes = 30、LookbackMinutes = 90。 相較於臨界值 60 分鐘，多保留 30 分鐘餘裕，應付機器忙碌、程式延遲啟動等意外狀況；同時系統須確保做好「以 任務名稱 + Trigger時間 為 key」的 resolved 去重機制，這樣拉長 Lookback 不會產生任何重複告警的副作用。

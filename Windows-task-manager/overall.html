Windows Task Scheduler 排程監控設計 —— 三種類型與對應解法

本文件彙整 Weekly、Daily 單次、Daily+高頻重複（心跳型）、Multiple Triggers（多組獨立Trigger）四種 Trigger 類型的判斷模型與設計取捨， 是理解整體監控架構的入口文件。各類型的完整情境圖解請參閱對應的獨立 HTML 文件。

1問題背景

Windows Task Scheduler 的排程任務可能因為機器休眠、服務未啟動、資源不足等原因「該執行卻沒執行」（漏排）， 或「有執行但失敗」。我們要設計一個定期巡檢的 Monitor Worker Service，主動偵測這兩種異常並發出告警。

核心困難點在於：不同 Trigger 設定方式，代表的「該不該告警」的判斷邏輯完全不同， 不能用同一套邏輯套用在所有類型上。本文件把目前討論過的四種類型與各自對應的設計方案整理如下。

2四種類型一覽

類型 A

Weekly（每週執行）

例：每週二 2:00 PM 執行一次

模型：單次事件

一週只有 1 個理論觸發時間點，需注意跨週邊界的候選歸屬。

類型 B

Daily 單次

例：每天 3:00 AM 執行一次

模型：單次事件（同類型A）

每天都有新的理論觸發時間點，是最單純的情況，核心演算法完全不用調整。

類型 C

Daily + 高頻重複（心跳型）

例：2:01 PM 起每5分鐘重複，持續1天

模型：心跳（連續狀態）

Duration＝Recur間隔時無縫銜接，等於永久心跳，不是「某時刻該執行」的問題。

類型 D

Multiple Triggers（多組獨立Trigger）

例：10:10 AM / 4:10 PM / 10:10 PM 各自獨立Daily Trigger

模型：單次事件模型重複套用

逐一走訪每組Trigger各自判斷，去重key需帶入T，並留意Trigger間距過近的重疊風險。

3類型 A / B：單次事件模型

適用於「某個特定時刻理論上該執行一次」的排程

GetRunTimes 算出候選時間 T
→
GetHistory(T−Tolerance, T+Tolerance)
→
查到紀錄？
→
是：立刻結案
查無紀錄
→
時間閘門 now≥T+Tolerance？
→
是：判定漏排告警
→
否：略過，下輪再看
參數採用值意義
CheckIntervalMinutes30巡檢頻率
ToleranceMinutes30以 T 為中心的接受窗半徑
LookbackMinutes90每輪巡檢往前抓候選的範圍
安全公式：Lookback ≥ Tolerance + Interval（30+30=60，採用90留安全餘裕）， 確保「時間閘門打開」後，下一輪巡檢的 Lookback 視窗一定還能撈到這個候選 T，不會因為視窗滑過去而漏判。
關鍵設計：先查歷史紀錄，查到就結案（不用等閘門）；只有查無紀錄時，才需要時間閘門決定「現在能不能下結論說是漏排」—— 這避免了「延遲執行但最終成功」的任務被誤判。

詳細情境圖解：weekly-hourly-check-scenarios.html（類型A）、daily-single-check-scenarios.html（類型B）

4類型 C：心跳模型

適用於「理論上持續不間斷運作」的高頻重複排程

為何不能套用類型A/B的模型：
① 只檢查起始時間 → 起始成功後若中途整個停掉，後續 288 次都不跑也偵測不到
② 用固定視窗查詢（如「往前拉10分鐘查GetHistory」）→ 視窗大小與巡檢間隔沒對齊，兩次巡檢之間會出現查詢死角
gap = now − task.LastRunTime
→
gap ≤ GapThreshold？
→
是：心跳正常
gap ＞ GapThreshold
→
立即告警「心跳已停止」
→
不需等下一輪，也不需時間閘門
參數採用值意義
GapThresholdMinutes10（依任務心跳頻率個別調整）允許連續漏跳幾次心跳的容忍值
CheckIntervalMinutes30巡檢頻率（不影響判斷結果，只影響發現延遲）
核心優勢：LastRunTime 是連續遞增的狀態值，不是離散時間點， gap 超標的當下就是既定事實，不需要視窗查詢、不需要時間閘門等待、也不需要 resolved 去重機制 （每輪巡檢都是對同一個持續狀態的獨立評估）。

詳細情境圖解：daily-repeat-check-scenarios.html（類型C）

5類型 D：多組獨立 Trigger（單次事件模型的重複套用）

適用於一個 Task 掛載多組互相獨立的 Trigger，例如 10:10 AM / 4:10 PM / 10:10 PM 三組獨立 Daily Trigger

本質：類型 D 不是新模型，而是把類型 A/B 的單次事件模型，逐一套用在每一組獨立的 Trigger 上，各組候選時間 T 各自獨立判斷、互不影響。
逐一走訪 task.Definition.Triggers
→
每組各自算出候選 T
→
各自套用「查History→查無看閘門」演算法
設計要點說明
去重 Key必須是 (taskPath, T) 組合，不能只用 taskPath，否則一組判斷完會誤導其餘組別被跳過
常見Bug只取 triggers[^1]（最後一筆）會讓前面幾組完全沒被監控，且不會有任何錯誤訊息（沉默失效）
特有風險若兩組 Trigger 間距 < 2×Tolerance，各自的接受窗會重疊，可能把隔壁 Trigger 的執行紀錄誤判成自己的，導致真實漏排被誤判為正常
警示：間距過近時建議：① 設定階段檢查Trigger間距並示警、② 動態縮小Tolerance避免跨越到隔壁Trigger、③ 間距過近的任務改用其他監控策略（如心跳模式）或人工特別關注。

詳細情境圖解：multiple-triggers-check-scenarios.html（類型D）

6四種模型全面對照

單次事件模型（類型 A / B / D）

  • 判斷依據：離散候選時間點 T（類型D為多組T，各自獨立）
  • 需要 GetHistory 視窗查詢
  • 需要時間閘門等待（now≥T+Tolerance）
  • 需要 resolved 去重（類型D的去重key須含T，避免互相牽連）
  • 參數：Interval / Tolerance / Lookback

心跳模型（類型 C）

  • 判斷依據：連續數值 gap
  • 直接讀 LastRunTime 屬性，不需視窗查詢
  • 不需時間閘門，超標當下即結論
  • 不需去重，每輪都是獨立評估同一狀態
  • 參數：GapThreshold（依任務心跳頻率各自設定）

7總結：如何選擇判斷模型

判斷準則採用模型
Trigger 是否有明確的「理論上該執行的那一刻」（一天/一週固定時段）單次事件模型（類型A/B）
Trigger 的 Repetition Duration 是否等於 Recur 間隔（無縫銜接、本質是永久心跳）心跳模型（類型C）
是否只需監控「循環有沒有在跑」，不在乎個別重複實例的成敗心跳模型（類型C）
一個Task是否掛載多組互相獨立的Trigger單次事件模型逐組套用（類型D），並留意間距過近的重疊風險
共通前提：不論哪種模型，巡檢一開始都要先篩選 Enabled==true 的任務清單， Disabled 的任務不產生候選，自然不會被誤判漏排——這是所有類型共通的第一道篩選步驟。
整體結論：監控系統需要依 Trigger 的「本質」（單次事件 vs 持續心跳）分流採用不同判斷模型， 不能用同一套邏輯強行套用在所有排程類型上，否則容易出現誤判或偵測不到的死角。

Windows 排程任務失敗情境與 Log 對應關係分析

依據 OSMPlus（NineYi.OsmPlus.Batch.RunFlowById / EtlFlowControlService）原始碼與 Windows Task Scheduler Event Log 行為盤點 — 涵蓋所有失敗情境、是否產生 Log、Log 實際存放位置

1. 前提：兩種任務類型的差異

Windows Task Manager 網站上的「Log」按鈕，只有在任務被判定為 ETL Flow 任務（IsEtlTask() 判斷 Program/Arguments 是否包含 RunFlowById）時才會顯示。任務可分為兩大類：

任務類型執行方式是否可能有 OsmConsole Log備註
ETL Flow 任務 透過 NineYi.OsmPlus.Batch.RunFlowById.exe --flowid / --flowname 執行 可能有 視失敗發生的階段而定，詳見下方情境表
一般任務（PowerShell script、其他 .exe） 如 Monitor_CheckOrderShippingFee 等直接執行的排程 不會有 完全不會產生 E:\Files\OsmConsole\ 底下的資料夾結構，UI 也不會顯示 Log 按鈕（設計上正確排除）

2. Log 狀態圖例

● 有專屬 Log 該次執行有自己專屬的 service.* 檔案
● 僅有共用 Log 只會寫入當日所有任務共用的 ProgramException 檔案
● 完全沒有 Log 連共用 Log 都不會產生任何檔案紀錄

3. ETL Flow 任務執行流程與各階段失敗對應

以下依照 RunFlowById.exe → EtlFlowControlService.ExecuteFlowId/DoProcess 的實際執行順序，列出每一個可能失敗的關卡，以及該關卡失敗時的 Log 落點。

階段 0：工作排程器嘗試啟動 RunFlowById.exe 進程
帳號密碼錯誤、帳號被停用（0x80070533）、權限不足（缺少「以批次工作登入」權限）等 → Windows 產生 Event 101（Task Start Failed / Launch Failure），進程本身根本沒有被建立起來。
階段 1：進程已啟動，執行到 CreateFlowTask() 之前或本身失敗
例如資料庫連線失敗、ShopEtlFlowId 參數格式錯誤、insert 失敗等。此時 isExecuteFlow 仍為 false，例外會被 Program.cs 最外層 catch 攔截並呼叫 WriteProgramExceptionLog。
階段 2：CreateFlowTask() 成功，但找不到 TaskSlave 或 DoFlowValidation 失敗
flowServiceTasks.Any() == false 或流程設定驗證未通過。此時仍在 isExecuteFlow = true 這行**之前**，同樣落入共用 ProgramException log。
階段 3：isExecuteFlow = true 之後，CreateFlowService() 建構 Flow Service 物件本身失敗
例如反射建立類別失敗、StreamWriter 開啟 log 檔案失敗（磁碟權限/路徑問題）等，導致 flowflowService 仍為 null。此時例外會被最內層 catch 攔截，因為 flowflowService == null 所以完全不會呼叫 serviceConsole.WriteLine；例外重新拋出後回到 Program.cs，但因為 isExecuteFlow 已經是 true，連共用的 ProgramException log 都不會寫入。只會有 DB 的 TaskLog 表紀錄與 Slack 告警訊息。
階段 4：Flow Service 物件成功建構（service.* 檔案已建立並開始寫入）
從這一刻起，這次執行終於有了「屬於自己的」log 檔案（路徑中包含這次的 EtlFlowTaskId）。之後不論這個 Step 執行成功還是在 DoProcess() 過程中失敗，都會繼續寫入同一份已開啟的 log 檔案。
階段 5a：Step 執行成功
呼叫 ProcessFinished() 寫入 OutputChainData 後關閉 StreamWriter，Log 檔案完整保留。
階段 5b：Step 執行中拋出例外（業務邏輯錯誤、外部 API 失敗、SQL 錯誤等）
例外訊息、Exception Stack Trace 會被寫入這個已存在的 service.* 檔案中，且會同時更新 DB 狀態為 Error 並發送 Slack 告警。這是唯一「有詳細錯誤內容」的情境。
重點提醒：階段 3（Flow Service 建構失敗）是最容易被忽略的「靜默失敗」——它發生在 isExecuteFlow = true 之後，導致 Program.cs 判斷式誤以為「Flow 已經開始執行，錯誤會由 Flow 自己記錄」，但實際上這次連 log 檔案的 StreamWriter 都還沒建立成功，最終造成完全沒有任何檔案 Log 可查，只能從 DB 的 TaskLog 狀態與 Slack 告警歷史回溯原因。

4. 完整情境對照總表

# 失敗情境 發生階段 Windows Event Log 是否有 Log Log 實際位置 備註
1 帳號密碼錯誤 / 帳號停用 / 缺少「以批次工作登入」權限 進程啟動前（Task Scheduler 層級） Event 101 完全沒有 —（僅存在於 Windows 工作排程器 Event Log，ResultCode 欄位如 0x80070533） RunFlowById.exe 從未被執行，OsmConsole 完全沒有任何紀錄
2 一般任務找不到 PowerShell 腳本檔案 進程啟動後，Exit Code 與一般程式錯誤相同（皆為 0x1） Event 200/201 完全沒有（且無法單靠錯誤碼區分） — 已改用 WTM 主動 File.Exists() 檢查，於 UI 顯示警示區塊彌補
3 資料庫連線失敗 / CreateFlowTask() Insert 失敗 isExecuteFlow 尚為 false Event 200/201 共用 Log {LogRoot}\ProgramException\{yyyyMMdd}\service.* 當日所有任務共用同一份檔案，需自行比對是否為本次錯誤
4 找不到任何 TaskSlave（流程未設定執行步驟） isExecuteFlow 尚為 false Event 200/201 共用 Log {LogRoot}\ProgramException\{yyyyMMdd}\service.* 同上
5 DoFlowValidation 流程設定驗證失敗 isExecuteFlow 尚為 false Event 200/201 共用 Log {LogRoot}\ProgramException\{yyyyMMdd}\service.* 同上
6 CreateFlowService() 建構 Flow Service 物件本身失敗（反射建立失敗、StreamWriter 開啟失敗等） isExecuteFlow 已為 true，但 flowflowService 仍是 null Event 200/201 完全沒有 — （僅 DB TaskLog 表 + Slack 告警） 最容易被忽略的靜默失敗，連共用 ProgramException log 都不會寫，因為 Program.cs 判斷 isExecuteFlow==false 才寫共用 log，此時已是 true
7 Flow Step 執行中發生業務邏輯錯誤（SQL 錯誤、外部 API 失敗、資料格式錯誤等） Flow Service 物件已成功建構之後 Event 200/201 有專屬 Log {LogRoot}\{ShopId}\{yyyyMMdd}\{分類}\{FlowId}_{FlowName}_{ShopId}\{EtlFlowTaskId}\{StepName}\service.* 唯一能看到完整 Exception Stack Trace 的情境
8 Flow Step 正常執行成功（完成） Flow Service 物件已成功建構之後 Event 200/201 有專屬 Log {LogRoot}\{ShopId}\{yyyyMMdd}\{分類}\{FlowId}_{FlowName}_{ShopId}\{EtlFlowTaskId}\{StepName}\service.* 記錄執行過程與 OutputChainData 內容

5. 對 Windows Task Manager 網站的影響與建議

目前 UI 顯示「找不到 ETL Log 檔案」可能的真正原因

可能原因屬於上表情境是否可從 UI 改善
該任務本來就不是 ETL Flow 任務—✅ 目前已用 IsEtlTask() 正確排除，不顯示按鈕
Event 101 Launch Failure，進程未啟動情境 1✅ 已用 MissingScriptPath 概念的警示邏輯可延伸套用；此類先天無 log 可查，UI 應提示「此錯誤發生於排程啟動前，不會有 OsmConsole Log」
LogRootPath 設定值磁碟機代號錯誤（如先前 C: vs 實際 E:）環境設定問題，非 OSMPlus 邏輯✅ 已修正 appsettings.QA.json / appsettings.Production.json
檔名不是固定 service.log（可能為 .txt 或 {shopId}.log）檔名慣例不一致✅ 已改用萬用字元 service.* 搜尋；{shopId}.log 命名的特殊服務仍待擴充規則
失敗發生在情境 3 / 6（共用 log 或完全無 log）情境 3、6⚠️ 建議：UI 應明確告知「此次失敗發生於流程啟動階段，請查看當日共用 ProgramException Log」或「此次失敗未產生任何檔案 Log，請查看 Slack 告警紀錄」，而非單純顯示「找不到 ETL Log 檔案」造成誤解

建議後續優化方向

  • UI 找不到 log 檔案時，依據執行結果與時間點，區分顯示不同提示文字（而非統一顯示「找不到 ETL Log 檔案」），讓使用者知道是「先天不會有」還是「應該要有但抓錯位置」。
  • 當任務失敗且判定為 ETL 任務，但連 ProgramException 共用 log 都找不到符合時間點的內容時，可提示使用者改查 DB EtlFlowTaskLog 表或 Slack 告警歷史。
  • 持續驗證各環境（QA / Prod / HK / MY）的 LogRootPath 磁碟機代號是否與 OSMPlus 該環境的 AppSettings.*.config 一致，避免再次出現磁碟機代號設定錯誤。

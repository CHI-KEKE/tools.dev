一般 Task / ETL Flow 分類邏輯確認

對應截圖：aaa40_0.png（執行歷史頁面，切換至 ETL Flow Tab）

✅ 程式碼邏輯設計正確

頁面依 TaskType（general / etl）分流，下拉選單與合併歷史都只會取「同分類」的任務：

// HistoryModel.OnGet()
TaskType = taskType == "etl" ? "etl" : "general";

var allTasks = _taskSchedulerService.GetAllTasks().ToList();
TasksForDropdown = IsEtlMode
    ? allTasks.Where(t => _taskSchedulerService.IsEtlTask(t))
    : allTasks.Where(t => !_taskSchedulerService.IsEtlTask(t));

// 「全部任務」時，只彙整同分類前 5 個任務的歷史
foreach (var task in TasksForDropdown.Take(5))
    allHistory.AddRange(_taskSchedulerService.GetTaskHistory(task.Path));

IsEtlTask() 判斷方式：比對 TaskInfo.Program / Arguments 是否包含 appsettings.json 內 EtlConfig:RunFlowByIdProgram 設定的執行檔名稱 （預設 NineYi.OsmPlus.Batch.RunFlowById.exe，比對時會去除副檔名）。

⚠️
但截圖實際結果與邏輯不符： 畫面已切到 ETL Flow Tab（按鈕呈實心樣式、統計卡為藍色）， 但清單中卻混入明顯是一般任務的 \Chat\DispatchInActiveConversationNotification、 \Chat\DispatchUnreadNotification。

可能原因與驗證方式如下：

可能原因如何驗證
QA 站台版本 尚未部署到最新程式碼（比本機舊） 確認 QA 站台的部署時間 / 檔案版本，是否已包含最新的 History 分類邏輯（commit 8f02c65）
該 Chat 任務的 Program／Arguments 欄位 剛好包含 ETL 執行檔名稱字串，被誤判為 ETL 任務 到「任務管理」頁面查看該任務詳細資料，確認 Program 欄位是否意外含有 RunFlowById 字樣
💡
研判 第一個原因（版本落差） 可能性較高，建議先確認 QA 部署版本，再重新驗證畫面行為。

ETL Log 目前的抓取方式

對應截圖：aaa47.png（點擊「Log」按鈕展開的檔案清單）

觸發流程：點擊 Log 按鈕 → AJAX 呼叫 HistoryModel.OnGetEtlLogs → 呼叫 TaskSchedulerService.GetEtlLogFiles()：

  1. 僅在該筆執行「結果 = Failed」時，才額外搜尋 LogRootPath\ProgramException\{yyyyMMdd}\service.log（並標示警告：此 log 為當日共用， 不一定是本次失敗的真正原因）。
  2. 正常情況：掃描設定值 EtlConfig:LogRootPath （預設 D:\Files\OsmConsole\）底下 每一個 Shop 資料夾 當日的 service.log。
  3. 若能從任務 Arguments 解析出 --flowname 或 --flowid，會用來篩選資料夾； 若 Arguments 只是單純數字（無前綴關鍵字），則不篩選，搜尋當日「全部」Shop 的 log。
  4. 找不到符合檔案時，前端顯示：此日期（yyyyMMdd）找不到 ETL Log 檔案
🔑
關鍵原因：Log 檔名沒有帶執行時間戳記
每個 Shop、每天只有固定一個 service.log，並非依每次執行分開存檔。 若同一天同一個 Flow 執行了多次，後面的執行會直接覆蓋前面的 log 內容—— 只有「當天最後一次」執行留下的 log 檔還存在。

對照截圖時間軸，這個現象完全吻合：

18:36:36
最新一次執行
✅ 找得到 Log
18:26:36
較早一次執行
❌ 找不到（已被覆蓋）
18:16:36
更早一次執行
❌ 找不到（已被覆蓋）
⚠️
並非系統抓取邏輯有誤，而是 ETL 程式本身寫 log 的方式造成同一天歷史紀錄無法回溯。 若要保留每次執行的完整 log，需要請 ETL 程式那端改成 依執行時間（加上 timestamp） 命名 log 檔案；Task Manager 端目前只能讀取「當下實際存在」的檔案，無法還原已被覆蓋的內容。

Windows Task Scheduler 實際存在的 Trigger 樣態

從現有伺服器的排程清單截圖歸納出 4 種 Trigger 類型，並針對各類型設計對應的監控策略。

類型 C

類型 C
At 5:30 PM every day - After triggered, repeat every 10 minutes for a duration of 1 day

2四種 Trigger 類型 × 對應監控策略

W

類型 A：Weekly（每週特定星期幾）

At 2:30 PM every Tuesday of every week
  • 一週只觸發 1 次
  • LookbackHours 需涵蓋至少 7×24 小時，否則巡檢區間內可能抓不到任何一筆
  • 沿用「檢查每一筆應觸發時間」邏輯即可，無特殊處理
需調整回顧區間
D

類型 B：Daily 單次

At 3:00 AM every day
  • 一天只觸發 1 次
  • LookbackHours = 24 即可涵蓋
  • 目前程式邏輯已可正確處理
現有邏輯適用
R

類型 C：Daily + 高頻重複

At 2:01 PM every day, repeat every 5 min for 1 day
  • 一天可能觸發 近 288 次（每 5 分鐘一次）
  • GetRunTimes() 會把每次重複都展開回傳，逐一比對不切實際
  • 採用方案：只檢查該 Trigger 當天「第一次啟動時間」（例：2:01 PM），忽略後續重複實例
需特殊處理：忽略 Repetition
M

類型 D：Multiple Triggers（一任務多組獨立 Trigger）

10:10 AM / 4:10 PM / 10:10 PM（各自獨立 Daily Trigger）
  • 同一任務底下有多組各自獨立的 Trigger（非同一 Trigger 的重複）
  • 每一組都要各自被檢查，不能只取最後一筆
  • 對應前次討論修正：GetExpectedRunTimes 要回傳全部而非只取最後一筆
需特殊處理：逐一檢查

3類型 B 圖解：Daily 單次

情境：每天固定 3:00 AM 觸發一次，最簡單的樣態

昨天 00:00 ──────────────────────────────────────────────→ 今天 08:00（巡檢當下）
昨天 00:00
今天 08:00
✓
昨天 3:00 AM
唯一應觸發點
24 小時內只有 1 個應觸發時間點，直接比對即可
① GetRunTimes
task.GetRunTimes(昨天00:00, 今天08:00, 1000)
回傳：[ 昨天 03:00 ] —— 只有 1 筆理論應觸發時間
② GetHistory
GetHistory(taskPath, since: 昨天 02:45)
查 Event Log，找 02:45~03:15 附近是否有 EventID 200/201 紀錄，比對這筆是否真的執行成功
結論：這是最單純的情況，LookbackHours = 24 剛好涵蓋，目前程式邏輯（無論是否修正）都能正確處理，不需特殊調整。

4類型 A 圖解：Weekly（每週特定星期幾）

情境：At 2:30 PM every Tuesday of every week — 一週只觸發 1 次

本週一 ── 二 ── 三 ── 四 ── 五 ── 六 ── 日（今天，巡檢當下）
週一 00:00
今天（週日）
✓
週二 2:30 PM
本週唯一觸發點
① GetRunTimes
task.GetRunTimes(週一00:00, 今天08:00, 1000)
回傳：[ 週二 14:30 ] —— 但如果區間只設 24 小時（昨天~今天），會是 []（空清單），完全抓不到這筆！
② GetHistory
GetHistory(taskPath, since: 週二 14:15)
查 Event Log，找週二 14:15~14:45 附近是否有對應執行紀錄
關鍵問題：如果 LookbackHours 只設 24 小時，往前只能看到「昨天」， 根本抓不到「這週二」那筆應觸發時間 —— GetExpectedLastRunTime 會直接回傳 null， 導致這個任務完全不會被檢查到！
修正：回顧區間至少要設定 168 小時（7 天），才能確保每種週期的任務都落在檢查範圍內。

5類型 D 圖解：Multiple Triggers（一任務多組獨立 Trigger）

情境：NC-ExpenseOrderSlaveCheck 同時有 3 組獨立 Daily Trigger：10:10 AM / 4:10 PM / 10:10 PM

昨天 00:00 ──────────────────────────────────────────────→ 今天 08:00（巡檢當下）
昨天 00:00
今天 08:00
✕
昨天 10:10 AM
應觸發 #1
✕
昨天 4:10 PM
應觸發 #2
✓
昨天 10:10 PM
應觸發 #3（最後一筆）
若沿用「只取最後一筆」的舊邏輯，只有這一筆會被檢查
另外 2 筆完全不會被驗證，即使漏排也不會告警
① GetRunTimes
task.GetRunTimes(昨天00:00, 今天08:00, 1000)
實際回傳：[ 昨天10:10, 昨天16:10, 昨天22:10 ] —— API 本身有回傳全部 3 筆，是程式邏輯只取 [^1]（最後一筆）才漏掉前 2 筆
② GetHistory ×3
GetHistory(taskPath, since: 昨天00:00) 查一次，對 3 筆各自比對最接近的紀錄
同一次 GetHistory 查詢結果，拿來跟 10:10 / 16:10 / 22:10 這 3 個時間點分別比對，各自獨立判斷
修正：必須逐一走訪這個任務底下的每一組 Trigger（10:10 AM、4:10 PM、10:10 PM 各自是獨立 Trigger）， 分別計算各自的應觸發時間並各自比對執行歷史，而不是把整個 Task 的 GetRunTimes() 結果只取最後一筆。

6類型 C 圖解：高頻重複型只檢查「第一次啟動時間」

情境：2:01 PM 開始，之後每 5 分鐘重複一次，持續 1 天

當天 00:00 ──────────────────────────────────────────────→ 23:59
00:00
23:59
✓
2:01 PM
唯一檢查點
2:01 PM 起始時間 — 唯一納入漏排/失敗判斷的時間點
之後每 5 分鐘的重複實例 — 忽略，不逐一比對
① GetRunTimes
trigger（清空 Repetition 後）.GetRunTimes(當天00:00, 當天23:59)
若直接對整個 Task 呼叫 GetRunTimes，會展開回傳近 288 筆（每 5 分鐘一筆）； 改成先複製 Trigger 並清空 Repetition.Interval，才會只回傳 [ 14:01 ] 這一筆起始時間
② GetHistory
GetHistory(taskPath, since: 13:46)
只確認 14:01 附近「有沒有開始執行過」，不逐一比對後續 5 分鐘一次的重複實例
採用策略：忽略 Trigger 的 Repetition 設定展開出的重複實例，只用 Trigger 本身的 StartBoundary（起始時間規則，例如「每天 2:01 PM」）去計算應觸發時間並檢查。 這樣可以大幅降低誤判與效能負擔，同時抓到最關鍵的起點：「這個高頻任務今天到底有沒有開始跑」。

實作方向

// 對每一個 Trigger 各別處理，而非直接呼叫 Task.GetRunTimes()（會展開所有重複實例）
foreach (var trigger in task.Definition.Triggers)
{
    if (trigger.Repetition.Interval != TimeSpan.Zero)
    {
        // 高頻重複型：暫時複製一份、清空 Repetition，只計算「起始時間」本身
        var clone = trigger.Clone();
        clone.Repetition.Interval = TimeSpan.Zero;
        clone.Repetition.Duration = TimeSpan.Zero;
        // 用只含這個 trigger 的暫存 TaskDefinition 呼叫 GetRunTimes，取得起始時間清單
    }
    else
    {
        // 一般型（Daily 單次 / Weekly）：直接計算應觸發時間
    }
}

下一步：目前 SchedulerReader.GetExpectedLastRunTime() 是對整個 Task 呼叫 GetRunTimes()，這會把所有 Trigger（含重複實例）混在一起展開，無法區分「該檢查全部」或「只檢查起始點」。 需要改為逐一走訪 task.Definition.Triggers，依上表策略分別處理，再合併成最終的應檢查時間清單。

設定與模型（貫穿全流程）

MonitorOptions.cs MonitoredTask.cs (TaskMonitorPlan) appsettings.json
設計文件 vs 實際實作最大的差異：原本設計文件設想「逐一走訪每一組 Trigger，各自呼叫 GetRunTimes」，但實測 Microsoft.Win32.TaskScheduler 套件的 GetRunTimes 只存在於已註冊的 Task 物件上（整合該任務「全部」Trigger），無法針對單一 Trigger 單獨計算。因此實作改成「以整個任務為判斷單位」，詳見第 2 節。

2核心判斷邏輯：TaskMonitorPlan

SchedulerReader.GetMonitorPlan() 是整個系統的大腦，決定一個任務要走哪一套監控模型

Q：這個任務的 Definition.Triggers 中，是否「任一組」Trigger 有設定 Repetition.Interval > 0？
是 → 標記 IsHeartbeat = true（心跳型，對應類型 C）
直接讀取 task.LastRunTime / task.LastTaskResult，不展開候選時間。
否 → IsHeartbeat = false（單次事件型，涵蓋類型 A / B / D）
呼叫 task.GetRunTimes(windowStart, windowEnd, 1000)「一次」取得該任務全部 Trigger 合併後的候選執行時間清單 CandidateRunTimes。
已知簡化 / 限制：若一個任務「同時」混有心跳型 Trigger 與單次事件型 Trigger（例如一個 Trigger 每天 3AM 觸發、另一個 Trigger 每 5 分鐘重複執行），目前會整個任務被視為「心跳型」監控，單次事件 Trigger 的獨立判斷會被忽略。程式碼中已用 HasMixedTriggerTypes 欄位記錄並輸出 warning log 提示。實務建議：混合情境拆成兩個獨立任務較好維護。

TaskMonitorPlan 資料結構

public class TaskMonitorPlan
{
    public string TaskPath { get; set; }
    public bool IsHeartbeat { get; set; }              // true=心跳型(類型C), false=單次事件型(類型A/B/D)
    public List<DateTime> CandidateRunTimes { get; set; }  // 僅單次事件型使用
    public DateTime? LastRunTime { get; set; }          // 僅心跳型使用
    public int? LastTaskResult { get; set; }            // 僅心跳型使用
    public bool HasMixedTriggerTypes { get; set; }       // 混合類型警示旗標
}
順帶修正的既有 Bug：v1 版本原本用 runTimes[^1] 只取 GetRunTimes 回傳陣列的「最後一筆」，等於多 Trigger 任務只會監控最晚的一個時間點。新版直接保留完整清單交給 Worker 逐一比對，自然涵蓋類型 D（Multiple Triggers）不需要額外程式碼。

🫀 CheckHeartbeatTask（心跳型 / 類型C）

gap = now - plan.LastRunTime

  • gap > GapThresholdMinutes → 告警 HeartbeatStopped（心跳停止，可能整個排程卡死或已被手動停止）
  • LastTaskResult != 0 → 告警 Failed（有跑但執行結果失敗）
  • 兩者互不排斥，可能同時觸發

📅 CheckSingleEventTask（單次事件型 / 類型A/B/D）

逐一走訪 plan.CandidateRunTimes 中落在 Lookback 視窗內的每個 T

  • Key = (taskPath, T) 已 resolved → 略過（避免重複判斷）
  • 查 GetHistory(taskPath, T-tolerance, T+tolerance)：查到 → 依結果碼標記成功/失敗並 resolved
  • 查無 且 now < T + ToleranceMinutes（接受窗未關）→ 先略過，下一輪再查
  • 查無 且接受窗已關 → 告警 Missed（漏排）並標記 resolved

去重機制：兩個 HashSet 各司其職

集合Key 格式用途適用模型
_resolvedKeys {TaskPath}|{ExpectedRunTime:O} 標記某個候選時間「已有結論」（無論成功/失敗/漏排），避免視窗重疊時重複查詢與重複告警 僅單次事件型
_alertedKeys {TaskPath}|{AlertType}|{ExpectedRunTime:O} 真正發過的告警去重（含 AlertType），避免同一件事重複發送通知 兩種模型皆用
已改善（v1.1）：兩個集合已從 HashSet<string> 改為 Dictionary<string, DateTime>，Value 記錄「寫入時間」。每輪巡檢開始時會呼叫 CleanupExpiredKeys()，清掉超過 KeyRetentionHours（預設 48 小時）未更新的 Key，不再無限增長。詳見下方「清理機制」小節。

清理機制：Dictionary + TTL

解決「只增不減、長期佔用記憶體」的限制，並附帶解決心跳型任務長期停止只告警一次的問題

private readonly Dictionary<string, DateTime> _resolvedKeys = new();
private readonly Dictionary<string, DateTime> _alertedKeys = new();

private void CleanupExpiredKeys(DateTime now)
{
    var retention = TimeSpan.FromHours(_options.KeyRetentionHours);   // 預設 48 小時

    var expiredResolved = _resolvedKeys.Where(kv => now - kv.Value > retention)
                                        .Select(kv => kv.Key).ToList();
    foreach (var key in expiredResolved) _resolvedKeys.Remove(key);

    var expiredAlerted = _alertedKeys.Where(kv => now - kv.Value > retention)
                                      .Select(kv => kv.Key).ToList();
    foreach (var key in expiredAlerted) _alertedKeys.Remove(key);
}

在 RunOnce() 開頭、每一輪巡檢都會先呼叫一次 CleanupExpiredKeys(now)，確保集合大小長期維持在「近 48 小時內出現過的 Key」這個有限範圍，不會無限增長。

設計考量說明
為什麼是 48 小時，不是更短？ 遠大於 LookbackMinutes(90分鐘)對應的視窗，正常情況下不會提早清掉還有效的 Key；即使服務短暫離線後補跑巡檢，48 小時的緩衝也足夠涵蓋。
單次事件型（A/B/D）清理後有風險嗎？ 沒有風險。過期的 Key 對應的候選時間 T 早就在 48 小時前被 resolved（成功/失敗/漏排都已確定），清掉後不會被重新查詢，因為未來的 CandidateRunTimes 只會產生新的、未來的 T，不會重算過去的 T。
心跳型（C）清理後的附帶效果 意外的好處：若心跳長期卡死（LastRunTime 永遠不變），對應的 _alertedKeys 過期 Key 會被清掉 → 下一輪重新計算 gap（仍然超標）→ 重新 RaiseAlert → 等同每 48 小時「重新提醒一次仍在停止中」，不需要額外設計提醒排程，直接用清理機制順便達成。

為什麼需要 _resolvedKeys？具體時間軸範例

（以下範例聚焦「同一輪次內視窗重疊」的去重情境，與上方 48 小時 TTL 清理是兩個獨立但互補的機制）

情境：類型B任務「每天 3:00 AM 執行」，IntervalMinutes=30、ToleranceMinutes=30、LookbackMinutes=90。核心關鍵是 LookbackMinutes(90) > IntervalMinutes(30)，代表同一個候選時間 T 會連續出現在「好幾輪」巡檢的 CandidateRunTimes 清單裡，而不是只出現一次。

巡檢輪次Lookback 視窗T=03:00 在窗內？resolvedKeys 有這個 Key？實際動作
Round1 @02:30 [01:00, 02:30] ❌ 還沒到 — T=03:00 尚未落在視窗內，這輪根本看不到它
Round2 @03:00 [01:30, 03:00] ✅ 否 查歷史紀錄 [02:30,03:30]：查無（任務實際 03:05 才跑，此刻還沒發生）。接受窗未關（now=03:00 < 03:30）→ 略過，不標記 resolved，下一輪再查
Round3 @03:30 [02:00, 03:30] ✅ 否 查歷史紀錄：這次查到了（任務 03:05 執行成功）→ 無需告警，resolvedKeys.Add(key)
Round4 @04:00 [02:30, 04:00] ✅（仍在窗內！） 是 _resolvedKeys.Contains(key) 為 true → 直接 continue，完全不查 GetHistory
重點：因為 Lookback(90分鐘) 大於 Interval(30分鐘)，同一個 T=03:00 會連續出現在 Round2、Round3、Round4 三輪的候選清單裡（視窗會重疊）。如果沒有 _resolvedKeys，Round4 會對「早就已經查到成功紀錄」的同一個 T 再查一次 Event Log——結果不會變，純粹是白白浪費一次查詢。任務數量一多、Lookback 設得越大，這種重複查詢會被放大好幾倍。_resolvedKeys 就是讓「已經有結論的候選時間」在後續輪次直接跳過，不用再進 GetHistory。
對應的取捨（trade-off）：一旦某個 T 被標記為 Missed（漏排）並 resolved，之後就算這個任務「遲到很久才真的手動被跑起來」（例如接受窗已關閉後的 03:50 有人手動觸發執行），Worker 也不會再回頭去查、也不會更新這筆結論——因為 _resolvedKeys 已經把它視為蓋棺論定。這是刻意接受的行為：接受窗關閉代表「已經確定太晚了」，晚到的執行不影響漏排告警已經發出的事實，重點是及時通知，不是事後修正歷史紀錄。

常見疑問澄清

Q1：修復問題後，這個任務會不會「永遠」被當作 resolved，之後都不再監控？

不會。Key 的格式是 {TaskPath}|{ExpectedRunTime:O}，綁定的是「某一個特定的候選時間點 T」，不是整個任務。例如任務是「每天 3:00 AM」：

  • 今天 T=2026-07-09 03:00 被判定漏排 → resolved，key = MyTask|2026-07-09T03:00:00
  • 修復問題後，明天 T=2026-07-10 03:00 是完全不同的 key，_resolvedKeys 裡沒有這筆，所以明天照樣會被正常巡檢、正常判斷

「永遠 resolved」只發生在同一個特定時間點事件本身（不會再回頭更新這一筆的結論），不會擴散影響未來每一天的排程監控。

Q2：所有四種類型（A/B/C/D）都會用到 _resolvedKeys 嗎？

_resolvedKeys 只用於單次事件型（類型 A/B/D），心跳型（類型 C）完全不會用到它。原因是心跳型沒有離散的候選時間清單，每一輪都是對「當下這個持續狀態」重新計算一次 gap = now − LastRunTime，本質上是 idempotent（重複算、結果一樣），不存在「同一個事件被重複查詢」的問題，自然不需要去重。

Q3：心跳型（類型 C）沒有 _resolvedKeys，那它的告警會不會被無限重複發送？

不會，但要留意跟單次事件型不太一樣的行為。心跳型告警一樣會經過 _alertedKeys 去重，key 是 {TaskPath}|{AlertType}|{LastRunTime:O}，這裡的 LastRunTime 是任務目前記錄的最後執行時間，不是每輪的候選時間：

情境行為
心跳真的停了（LastRunTime 卡住不變）第一輪偵測到 HeartbeatStopped 後 key 固定不變 → 之後每輪都被 _alertedKeys 擋掉，只告警一次，不會每輪重複通知
心跳後來恢復了（LastRunTime 更新到新時間）key 隨之改變 → 若之後又停止，會用新 key 重新告警一次
已改善（v1.1）：這個限制已透過上方的 TTL 清理機制解決——若心跳持續停止超過 KeyRetentionHours（預設 48 小時），對應的 _alertedKeys Key 會被清除，下一輪重新計算 gap 仍超標即會重新觸發告警。等同「停止期間每隔 48 小時重新提醒一次」，不需要額外設計提醒排程，直接用清理機制順便達成。

_resolvedKeys 與 _alertedKeys 的記錄時機差異

兩個集合雖然都是「去重用的 Dictionary」，但「什麼情況下會記進去」完全不同，容易混淆：

集合任務正常成功執行時，會記錄嗎？任務失敗 / 漏排 / 心跳停止時，會記錄嗎？本質
_resolvedKeys ✅ 會記（matched.IsSuccess == true 時仍會 Add(key)，只是不觸發告警） ✅ 會記 只代表「這件事已經查過、有明確答案了」，跟是不是問題無關，重點是避免重複查詢 GetHistory
_alertedKeys ❌ 不會記（成功不會呼叫 RaiseAlert，自然沒有東西可去重） ✅ 只有異常情況（呼叫 RaiseAlert 時）才記 只代表「這個問題已經通知過了」，避免同一個異常被重複發送通知
白話理解：_resolvedKeys 回答的問題是「這個時間點我還要不要再查一次歷史紀錄？」（不管查到的是好消息還是壞消息，查過了就不用再查）；_alertedKeys 回答的問題是「這個壞消息我還要不要再通知一次？」（好消息從來不需要通知，所以它天生只在有問題時才會累積內容）。

4設定參數 MonitorOptions

五個參數對應到前面所有情境圖解中反覆出現的變數

參數預設值意義對應設計文件中的名稱
IntervalMinutes30巡檢週期，多久跑一次 Worker巡檢間隔
ToleranceMinutes30單次事件型任務的「接受窗」寬度，超過才判漏排接受窗 / Tolerance
LookbackMinutes90每輪往回看多久去撈候選時間與歷史紀錄，需 > Interval + Tolerance 避免死角Lookback 視窗
GapThresholdMinutes10心跳型任務的 gap 閾值，超過視為心跳停止Gap 閾值
KeyRetentionHours48去重快取（_resolvedKeys/_alertedKeys）的保留時間，超過未更新即清除，避免記憶體無限增長去重 Key TTL
"MonitorOptions": {
  "IntervalMinutes": 30,
  "ToleranceMinutes": 30,
  "LookbackMinutes": 90,
  "GapThresholdMinutes": 10,
  "KeyRetentionHours": 48
}
為何 LookbackMinutes(90) > IntervalMinutes(30) + ToleranceMinutes(30)=60？ 多留 30 分鐘緩衝，確保即使某一輪巡檢延遲執行，前一輪還沒關窗的候選時間依然會被涵蓋到，不會因為視窗切齊而漏查。

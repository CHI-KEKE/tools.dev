# 去重機制（Dedup）優化規劃

> 狀態：**已實作**（`WindowsTaskManager.Monitor` 專案，`MonitorOptions.cs` / `TaskMonitorWorker.cs`）。實作結果見文末「五、實作結果」。
> 緣起案例：`舊的有抓到新的沒抓到.md` 中 `Referrer_Promotion_Expire_SalePage_Close` 這個心跳型任務，因為 `LastRunTime` 持續卡在同一個時間點不動，導致同一個異常事故只在 05:55 收到過一次 Slack 告警，之後 48 小時內完全靜默，即使 09:55 巡檢時 gap 已經累積到 484 分鐘也沒有再提醒。

---

## 一、問題現況

`TaskMonitorWorker` 目前用兩個去重字典，但共用同一個全域設定 `MonitorOptions.KeyRetentionHours`（目前為 48 小時）：

| 字典 | 用途 | Key 組成 |
|---|---|---|
| `_resolvedKeys` | 單次事件型（Type A/B/D）避免同一個候選執行時間被重複下結論 | `{TaskPath}\|{ExpectedRunTime:O}` |
| `_alertedKeys` | 所有告警類型的「已發送過」去重，避免重複通知 | `{TaskPath}\|{AlertType}\|{ExpectedRunTime:O}` |

問題出在 `_alertedKeys` 用在**心跳型（Type C）**的 `HeartbeatStopped` / `Failed` 告警時：`ExpectedRunTime` 帶的是 `LastRunTime`。只要任務真的卡死不動，`LastRunTime` 永遠不變 → key 永遠不變 → 同一個事故只會提醒一次，最長要等 48 小時保留期限過期才會提醒下一次。這跟「單次事件型」的去重目的（避免 Lookback 視窗 overlap 重複告警）完全是兩回事，卻共用了同一套機制與設定值，導致副作用被放大。

---

## 二、兩個去重各自的正確定位

### 1. `_resolvedKeys`（單次事件型 overlap 防重）
- **目的**：避免同一個候選執行時間點，因為 Lookback 視窗（`LookbackMinutes`，目前 90 分鐘）與巡檢週期（`IntervalMinutes`，目前 30 分鐘）重疊，被連續好幾輪重複下結論、重複告警。
- **正確的保留時間依據**：只要超過 `LookbackMinutes`，該候選時間就再也不會出現在任何一輪的視窗裡了，**保留時間只需要「略大於 Lookback 視窗」即可**（例如 `LookbackMinutes + 一點緩衝`），跟 48 小時、跟巡檢週期都沒有必然關係。48 小時對這個用途是「過度保留」，沒有實際壞處但沒必要。

### 2. `_alertedKeys` 用在心跳型的持續性提醒
- **目的**：避免問題持續存在時，每次巡檢（每 30 分鐘）都重複發送一模一樣的「心跳已停止」訊息，變成洗版。
- **重要澄清**：這裡的保留時間**沒有技術上「正確」的數字**，跟巡檢週期、Lookback 視窗都無關，純粹是維運上「持續異常時，多久提醒一次」的取捨：
  - 若設得太短（例如等於巡檢週期 30 分鐘）→ 等同每輪都重新告警，等於沒有去重、變成洗版，跟當初設計目的相反。
  - 若設得太長（目前 48 小時）→ 會像這次案例一樣，長時間異常卻只提醒一次，容易被忽略。
- **結論**：應該獨立出一個「心跳持續異常的提醒間隔」設定，跟另外兩者脫鉤，由維運團隊依實際容忍度決定（例如每 1~2 小時提醒一次）。

## 三、規劃方向（待後續動工時實作）

1. **拆分保留時間設定**，不要再共用同一個 `KeyRetentionHours`：
   - `_resolvedKeys`（單次事件型 overlap 防重）→ 改用貼近 `LookbackMinutes` 的短保留時間（例如 `LookbackMinutes + Buffer`），不需要額外開放設定，用程式自動換算即可。
   - `_alertedKeys` 用在心跳型持續性提醒 → 新增獨立設定，例如 `HeartbeatAlertRepeatIntervalMinutes`（預設值待與維運團隊確認，候選為 60 / 120 / 240 分鐘）。

2. **心跳型 Key 產生邏輯需要一併檢視**：目前 Key 用 `LastRunTime` 當作 `ExpectedRunTime`，只要任務卡死 `LastRunTime` 不變，Key 就不會變。若改成獨立的提醒間隔設定，需要確認新的 dedup 判斷邏輯能否正確運作（例如改用「距離上次對這個 Key 發送告警的時間」而非「距離上次任務執行時間」來判斷是否該重新提醒），避免只是換了保留時間但邏輯仍然卡住。

3. **保持單次事件型的既有行為不變**：這次調整只針對心跳型的持續性提醒體驗，不應該影響單次事件型（Missed/Failed）目前的 overlap 防重邏輯與行為。

4. **（附帶建議，非本次去重規劃範圍，另案處理）**：`HeartbeatStopped` 告警內容目前沒有帶出 `LastTaskResult`/`ResultCode` 根因（例如 `0xE0434352`），建議一併補上，讓維運人員從 Slack 訊息就能直接看到失敗原因。

## 五、實作結果

### 1. `Options/MonitorOptions.cs` 新增兩個設定
```csharp
/// 單次事件型 Trigger 專用：_resolvedKeys 去重快取的保留時間（分鐘）。預設 120 分鐘。
public int ResolvedKeyRetentionMinutes { get; set; } = 120;

/// 心跳型 Trigger 專用：心跳持續異常時重複提醒的間隔（分鐘），與 KeyRetentionHours 脫鉤。預設 120 分鐘。
public int HeartbeatAlertRepeatIntervalMinutes { get; set; } = 120;
```
`KeyRetentionHours`（預設仍 48 小時）保留給 `_resolvedKeys`／`_alertedKeys` 單次事件型項目當作一般性安全網，語意上跟心跳型脫鉤。

### 2. `appsettings.json` 對應新增
```json
"ResolvedKeyRetentionMinutes": 120,
"HeartbeatAlertRepeatIntervalMinutes": 120,
```

### 3. `Workers/TaskMonitorWorker.cs` 邏輯調整
- `CleanupExpiredKeys`：`_resolvedKeys` 改用 `ResolvedKeyRetentionMinutes`（分鐘）清理；`_alertedKeys` 仍用 `KeyRetentionHours`（小時）當安全網。
- `RaiseAlert` 新增可選參數 `TimeSpan? repeatInterval`：
  - 傳入時（心跳型 `Failed`／`HeartbeatStopped`）：Key 改為 `{TaskPath}|{AlertType}`（不含 `ExpectedRunTime`），判斷「距離上次發送是否已超過 `repeatInterval`」，超過就重新發送——解決了「`LastRunTime` 卡死不動導致 Key 永遠不變、只告警一次」的問題。
  - 不傳入時（單次事件型 `Failed`/`Missed`）：維持原本行為（Key 含 `ExpectedRunTime`，同一筆候選時間只送一次）。
- `CheckHeartbeatTask` 呼叫 `RaiseAlert` 時，`Failed`（gap≤閾值但結果失敗）與 `HeartbeatStopped`（gap>閾值）兩處都帶入 `TimeSpan.FromMinutes(_options.HeartbeatAlertRepeatIntervalMinutes)`。
- 新增 `ClearHeartbeatAlertState(taskPath)`：在任務確認恢復正常的三個分支（心跳正常執行、心跳視窗外的安靜期、OSM Log 佐證仍正常）都會呼叫，清除該任務殘留的 `Failed`／`HeartbeatStopped` 提醒時間戳，確保「這次事故解決後，下次再發生新事故會立即重新提醒」，不會被上一次事故留下的時間戳誤擋。

### 4. 效果驗證
- `dotnet build` 通過（0 錯誤 0 警告）。
- 專案目前無既有單元測試可執行，僅以編譯成功驗證語法/型別正確；邏輯正確性已透過程式碼審閱確認（見上方調整說明）。

### 5. 行為對照（以本次案例 `Referrer_Promotion_Expire_SalePage_Close` 為例）
- **調整前**：05:55 告警一次後，即使 09:55 gap 已達 484 分鐘仍持續異常，也要等到 48 小時後才會再收到提醒。
- **調整後**：05:55 告警一次後，若任務持續未恢復，每隔 2 小時（`HeartbeatAlertRepeatIntervalMinutes=120`）會重新收到一次「心跳已停止」提醒，直到任務恢復正常為止；一旦恢復，提醒狀態立即清除，若之後又發生新的異常會馬上重新提醒。

WindowsTaskManager.Monitor · 排程監控機制

心跳型排程「只跳一次告警」問題
新舊 Monitor 去重機制比對

心跳型任務（Type C）長時間卡死時，舊機制因為去重 Key 綁死在不會變動的 LastRunTime， 導致告警只會在第一次觸發，之後最長要靜默 48 小時才會再提醒一次。 新機制針對心跳型任務獨立出「持續性提醒間隔」，讓異常持續多久，就每隔固定時間持續提醒，不再被長期忽略。

🔎 實際案例：\ETL_Service\Referrer_Promotion_Expire_SalePage_Close（任務 253）— 2026/07/24 卡死事件

1 問題總覽

維運觀察到：某心跳型排程實際上已經停止執行超過 8 小時，但 Slack 只在最一開始跳過一次告警，之後就完全安靜，導致問題被忽略。

1 次
舊機制：8 小時內只告警 1 次（05:55），09:55 gap 已達 484 分鐘仍未再告警
48 hr
舊去重 Key 保留時間 KeyRetentionHours，套用在所有告警類型，心跳型也共用
120 min
新機制：心跳型獨立參數 HeartbeatAlertRepeatIntervalMinutes，異常持續就每 2 小時重新提醒

2 根本原因：去重 Key 綁錯了會變動的欄位

舊機制不分任務類型，一律用同一組 _alertedKeys 做去重。心跳型任務的 ExpectedRunTime 帶的是 plan.LastRunTime；但任務一旦真的卡死，LastRunTime 就永遠停在同一個時間點不會前進 —— 這代表 Key 永遠相同，去重邏輯會把「持續中的同一事故」誤判成「已經處理過、不用再提醒」。

舊機制

Key 含固定不變的 LastRunTime

卡死任務的 LastRunTime 不會前進，Key 永遠一樣 → 保留期內永遠被去重擋下。

TaskPath+ AlertType+ ExpectedRunTime = LastRunTime（卡死後不變）
key = "\ETL_Service\Referrer_Promotion_Expire_SalePage_Close|HeartbeatStopped|2026-07-24T01:51:11" // 05:55、09:55、13:55... 全部算出同一組 key // → 48hr 內只有第一次會真的送出 Slack
  • 成因誤判：一開始以為是 Lookback 視窗 overlap，其實心跳型每輪只是「當下狀態快照比較」，本質上沒有 overlap 問題。
  • 真正原因：把「防洗版」去重邏輯，套用在「狀態持續惡化但 Key 不變」的心跳場景。
  • 後果：問題持續 8 小時、24 小時、甚至 47 小時，維運都收不到第二次提醒。
新機制

Key 拿掉 ExpectedRunTime，改用「距上次發送」判斷

心跳型改用獨立 Key（不含時間戳），配合「距上次發送是否已超過提醒間隔」重新決定要不要再送。

TaskPath+ AlertType
key = "\ETL_Service\Referrer_Promotion_Expire_SalePage_Close|HeartbeatStopped" if (now - lastSentAt >= HeartbeatAlertRepeatIntervalMinutes /*120分*/) { // 異常仍持續 → 重新發送提醒 } // 任務恢復正常 → ClearHeartbeatAlertState 立即清掉這個 key
  • 持續提醒：只要 gap 仍超過閾值，每隔 120 分鐘（可調）就會重新發送一次告警。
  • 恢復即清除：任務一旦恢復正常，狀態立刻清除，下次再異常會馬上重新提醒，不受殘留時間戳影響。
  • 參數脫鉤：HeartbeatAlertRepeatIntervalMinutes 與單次事件型的 KeyRetentionHours（48hr）完全分開，互不影響。

5 容易混淆的兩件事：「判定異常」跟「提醒間隔」是分開的

這兩個時間概念很容易被誤以為是同一個設定，實際上分屬兩套獨立機制、互不影響。 即使任務自身心跳頻率不同（例如每 3 小時才心跳一次），也只有「判定異常」的門檻會跟著自動換算， 「持續提醒」的節奏維持全域固定。

① 第一次判定異常

依據 GapThreshold（+ 30 分鐘巡檢週期），跟 120min 完全無關

每輪巡檢都算一次 gap = now - LastRunTime，只要 gap 超過該任務自身換算出的 GapThreshold，當輪就立刻判定異常並發送第一次告警。

GapThreshold = max(GapThresholdMinutes=10, RepetitionInterval × HeartbeatGapMultiplier=2.0) // 例：任務自身心跳頻率 3hr(180分) → GapThreshold = max(10, 180×2) = 360分鐘(6hr) // 巡檢週期 30 分鐘一輪 → 6hr 一到，最近一輪巡檢就會判定異常，立即發送第 1 次告警 // 這裡的「間隔」是巡檢週期抓到的時間點，不是 120min
② 第一次告警之後

每輪巡檢都重新檢查「是否恢復」+「是否已滿提醒間隔」

第二次起，每輪巡檢都會重新評估兩個條件，兩者共同決定要不要再發一次告警。

每輪巡檢時： 若 gap <= GapThreshold（已恢復) → ClearHeartbeatAlertState，不發告警 → 下次再異常視為「全新事故」，回到①重新判定 否則（尚未恢復)： 若 now - lastSentAt < 120分鐘（HeartbeatAlertRepeatIntervalMinutes) → 跳過本輪，安靜等待 若 now - lastSentAt >= 120分鐘 → 重新發送告警，更新 lastSentAt = now

💡 結論：「判定異常的門檻」（GapThreshold）會依任務自身心跳頻率自動換算（頻率越低，門檻越寬鬆）； 但「異常持續期間要多久提醒一次」（HeartbeatAlertRepeatIntervalMinutes）目前是全域固定值， 不會因為任務本身心跳頻率不同而跟著縮放。也就是說一個 3 小時心跳一次的任務，一旦真的壞掉判定異常後， 還是會用跟 10 分鐘心跳任務一樣的 120 分鐘節奏被重複提醒——這是刻意的設計取捨（事故發生後統一提醒節奏，避免被忽略）， 但若未來想要「提醒節奏也依任務頻率縮放」，目前尚未支援，需要額外調整。

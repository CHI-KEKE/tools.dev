## 案例釐清：253 - Referrer_Promotion_Expire_SalePage_Close（新版 Monitor 是否有抓到）

### 任務基本資訊
- 任務路徑：`\ETL_Service\Referrer_Promotion_Expire_SalePage_Close`
- Trigger：`At 11:11 AM every day - After triggered, repeat every 00:10:00 indefinitely`（每天 11:11 開始，之後每 10 分鐘重複一次，無限期）
- Action：`D:\Batch\EtlConsole\OSMPlusBatchRunFlowById\NineYi.OsmPlus.Batch.RunFlowById.exe --flowname Referrer_Promotion_Expire_SalePage_Close`
- 最後一次執行結果：`0xE0434352`（.NET 程式丟出未捕捉的例外 / CLR Exception）

### 結論：新版 Monitor 其實有抓到，只是容易被誤以為「沒抓到」

**1. 因為有 Repetition，這個任務會被新版 Monitor 分類為「心跳型（Type C）」**
只要任務底下任一組 Trigger 設定了 Repetition，整個任務就會用「心跳模型」判斷：比對 `gap = now − LastRunTime` 是否超過 `GapThreshold`。
`GapThreshold = max(GapThresholdMinutes下限10分鐘, RepetitionInterval(10分) × HeartbeatGapMultiplier(2.0)) = 20 分鐘`。

**2. 實際發生的事件時間軸**
- **01:51:12**：該次執行因呼叫 NMQ V3 API 收到 `503 Service Temporarily Unavailable`，丟出未捕捉例外，Task Scheduler 記錄 `LastTaskResult=0xE0434352`，`LastRunTime=2026-07-24 01:51:11`。
- **01:45 ~ 05:55**：同時間整台主機/排程服務疑似短暫停擺，大量其他任務（約 20~30 個）的 gap 也同時累積到 240~320 分鐘。
- **05:55:49**：Monitor 巡檢時偵測到本任務 gap 已達 244 分鐘（遠超過 20 分鐘閾值），**正確發出了 `HeartbeatStopped` 告警**並成功送到 Slack（見 `real-alert.txt`、`Monitor-5-55-log.txt` 第 466~473 行）：
  ```
  [05:55:49.526] [WRN] 心跳型任務 \ETL_Service\Referrer_Promotion_Expire_SalePage_Close 心跳已停止！距離最後一次執行已 244 分鐘（閾值 20 分鐘）。
  [05:55:49.526] [INF] 發送告警："HeartbeatStopped" | 任務 ...Referrer_Promotion_Expire_SalePage_Close（ETL Flow）| 預期時間 2026-07-24 01:51:11 | 詳情：心跳已停止，距離最後一次執行已 244 分鐘（閾值 20 分鐘）
  ```
- **09:55:38**：這輪巡檢時，機器上絕大多數任務（如 `ETL_UpdateMemberCenterFirstAndRepurchase`、`OMO_Loyalty_ETL_LoyaltyPointMigration_RoutinePerMin`）都已恢復正常心跳（gap 只有 1~6 分鐘），**唯獨這個任務的 `LastRunTime` 仍然停在 01:51:11 沒有前進**，gap 已累積到 484 分鐘：
  ```
  [09:55:38.875] [WRN] 心跳型任務 \ETL_Service\Referrer_Promotion_Expire_SalePage_Close 心跳已停止！距離最後一次執行已 484 分鐘（閾值 20 分鐘）。
  ```
  但這輪**沒有**再送出 Slack 通知。

**3. 為什麼 09:55 沒有再收到 Slack 通知？—— 這是設計上的告警去重（dedup），不是漏報**
Monitor 內部用一個字典 `_alertedKeys` 記錄「已經發送過的告警」，Key 組成為：
```
{TaskPath}|{AlertType}|{ExpectedRunTime}
```
對於心跳型的 `HeartbeatStopped` 告警，`ExpectedRunTime` 帶的是 `LastRunTime`。因為這個任務的 `LastRunTime` 從 01:51:11 之後就再也沒有更新過（真的卡住了），所以之後每一輪算出來的 key 都跟 05:55 那次完全相同，會被以下邏輯擋下來，不會重複發送：
```csharp
if (_alertedKeys.ContainsKey(key))
{
    //// 已經告警過，且尚未過期，不重複發送。
    return;
}
```
這個去重 Key 的保留期限是 `MonitorOptions.KeyRetentionHours`（目前設定 **48 小時**），也就是同一個「心跳停止事件」在 48 小時內只會被提醒一次；除非任務恢復又再次停止（`LastRunTime` 改變產生新的 key），或是超過 48 小時保留期限過期後才會重新提醒一次。

**4. 目前判斷（非 Monitor 程式問題，是真實的營運事故）**
- 01:45~05:55 那段機器停擺是暫時性的，多數任務已自行恢復。
- 但 `Referrer_Promotion_Expire_SalePage_Close` 從 01:51 那次失敗後就完全沒有再被 Task Scheduler 觸發過，很可能是該次未捕捉例外導致處理程序沒有真正乾淨結束（背景執行緒或 Job Object 沒釋放），配合 Task 的「多執行個體原則」若為預設的**「不啟動新的執行個體」**，會讓 Task Scheduler 誤判前一個還在執行，因而永久跳過後續所有的 10 分鐘重複觸發。
- **需要人工介入**：到主機上確認是否有卡住的 `NineYi.OsmPlus.Batch.RunFlowById.exe` 殘留 process，砍掉後觀察該任務是否恢復自動觸發。

**5. 額外的告警內容改善建議（尚未實作）**
目前 `HeartbeatStopped` 告警內容只會顯示「距離最後一次執行已 N 分鐘」，並未帶出真正的失敗原因（`LastTaskResult=0xE0434352`）。建議未來把 `ResultCodeFormatter.Format(plan.LastTaskResult)` 一併寫入告警 Detail，讓維運人員從 Slack 訊息就能直接看到根因，不用再回頭查歷史紀錄或 Log。

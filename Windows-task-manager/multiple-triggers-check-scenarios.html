類型 D · Multiple Triggers（一任務多組獨立 Trigger）

「每 30 分鐘巡檢一次」下，單一任務掛載多組獨立 Trigger 的情境

範例：同一個 Task 掛載 3 組獨立的 Daily Trigger —— 10:10 AM / 4:10 PM / 10:10 PM。 每一組 Trigger 都是各自獨立的「單次事件」，套用與類型 A/B 完全相同的判斷模型 IntervalMinutes=30 / ToleranceMinutes=30 / LookbackMinutes=90， 但需要逐一走訪所有 Trigger、並用 (taskPath, T) 作為去重 key，避免互相干擾。

1基本設定回顧 —— 為什麼要逐一走訪每組 Trigger

項目說明
Task 結構一個 Task.Definition.Triggers 集合裡包含 3 個獨立的 DailyTrigger 物件，各自有自己的 StartBoundary
常見誤區（已知Bug）若程式只取 triggers[^1]（最後一筆）或直接對整個 Task 呼叫一次 GetRunTimes 並誤以為只有一個結果，會導致前面幾組 Trigger 完全沒被監控
正確做法逐一走訪 task.Definition.Triggers，對每一組 Trigger 各自呼叫 GetRunTimes 取得候選時間 T，並各自獨立套用類型A/B相同的判斷流程
去重 key必須是 (taskPath, T) 的組合，不能只用 taskPath——否則 10:10 AM 那組一旦被標記 resolved，會誤導系統以為整個任務今天已經檢查完畢，連帶跳過 4:10 PM、10:10 PM 那兩組
// 正確：逐一走訪每一組 Trigger，各自獨立判斷
foreach (var trigger in task.Definition.Triggers)
{
    var candidateTimes = GetRunTimesForSingleTrigger(trigger, now.AddMinutes(-90), now);
    foreach (var T in candidateTimes)
    {
        var key = (taskPath, T);            // 去重 key 帶入 T，而非只用 taskPath
        if (IsResolved(key)) continue;

        var history = GetHistory(taskPath, T.AddMinutes(-30), T.AddMinutes(30));
        if (history.HasRecord)
        {
            Resolve(key, history.Result);   // 查到紀錄，立刻結案
        }
        else if (now >= T.AddMinutes(30))   // 時間閘門
        {
            RaiseAlert(taskPath, T, "漏排");
            Resolve(key);
        }
        // 否則略過，下一輪再看
    }
}

// ❌ 錯誤示範（專案內已知Bug）：只取最後一筆
var lastTrigger = task.Definition.Triggers[^1];   // 只處理 10:10 PM，前兩組完全沒被監控

後果：即使 10:10 AM 與 4:10 PM 兩組都真實發生漏排，因為程式邏輯只走訪最後一筆 Trigger， 系統永遠不會對這兩組產生候選 T，自然也不會發出任何告警 —— 監控形同虛設但不會有任何錯誤訊息，是最危險的一種 Bug（沉默失效）。
對應到專案程式碼：此為 SchedulerReader.cs 目前 runTimes[^1] 的已知 Bug，修正方式即為情境1採用的「逐一走訪所有 Triggers」寫法。

5情境 4：⚠ 警示案例 —— 多組 Trigger 間距過近，接受窗重疊誤判

假設另一個任務的 3 組 Trigger 設定為 10:00 AM / 10:20 AM / 4:00 PM——前兩組只間隔 20 分鐘，小於 2×Tolerance(30分)=60分鐘，導致接受窗重疊。

危險情境推演：假設 T①(10:00) 因故漏排（完全沒觸發），但 T②(10:20) 準時執行成功。

查詢對象查詢區間查到的紀錄可能誤判
T①=10:00 的 GetHistory[9:30, 10:30]查到 10:20 那筆成功紀錄（屬於T②）⚠ 誤判T①「有執行」，實際上T①漏排未被發現
T②=10:20 的 GetHistory[9:50, 10:50]查到 10:20 那筆成功紀錄✅ 正確結案
根本問題：GetHistory(taskPath, T−30, T+30) 只用 taskPath 篩選，不會區分「這筆執行紀錄到底對應哪一組 Trigger」。 當兩組 Trigger 的接受窗重疊時，屬於 T② 的執行紀錄可能被誤認成 T① 的執行結果，導致 T① 真實漏排卻被誤判為「有執行」而不告警。
設計建議：
① 設計階段先檢查任務的所有 Trigger 間距，若任兩組間距 < 2×Tolerance，應發出設定警示或提高該任務的告警靈敏度
② 或將 Tolerance 依 Trigger 間距動態縮小（例如取 min(標準Tolerance, 相鄰Trigger間距/2)），避免接受窗互相跨越到隔壁 Trigger 的執行時間
③ 最保守作法：若間距過近，直接告知維運人員此任務不適合逐 Trigger 監控，建議改為心跳模式（類型C）或人工特別關注

6小結：類型 D 的設計要點總覽

面向類型 D（Multiple Triggers）類型 A/B（單一Trigger）
候選計算方式逐一走訪 task.Definition.Triggers，每組各自呼叫 GetRunTimes對唯一的 Trigger 呼叫一次即可
去重 Key必須包含 T：(taskPath, T)同樣是 (taskPath, T)，但因只有一組候選較不容易踩坑
核心演算法相同 —— 查History優先，查無才看時間閘門
Interval/Tolerance/Lookback相同：30 / 30 / 90 分鐘
特有風險① 只取最後一筆Trigger的實作Bug（沉默失效）
② 多組Trigger間距過近時接受窗重疊誤判		無此類問題
結論：類型 D 本質上不是新模型，而是類型A/B的單次事件模型「重複套用在多組獨立Trigger上」。 只要做到：① 完整走訪所有 Trigger（不遺漏）、② 去重key帶入T（不互相牽連），核心演算法完全不需改動。 唯一需要額外設計防護的是「Trigger間距過近」的邊界情況，建議在任務設定階段就先檢查間距，必要時提高警覺或改用其他監控策略。

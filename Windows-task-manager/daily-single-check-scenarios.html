類型 B · Daily 單次 Trigger

「每 30 分鐘巡檢一次」下，Daily 單次任務的各種情境

Trigger 範例：At 3:00 AM every day，一天只觸發 1 次。採用與 Weekly 類型相同的設定： IntervalMinutes = 30、ToleranceMinutes = 30、LookbackMinutes = 90， 判斷邏輯同樣是「以 Trigger 時間為中心的接受窗」+「時間閘門」模型。逐一檢視：正常結案、漏排告警、延遲但成功、 跨日邊界、多個 Daily 任務併存等情境。

1基本設定回顧 —— Daily 單次為何比 Weekly 更單純

參數設定值對 Daily 單次的意義
IntervalMinutes30每 30 分鐘巡檢一次
ToleranceMinutes30Trigger 前後 30 分鐘算合理範圍；閘門 = Trigger + 30分
LookbackMinutes90每次巡檢用 GetRunTimes(now-90分, now) 抓候選。因為 Daily 每天都會產生 1 筆新的候選時間點，90 分鐘視窗完全足夠涵蓋，不需要像 Weekly 一樣擔心「一週才 1 筆、視窗要拉更長」的問題
與 Weekly 類型的關鍵差異：Weekly Trigger 一週只產生 1 筆候選時間點，跨週邊界時容易漏抓； Daily Trigger 每天都會產生 1 筆新的候選，只要 Lookback（90分鐘）≥ 安全公式門檻（60分鐘）， 同一套「查History → 查無才看閘門」的演算法完全不需要修改就能直接套用，是所有 Trigger 類型中最單純的一種。 
for T in GetRunTimes(taskPath, now - 90分, now):
    if (task, T) 已經 resolved: continue

    history = GetHistory(taskPath, T - 30分, T + 30分)

    if history 有找到成功或失敗紀錄:
        下結論（成功 → 結案 / 失敗 → 告警）並標記 resolved
    else if now >= T + 30分:
        判定「漏排」，發出告警，並標記 resolved
    else:
        continue   // 閘門未開，略過，下一輪再看

結論：3:00 巡檢當下，成功紀錄可能還沒寫入（任務剛開始跑），查不到；3:30 巡檢再查一次就能查到成功紀錄，立刻結案。 跟 Weekly 情境唯一的差別是：Daily 每天都會重複發生一次這個流程，不需要跨週等待。

判斷邏輯：3:00 巡檢時，GetRunTimes(taskPath, 1:30,3:00) 抓到候選 T=3:00；GetHistory(taskPath, 2:30,3:30) 查無紀錄； 閘門 now(3:00) ≥ T+Tolerance(3:30) 不成立 → 略過。 到了 3:30 巡檢，同一筆 T=3:00 再次被抓到；GetHistory 仍查無紀錄；這次閘門 3:30 ≥ 3:30 成立 → 判定漏排、發出告警，並標記 resolved。
去重機制：下一次 4:00 巡檢時，即使 Lookback 視窗仍涵蓋 3:00 這筆，因為已標記 resolved 會直接跳過；直到隔天 3:00 AM 才會產生新的 key，不會每天累積重複告警。

容易誤判的地方：如果程式邏輯用「日曆日」切割（例如固定抓「今天 00:00 到現在」），在午夜前後容易出現「這筆算今天還是昨天」的判斷混亂，尤其當任務是「每天凌晨剛過午夜」這種貼近日界線的時間點時特別容易出錯。
正確做法：同樣用以現在時間為終點、往前推 90 分鐘的滑動窄視窗 —— GetRunTimes(taskPath, now-90分, now)，完全不依賴日曆日切割。 不管巡檢當下是 23:30、00:00 還是 00:30，只要視窗連續銜接，00:20 這筆必然會落在某一次巡檢視窗內，不會因為跨過午夜而漏抓或重複抓。

8小結：Daily 單次 vs Weekly 的差異對照

面向Daily 單次（本文）Weekly
候選產生頻率每天 1 筆，天天都有新的候選需要判斷每週只有 1 筆，跨週邊界要特別小心視窗銜接
Lookback 是否需要特別放大不需要，90分鐘（滿足安全公式）即可穩定涵蓋同樣是90分鐘即可，因為採用滑動窄視窗而非「回顧一整週」的舊模型
漏排確認延遲約 30 分鐘（閘門開啟後下一輪即確認）約 30 分鐘（機制相同）
核心演算法完全相同 —— 查History優先，查無才看時間閘門，成功結案/失敗告警/漏排告警三選一
額外要注意事項需先排除 Enabled=false 的任務（情境6）需注意跨週邊界的視窗銜接（情境4）
結論：Daily 單次是所有 Trigger 類型中最單純的一種 —— 因為每天穩定產生 1 筆候選，不需要為了「等很久才出現1筆」而特別放大 Lookback， 也不會有 Weekly 那種「一週一次、視窗銜接特別敏感」的問題。核心演算法（查History → 查無才看閘門）完全不需要為 Daily 類型做任何調整， 直接沿用同一套邏輯即可正確處理成功、失敗、漏排三種結果。

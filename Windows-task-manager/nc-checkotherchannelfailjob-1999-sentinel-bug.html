心跳型排程「假心跳停止」誤報事件
NC-CheckOtherChannelFailJob（1999-11-30 Sentinel Bug）

一支昨天早上才新掛上去、實際上還一次都沒執行過的排程，被 Monitor 判定為「心跳已停止 14,024,745 分鐘（約 26.7 年）」而發出告警。 根因是 Windows Task Scheduler 底層 API 對「從未執行過」的任務，回傳的並非預期的空值，而是一個歷史悠久的特殊 sentinel 日期。

2 第一個線索：「預計執行時間 1999-11-30」不是巧合

這支任務是「昨天早上新掛的排程」，照理說「上次執行時間」應該是 null／從未執行，但告警卻算出一個具體、極舊的日期， 而且 1999-11-30 這組數字在後端排程監控圈裡其實是個「熟面孔」。

🔍 查證結果
本專案使用的 Microsoft.Win32.TaskScheduler（NuGet 套件，封裝 Windows Task Scheduler COM API）有一個已知行為： 當任務「從未執行過」時，Task.LastRunTime 並不會回傳 DateTime.MinValue， 而是回傳 Task Scheduler 底層 API 的特殊 sentinel 值 1999-11-30 00:00:00。 這個行為在套件官方 GitHub 已有 issue 記錄（dahall/TaskScheduler #779）。
🧮 驗算：2026-07-30 − 1999-11-30 ≈ 26.67 年 ≈ 14,024,745 分鐘 —— 跟告警訊息裡的數字完全吻合， 證實這支排程根本不是「心跳停止」，而是「還沒有第一次執行紀錄」被誤判。

3 根因鏈：程式碼裡漏接的一種 sentinel 值

程式碼位置：WindowsTaskManager.Monitor/Services/SchedulerReader.cs

🆕

Step 1 — 排程新掛上去，還沒觸發過第一次執行

任務底下設有 Repetition Trigger（每小時重複），被 Monitor 判定為心跳型（Type C），但因為剛建立，Task.LastRunTime 屬於「從未執行」狀態。

🧬

Step 2 — Task Scheduler API 回傳非預期的 sentinel 日期

底層 API 沒有回傳 DateTime.MinValue 或 null，而是回傳歷史悠久的怪異值 1999-11-30 00:00:00，這是 COM API 對「從未執行」狀態的內部表示方式，並非本專案自訂邏輯的產物。

🕳️

Step 3 — 程式碼的「從未執行」判斷只接住了 default，沒接住這個 sentinel

原本的防呆判斷是 task.LastRunTime == default ? null : task.LastRunTime，這裡的 default 是 C# 的 DateTime.MinValue（0001-01-01），跟 Task Scheduler 實際回傳的 1999-11-30 是兩個不同的值 —— 判斷完全沒接住，1999-11-30 被當成「真實的最後執行時間」往下傳遞。

💥

Step 4 — 心跳判斷邏輯用這個假時間算出巨大 gap，誤判為異常

CheckHeartbeatTask 用 gap = now − LastRunTime 判斷是否心跳停止，這裡的 LastRunTime 已經被污染成 1999-11-30，算出 gap ≈ 14,024,745 分鐘，遠超過閾值 120 分鐘，於是判定「心跳已停止」並發送告警 —— 但實際上任務只是「還沒開始」，不是「壞了」。

✅

Step 5 — 修正：新增 sentinel 正規化，兩種「從未執行」值都視為 null

新增 NormalizeLastRunTime() 輔助方法，同時檢查 default 與 1999-11-30 兩種 sentinel，套用到心跳型與單次事件型兩處計算 LastRunTime 的地方。修正後，剛新掛的排程會正確落入既有的 plan.LastRunTime == null 分支，判定為「尚無資料，本輪不判斷」，不再誤報。

4 修正前後程式碼對照

兩處計算 LastRunTime 的地方都套用同一個正規化方法，避免同樣的問題在單次事件型任務上也發生。

SchedulerReader.cs — 新增輔助方法
+ private static DateTime? NormalizeLastRunTime(DateTime value)
+ {
+ var neverRunSentinel = new DateTime(1999, 11, 30);
+ return value == default || value == neverRunSentinel ? (DateTime?)null : value;
+ }
SchedulerReader.cs — 心跳型任務（GetMonitorPlan）
- var lastRunTime = task.LastRunTime == default ? (DateTime?)null : task.LastRunTime;
+ var lastRunTime = NormalizeLastRunTime(task.LastRunTime);
SchedulerReader.cs — 單次事件型任務（GetMonitorPlan）
- var lastRunTimeForSingleEvent = task.LastRunTime == default ? (DateTime?)null : task.LastRunTime;
+ var lastRunTimeForSingleEvent = NormalizeLastRunTime(task.LastRunTime);

5 與先前「48hr 去重」問題的區別

兩起事件都是心跳型任務的誤報，容易被誤以為是同一個問題，實際上根因完全不同、修法也不同。

先前事件：Referrer_Promotion_Expire_SalePage_Close

問題類型：長期異常只告警一次

任務真的卡死了，但去重 Key 綁死在不變的 LastRunTime，導致 48hr 內只提醒一次。

  • 觸發前提：任務曾經正常執行過，之後才卡住
  • 問題本質：告警去重機制設計缺陷
  • 修法：獨立提醒間隔 HeartbeatAlertRepeatIntervalMinutes + Key 拿掉時間戳
本次事件：NC-CheckOtherChannelFailJob

問題類型：從未執行過就被判定異常

任務根本還沒執行過第一次，Task Scheduler API 回傳的 sentinel 值沒被正確辨識，直接誤判為「心跳停止 26.7 年」。

  • 觸發前提：任務剛建立，一次都還沒執行過
  • 問題本質：「從未執行」的判斷邏輯不完整（漏接一種 sentinel 值）
  • 修法：NormalizeLastRunTime() 同時識別 default 與 1999-11-30

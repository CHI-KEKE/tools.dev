Architecture Field Notes · nine1.regularpurchase.v2

FluentValidation 獨立驗證專案的誕生

從一段 if-else，到跨專案的驗證邊界——一次架構決策的思考軌跡

案例：新增定期購方案（含贈品活動）API · 2026

這不是一份「FluentValidation 怎麼用」的教學，而是一份決策紀錄： 為什麼從最初的手寫 if (rule.Type != "GIFT")， 一路演化成獨立的 Common.Validators 專案？ 每一步的判斷依據是什麼？哪些是刻意留白、之後才做的？

整個過程沒有一步是「憑感覺換技術」——每個轉折點都對應一個具體徵兆， 或是一次現況盤點（grep 公司既有專案慣例）。這份筆記把思考過程攤開， 方便日後遇到類似情境時，重新檢視同一套判斷邏輯是否還成立。

Chronology

六個轉折點

從魔術字串到 Enum，從手寫方法到 Interface，再到 FluentValidation 與獨立專案

起點手寫 if-else 的具體徵兆

最初的贈品活動規則驗證，就是一段線性增長的 if-else：

RegularProductService.cs（重構前）
if (rule.Type != "GIFT")
    return "不支援的活動類型";

if (rule.TriggerMode != "INTERVAL")
    return "不支援的觸發模式";
// ... 一路寫下去

判斷「不好維護」不是憑直覺，而是列出可觀察的具體徵兆：

  • 職責混雜：型別檢查、範圍檢查、跨欄位邏輯全擠在同一個方法
  • 錯誤訊息硬編碼：字串散落各處，難以統一管理與 i18n
  • 規則不可重用：Add / Edit 兩支 API 未來都要驗證同一組規則
  • 只回傳第一個錯誤：前端無法一次拿到所有欄位錯誤
  • 魔術字串："GIFT"／"INTERVAL" 全大寫比對，無編譯期檢查

先做的小手術：把字串抽成 RegularProductPromotionTypeEnum／ TriggerModeEnum，值改 PascalCase；且只定義目前真的用到的值 （如 Sequence 雖有文件規劃但未實作，就先不寫進 enum）， 避免出現「定義了卻沒邏輯」的假選項。

過渡先抽 Interface，不急著上 FluentValidation

在還沒決定要不要導入 FluentValidation 前，先做一個低成本、可逆的過渡：

IRegularProductPromotionRuleValidator.cs
public interface IRegularProductPromotionRuleValidator
{
    string? Validate(List<RegularProductPromotionRule> rules, int shipLimitCount, int shippingSet);
}
為什麼先抽 Interface 專案完全沒用過 FluentValidation，貿然導入等於同時做「重構」+「導入新技術」， 風險會疊加。抽 Interface 本質是最基本的 Extract Class 重構，不改變邏輯，風險趨近於零。
留白的意義 這個 Interface 邊界剛好是「手寫版」與「未來 FluentValidation 版」唯二的替換點—— Service 完全不用改。這是一次刻意留給自己反悔空間的「便宜可逆決策」。

轉折「乾脆用 FluentValidation 就好」

看到親手抽出的 Interface 後，反問自己：這樣做是不是等於在山寨一個現成的函式庫？

觀察判斷
手寫 Interface 長什麼樣 IValidator、ValidationResult、 規則組合能力——FluentValidation 全部都有現成、久經考驗的實作
未來需求方向 驗證規則要能被組合、被多個 Request 共用，正是 FluentValidation 的核心設計目的
手寫要做到「收集所有錯誤」「跨欄位」「條件式驗證」 都得自己刻；FluentValidation 用 RuleFor／When／ SetValidator 宣告式表達即可
換的時機 現在專案還小、只有一個 Validator、一個消費者，換掉的代價最低
結論：不是「要不要用 FluentValidation」的技術偏好，而是「手寫的東西已經摸到它想解決的問題邊界」，繼續手刻等於重造輪子。

設計驗證整個 Request，而非只驗證片段

下一個判斷：只把 PromotionRule 換成 FluentValidation 夠嗎？

原本 Service 內部除了贈品規則，還有一堆手動 if（配送次數範圍、配送週期必填等）， 性質相同、只是驗證對象不同。如果只換掉一部分，同一支 API 會有兩套驗證風格並存， 維護心智負擔沒有真正下降。於是決定：用一個 Validator 驗證整個 ProductAddRequest， 內部巢狀委派子 Validator。

ProductAddRequestValidator : AbstractValidator<ProductAddRequest> ├─ RuleFor(ShopId) / ProductNo / ShippingPeriod / ShippingSet / Max / Fixed └─ RuleForEach(RegularProductPromotionRules) .SetValidator((request, _) => new RegularProductPromotionRuleValidator( ComputeShipLimitCount(request), request.ProductShippingSet)) │ └─ RegularProductPromotionRuleValidator : AbstractValidator<RegularProductPromotionRule> └─ RuleForEach(GiftItemList) .SetValidator(new RegularProductPromotionGiftItemValidator())

跨欄位參數傳遞的技術難題： RegularProductPromotionRuleValidator 需要知道父層 Request 的 shipLimitCount／shippingSet， 這不屬於 Rule 自身欄位。用 FluentValidation 的 SetValidator(Func<TParent,TChild,IValidator<TChild>>) overload， 在驗證當下動態 new 一個帶參數的子 Validator。

DI 註冊的取捨 子 Validator 建構子有必填參數，不適合被 AddValidatorsFromAssembly 批次註冊， 但它從來不會被單獨當服務注入——永遠是被父 Validator 動態建立。真正走 DI 的只有最外層 IValidator<ProductAddRequest>。
刻意不做的事 FluentValidation 天生能收集全部錯誤，但 Controller 的 Message 是單一字串設計。這次先只取 Errors[0].ErrorMessage，把「聚合所有錯誤」列為未來獨立的需求變更， 避免這次重構夾帶行為變更。

拆分要不要拆成獨立專案？

先盤點公司既有慣例：grep Nine1.Promotion／Cart／ Coupon／Shopping 等專案， 全部都採用獨立 Xxx.Common.Validators 專案模式， 統一 FluentValidation 11.5.1，用 AddValidatorsFromAssembly 做組件層級批次註冊。

面向放在 BL.Services拆獨立 Common.Validators
依賴方向與 Service 混在一起，邊界模糊只依賴 BE（DTO），方向單純
可測試性需連帶 Service 其他依賴可獨立單元測試，免 mock Repository
可重用性只有 Service 能用未來其他消費者也能引用
符合公司慣例否是（與既有多個專案一致）
現況規模—目前只有一個消費者，overhead 略顯「殺雞用牛刀」

最初建議是「規模還小，先不拆」，但這個保守建議被推翻了：

「我覺得趁現在還小的時候大家比較敢改專案，應該現在就拆成獨立 validators 專案！」

背後的道理：專案結構調整的阻力，會隨程式碼量、依賴數量、既有消費者數量增加而遞增。 現在搬移成本只是「新建 csproj + 改幾個 using」；等規則寫多、被多個 Service 依賴後再拆， 就會牽動一大片改動，且會有人怕改壞既有功能而不敢動。越早拆，沉沒成本越低—— 這比「當下 overhead 大小」更重要。

落地最終整合方式

  • 新建 Nine1.Regularpurchase.V2.Common.Validators 專案，只 ProjectReference BL.BE（Validator 只需認得 DTO，不依賴 Service/Repository）
  • 建立 AddRegularPurchaseValidators() 擴充方法，內部 AddValidatorsFromAssembly 批次註冊，之後新增 Validator 免手動加 DI
  • RegularProductService 改注入標準介面 IValidator<ProductAddRequest>，刪除舊的錯誤指向
  • AddProductAsync 開頭統一呼叫 ValidateAsync，取代純欄位規則的手動 if；但 SCM 查詢、重複商品檢查、生效區間 Overlap 檢查等依賴 DB／外部服務的規則刻意留在 Service，不塞進 Validator——Validator 只管靜態規則，才能維持單獨可測試
  • .sln 手動加入新專案；BL.Services／Test 補上 ProjectReference
Principles

可抽象出的七條通則

跳脫這個案例本身，未來遇到類似情境可以重新檢視的判斷依據

01

先做便宜的可逆重構，再做貴的技術選型

抽 Interface（Extract Class）幾乎零風險，卻能清楚劃出「要不要換函式庫」的決策邊界，降低反悔成本。

02

手寫程式碼開始山寨某個函式庫時，就是換函式庫的訊號

自己刻的 IValidator/Validate() 幾乎是 FluentValidation 的縮水版。

03

驗證邊界應對齊「物件」而非「欄位片段」

只驗證子物件、不驗證整個 Request，會讓同一支 API 存在多套驗證風格；應以「完整輸入物件」為單位設計。

04

跨欄位依賴不該逼子 Validator 走 DI 單例

用 SetValidator(Func<parent,child,IValidator<child>>) 在驗證當下動態建構，是標準手法。

05

拆專案的時機看「未來改動阻力」，不是看「當下 overhead」

規模小時拆分的邊際成本最低，此時最適合對齊公司既有架構慣例。

06

不要讓一次重構同時夾帶行為變更

維持「只回傳第一個錯誤」不變，把「聚合全部錯誤」留給未來獨立的需求變更，避免混淆驗收範圍。

07

Validator 只管靜態規則，I/O 依賴留在 Service

讓 Validator 保持純粹、可脫離資料庫與外部服務單獨做單元測試，是長期可維護性的關鍵界線。

現象啟動時直接拋出 AggregateException

還沒接到任何 Request，dotnet run 啟動階段就未處理例外：

Startup Exception
System.AggregateException: Some services are not able to be constructed

// Innermost exception
System.InvalidOperationException : Unable to resolve service for type 'System.Int32'
while attempting to activate
'RegularProductPromotionRuleValidator'.

根因批次掃描把「帶參數建構子」的 Validator 也註冊了

AddRegularPurchaseValidators() 用 AddValidatorsFromAssembly 掃描整個組件，把每個 AbstractValidator<T> 都當服務註冊進 DI。 但 RegularProductPromotionRuleValidator 建構子需要 (int shipLimitCount, int shippingSet)——這兩個值是 驗證當下從 ProductAddRequest 動態算出來的上下文， 根本不是能預先注入 DI 的服務。ASP.NET Core 啟動時做 DI 容器驗證，解析不到 System.Int32 對應的服務，直接在啟動階段炸掉。

這正是第 4 章設計時已預先標注的風險點： 「因為建構子有參數，不適合單獨註冊為 DI service——這點尚未驗證，是潛在風險點」。 這次啟動專案，風險兌現了。

它本來就不該被 DI 管理——設計上它永遠只被 ProductAddRequestValidator 用 SetValidator(Func<parent,child,IValidator<child>>) 在驗證當下動態 new 出來，真正需要走 DI 的只有最外層的 IValidator<ProductAddRequest>。

修復用官方 filter 排除該類別

利用 FluentValidation 公開的 AddValidatorsFromAssembly(assembly, filter:) overload，在批次掃描時明確排除這一個類別，不讓它進 DI 容器：

ServiceCollectionExtension.cs（修復後）
public static void AddRegularPurchaseValidators(this IServiceCollection services)
{
    services.AddValidatorsFromAssembly(
        Assembly.GetExecutingAssembly(),
        filter: scanResult => scanResult.ValidatorType != typeof(RegularProductPromotionRuleValidator));
}
為什麼這樣改安全 只排除「這一個」有問題的類別，其餘 Validator 建構子都沒有外部參數， 繼續正常走批次自動註冊，行為不變；不動任何業務驗證邏輯。
不是 hack filter 是 FluentValidation 公開 API 的正規用法， 不是反射繞過或私有 API。

驗證結果：dotnet build 整個 solution → 0 Error； dotnet run 實際啟動 Web.Api → 不再拋出 AggregateException， Kestrel 成功綁定埠、服務正常啟動。

延伸提醒（既有設計限制，非本次引入）：未來若再新增其他「建構子帶參數」的 Validator， 也必須一併加進這個 filter 排除清單，否則會重複踩到同樣的啟動期例外。若這類 Validator 增多， 可考慮改用白名單註冊或 marker interface 做更明確區分；目前只有一個特例，排除法已足夠且最小侵入。

現象VS Code 找不到 HK-Dev / TW-Dev / MY-Dev 啟動選項

launchSettings.json 明明已經定義好 TW-Dev／HK-Dev／MY-Dev 三個 profile（各自對應不同的 N1_MARKET）， 但 VS Code「執行與偵錯」面板下拉選單只看得到 C#: Debug Active File、Node.js…、 Docker: Build… 等原生 debugger 類型，完全找不到這三個自訂 profile， 導致每次啟動都落在預設值（TW-QA）。

根因launchSettings.json 與 .vscode/launch.json 是兩個獨立系統

檔案誰在讀作用
Properties/launchSettings.json dotnet run、Visual Studio、VS Code C# 擴充 定義「profile」——一組環境變數 + URL 設定的集合
.vscode/launch.json 只有 VS Code 的 Debug 面板 定義「VS Code 看得懂的 debug configuration」，需要自己手動指定要對應哪個 profile

launchSettings.json 裡的 profile 不會自動變成 VS Code Debug 面板下拉選單的選項；Visual Studio 有這種自動對應行為，但 VS Code 沒有——兩者中間必須靠使用者 自己在 .vscode/launch.json 手動建立一筆對應設定，VS Code 才認得。

修復在 .vscode/launch.json 手動對應 profileName

用新版 C# Dev Kit 支援的 "type": "dotnet" + profileName 屬性直接對應到 launchSettings.json 的 profile，不需要重複抄一次環境變數：

.vscode/launch.json
{
    "configurations": [
        {
            "name": "C#: Debug Active File",
            "type": "dotnet",
            "request": "launch",
            "projectPath": "${file}"
        },
        {
            "name": "HK-Dev",
            "type": "dotnet",
            "request": "launch",
            "projectPath": "${workspaceFolder}/.../Nine1.Regularpurchase.V2.Web.Api.csproj",
            "profileName": "HK-Dev"
        }
    ]
}
欄位意義 name 顯示名任取；type 固定 dotnet （舊版 coreclr 不支援 profileName）； profileName 必須與 launchSettings.json 逐字一致（含大小寫）。
生效方式 存檔後 Ctrl+Shift+P → Reload Window， Debug 面板下拉選單即會出現新選項。

常見踩雷點：① profileName 打錯字/大小寫不符，VS Code 不會報錯，只會悄悄套用預設環境變數； ② 改完忘記 Reload Window；③ type 誤用舊版 coreclr； ④ projectPath 要指到具體 .csproj，不能只給資料夾。

備援方案（不依賴 VS Code UI）：直接在終端機用 --launch-profile 參數指定：

Terminal
dotnet run --launch-profile HK-Dev

現象呼叫 API 收到 "No authorized."

本機啟動專案後，用 REST Client 呼叫 POST /api/regular/products， 沒有進到 Controller 的任何驗證邏輯（連最前面 ShopId <= 0 的檢查都沒觸發）， 直接收到統一格式的失敗回應：

Response
{
  "Status": "Failure",
  "TxId": "d5dc866684b04efabe2e94826feb2dc2",
  "Data": null,
  "ErrorMessage": "No authorized."
}

根因全域 ApiKeyAuthMiddleware 攔截在 MVC pipeline 之前

這支 API 有一個全域 ApiKeyAuthMiddleware，攔截所有 /api/* 路由，在進入 MVC pipeline（Controller/FluentValidation） 之前就先做驗證：

ApiKeyAuthMiddleware.cs
private const string ApiKeyHeaderName = "x-api-key";

if (context.Request.Path.StartsWithSegments("/api", ...))
{
    if (headers.TryGetValue(ApiKeyHeaderName, out var apiKey) == false
        || apiKey != this._validApiKey)
    {
        // 直接回傳 "No authorized."，不呼叫 next()，Controller 完全不會執行
    }
}
  • 對應 V1 PHP 的 check_api_key()，比對 x-api-key Header 與設定檔 _N1SECRETS:RegularPurchase:ApiGbXApiKey 是否相符
  • 這把 Key 依市場（TW/HK/MY）各自不同，實體檔案在 config\secrets.{Market}-QA.json 底下的 RegularPurchase.ApiGbXApiKey
  • 驗證發生在 Middleware pipeline 最前面，不符合就直接短路回應，next(context) 不會被呼叫， 完全不會進到 Controller——這就是為什麼「連最前面欄位檢查都沒反應」，不是驗證邏輯或 FluentValidation 的問題

修復Request 補上 x-api-key Header

Request 加上 x-api-key Header，值取自「目前啟動市場」對應的 secrets 檔案， 並建立可重複使用的 RegularProduct.http（REST Client 格式）， 把 baseUrl／apiKey／shopId 抽成頂端變數：

RegularProduct.http
@apiKey = REPLACE_WITH_APIGBXAPIKEY_FROM_SECRETS_JSON

POST {{baseUrl}}/api/regular/products
x-api-key: {{apiKey}}
Content-Type: application/json

{ ... }
踩雷點：跨市場誤用 Key 用 HK-Dev 啟動服務卻拿 TW 的 Key 去打，一樣會 "No authorized."—— Middleware 是逐字元比對，不會自動判斷市場。
與 FluentValidation 是不同層級 x-api-key 檢查在 Middleware pipeline， 會在 IValidator<ProductAddRequest> 跑之前就先擋下， 兩者互不影響也不能互相取代；除錯時要先排除「根本沒過 API Key 關卡」，再往下查驗證邏輯本身。

動機Service 建構子被迫塞越來越多 IValidator，驗證時機也不夠早

原本 RegularProductService 為了驗證 ProductAddRequest， 建構子必須注入 IValidator<ProductAddRequest>；可預期未來每多一支需要 FluentValidation 的 API，Service 建構子就要多塞一個 IValidator<TRequest>， 讓「業務邏輯」與「驗證」的依賴混在一起，且驗證發生在 Service 方法內部第一行，時機也不夠早—— 理想上應該是 Request 一進 Controller 就先擋掉不合法資料，Service 完全不用管驗證。

方案做法取捨
A. 全域 Action Filter（採用） 寫 IAsyncActionFilter，反射找出參數對應的 IValidator<T> 並執行 一次性建置，新增 Request 驗證完全不用碰 Filter／Service
B. Controller 手動呼叫 每支 Action 自己注入 IValidator<TRequest> 直覺但每支 API 都要複製貼上樣板碼
C. 整合進 MVC ModelState 自訂 ValidationVisitor 掛進內建模型驗證流程 官方已不建議，較舊較複雜，不採用

機制ValidationActionFilter：型別對上就自動驗證

Filters/ValidationActionFilter.cs
public class ValidationActionFilter : IAsyncActionFilter
{
    public async Task OnActionExecutionAsync(context, next)
    {
        foreach (var argument in context.ActionArguments.Values)
        {
            // 依「參數的實際型別」動態組出 IValidator<T>，向 DI 容器查詢是否有註冊
            var validatorType = typeof(IValidator<>).MakeGenericType(argument.GetType());
            var validator = context.HttpContext.RequestServices.GetService(validatorType) as IValidator;

            if (validator == null) continue; // 沒有對應 Validator 就放行

            var result = await validator.ValidateAsync(new ValidationContext<object>(argument));
            if (result.IsValid) continue;

            context.Result = new OkObjectResult(/* Status=Failure */);
            return; // 短路，Controller Action 完全不會被執行
        }
        await next();
    }
}
builder.Services.AddControllers(options =>
{
    options.Filters.Add<ValidationActionFilter>();
});

同步移除 RegularProductService 建構子的 IValidator<ProductAddRequest> 依賴，AddProductAsync 內也拿掉手動 ValidateAsync 呼叫。

結論只要建立對應 Validator 就自動生效，兩個前提缺一不可

這個機制能「加了 Validator 就自動生效、不用改其他程式碼」，關鍵在於兩件事同時成立：

  • 有寫 Validator 類別——繼承 AbstractValidator<TRequest>， 放在 Nine1.Regularpurchase.V2.Common.Validators 專案底下
  • 有被註冊進 DI——靠既有的 AddValidatorsFromAssembly(assembly, filter: ...) 自動掃描整個 Assembly，把所有 AbstractValidator<T> 註冊成 IValidator<T>；Filter 只在執行期用參數型別去問 DI 容器有沒有註冊， 完全不知道也不需要知道有哪些 Request 型別存在

因此新增 XxxRequestValidator : AbstractValidator<XxxRequest> 丟進 Common.Validators 專案，不需要改 Program.cs、Filter、Service， 下次呼叫對應 API 就會自動被攔截驗證。

例外 1：建構子帶無法被 DI 解析的參數 如 RegularProductPromotionRuleValidator 吃 (int, int)， 已在 filter 明確排除，不會被自動掃描，也不會被 Filter 攔截到—— 它是由 ProductAddRequestValidator 透過 SetValidator((request, _) => new ...(...)) 動態建立、傳入額外上下文。
例外 2：Validator 寫在 Common.Validators 專案以外 AddValidatorsFromAssembly 只掃描「這一個」組件； 其他專案想加 Validator，要嘛也放進這個組件，要嘛要在 ServiceCollectionExtension 多補一行掃描新 Assembly。
例外 3：多個參數且型別重複 目前每個 Request 型別只對應唯一一個 Validator；若同一 Action 有多個參數都各自有 Validator， Filter 依序驗證、遇到第一個失敗就短路回傳，尚無回傳「所有參數所有錯誤」的需求。

同一輪也在 Controller／Service 的 AddProductAsync 全路徑補上 ILogger 記錄，並確認 ProductAddRequestValidator 可安全注入 ILogger<ProductAddRequestValidator>（框架內建服務，DI 可解析， 跟 9.1~9.6 提到的「建構子吃 int 而炸掉」完全不同性質），在 PreValidate override 記錄「這次是誰進來驗證」。順手移除 Controller 裡與 Validator 重複的 ShopId <= 0 手動檢查。

驗證結果：dotnet build 0 Error； dotnet test --filter RegularProduct 20/20 通過。

補洞補齊遺漏的欄位規則，並把商品頁驗證抽成共用方法

逐一比對需求文件與程式碼，發現以下規則完全沒做：ProductPurchaseOption 應限 1 或 2；PlanTitle 全形/半形混合上限 20 字、純半形上限 40 字； PlanDateBegin 須晚於現在 10 分鐘以上；PlanDateEnd 須晚於 PlanDateBegin；以及生效期間不得超出商品銷售期間。

規則放置位置原因
PurchaseOption / PlanTitle 字數 / 日期時序 ProductAddRequestValidator 純欄位/跨欄位比對，不需外部資料，用 TimeProvider + DateTimeHelper.GetNow(...) 取得現在時間
生效期間 vs 商品銷售期間 RegularProductService（方案 A） 需要 SCM 回傳的 SellingStartDateTime/ SellingEndDateTime，FluentValidation 目前只做同步無 I/O 規則， 拿到 salePageData 後立刻檢查，與「商品序號已存在」等規則位置一致

順帶把 AddProductAsync／EditProductAsync 原本重複的「salePageData == null → ShippingTypeDef 非定期購 → HasPointsPayPairs」三段檢查抽成共用 ValidateSalePageData； 再另外包一層 ValidateSalePageDataForAddAsync， 只給 AddProductAsync 用，串接「生效期間 vs 銷售期間」 「商品序號已存在」「生效期間重疊」這三項只有新增流程才需要的檢查。 因為 ProductEditRequest 本身沒有 PlanDateBegin/PlanDateEnd 欄位， 這條規則刻意不放進兩邊都共用的 ValidateSalePageData， 避免共用簽章被迫塞進只有一邊會用到的參數。

驗證結果：dotnet build 0 Error，且抽出共用方法後 用 validatedSalePageData（null-forgiving）取代重複判斷， 沒有新增 CS8602 警告；dotnet test --filter RegularProduct 20/20 通過。EditProductAsync 本輪未變動。

疑問帶入非法 enum 字串為什麼只回傳籠統的 "Invalid Data"？

實際打 API 測試，把 Type、GiftTypeId 這類欄位帶入不存在的字串（如 "fefewf"、"yyy"）， 沒有進到 ProductAddRequestValidator 或 RegularProductService，而是直接回：

{
  "Status": "Failure",
  "TxId": "c8c6f690237c44b7adabd0eb69985992",
  "Data": null,
  "ErrorMessage": "Invalid Data"
}

根因：Type／GiftTypeId 是 enum 型別，搭配 JsonStringEnumConverter。整個順序是：

  1. ASP.NET Core 收到 body → 先做 Model Binding（JSON 反序列化成 ProductAddRequest）
  2. 非法字串無法轉成合法 enum 成員，反序列化在這一步就失敗
  3. [ApiController] 判定 ModelState 無效 → 在 Action 執行前 （比 ValidationActionFilter、Controller、Service 都早） 呼叫 Program.cs 裡的 InvalidModelStateResponseFactory
  4. 這個 factory 是刻意對齊 V1：型別轉換失敗一律回 HTTP 200 Status=Failure, ErrorMessage="Invalid Data"，而非 HTTP 400
結論：刻意設計、對齊 V1 行為，不是 bug，也不是 Filter/Validator 沒生效—— Model Binding 失敗發生在最早的階段，兩者根本沒機會被執行到。
除錯優先順序提醒：日後遇到「傳入看似合理的值，但直接回籠統 Invalid Data， 且 Validator/Service 的 Log 完全沒印出來」時，先檢查該欄位是否為 enum/int/DateTime 等非 nullable 型別、傳入值能否被反序列化，而不是先查 Validator 或 Service 業務規則。 若要讓錯誤訊息更明確，需調整 InvalidModelStateResponseFactory， 但會偏離目前對齊 V1 簡化訊息格式的設計，需先確認是否要改。

延伸SMS 站台 BFF 端 enum 序列化：預設會要求呼叫端傳數字

範圍轉移：以下發生在 NineYi.Sms（SMS/OSM 站台），不是本文件主體的 nine1.regularpurchase.v2——新增 BFF 端點 Api/RegularProduct/Create 用來串接 v2 站台的 POST /api/regular/products 時發現的獨立問題，記在此處是因為 跟 9.11 屬於同一系列（enum 序列化格式）的延伸案例。

SMS 端 RegularProductCreateRequestEntity 內的 ShippingCountModeEnum／RegularProductPromotionTypeEnum／ RegularProductPromotionTriggerModeEnum／ RegularProductPromotionOutOfStockActionEnum 一開始都只是單純 C# enum，沒有加任何 JsonConverter。

根因：SMS 站台是 ASP.NET (Framework) Web API + Newtonsoft.Json， 全域設定（WebApiConfig.cs／JsonConvertSetting.cs） 並未註冊 StringEnumConverter（只有既有的 ProductScopeJsonConverter 等自訂 converter，跟此次無關）。 Newtonsoft.Json 對純 enum 屬性的預設行為是數字，但需求規格書 （regular-product-create-api-spec.html 2.2 節）明確要求 ShippingCountMode 等欄位是 enum（string）， 範例 JSON 也都是 "Gift"／"Interval" 這類字串—— 若不處理，OSM 前端呼叫這支新 API 時會被迫傳數字，跟規格書、跟 v2 站台 （已用 JsonStringEnumConverter）的呼叫慣例不一致。

修復：只在這 4 個 enum 型別本身加 [JsonConverter(typeof(StringEnumConverter))] （沿用倉庫既有慣例，如 MemberCollectionTypeDefEnum）， 而不是修改 WebApiConfig.cs 全域註冊。
為什麼刻意選局部而非全域：全域加 config.Formatters.JsonFormatter.SerializerSettings.Converters 會影響全站其他既有 API 的 enum 序列化行為（風險高、範圍不可控）； 局部加在型別宣告上，只影響用到這 4 個型別的地方，不會波及其他人正在維護的功能。

驗證結果：MSBuild 整個 NineYi.Sms.sln → 0 Error。因為 RegularProductService 內組下游 Request 時是用 rule.Type.ToString()（或改用 AutoMapper 的 MapFrom(s => s.Type.ToString())）取字串， StringEnumConverter 只影響 JSON 序列化/反序列化， 不影響 .ToString() 的行為，兩者互不衝突。

除錯優先順序提醒（延伸 9.11）：新增一支 BFF API 時，若 Request/Response 內含 enum 欄位， 務必先確認該站台是否有全域 StringEnumConverter； 若沒有，且規格書要求字串格式，需自行在 enum 型別上補 [JsonConverter(typeof(StringEnumConverter))]， 不能假設「有 enum 屬性就自動是字串」——不同站台（ASP.NET Core System.Text.Json vs ASP.NET Framework Newtonsoft.Json）、甚至同站台不同 Controller 的全域設定都可能不同。

BugSMS 端 IsGiftEnabled=false 時仍組出贈品活動規則存入下游

範圍：NineYi.Sms，RegularProductService.Create。 實測請求帶 "isGiftEnabled": false 但同時夾帶 regularProductPromotionRules 陣列時，SMS 仍把該陣列轉換後整包傳給 v2 站台的 /api/regular/products，導致明明關閉贈品活動的方案， v2 端仍把 rpd_promotion_json 存成非空陣列。

根因：組裝 RegularProductCreateApiRequestEntity 時， RegularProductPromotionRules 欄位單純用 (entity.RegularProductPromotionRules ?? new List<...>()).Select(this.ToApiPromotionRule).ToList() 無條件轉換，完全沒有參考 entity.IsGiftEnabled—— 本輪稍早新增的 RegularProductCreateRequestEntityValidator 只驗證 「IsGiftEnabled=true 時規則不可為空」這個方向， 沒有反向規則「IsGiftEnabled=false 時應忽略/清空規則」， 呼叫端夾帶垃圾資料時就會被原樣transformed 存下去。

修復：RegularProductService.Create 改成依 entity.IsGiftEnabled 分流：true 才轉換 RegularProductPromotionRules；false 一律組空 List<RegularProductPromotionRuleApiEntity>() 傳給下游，不管呼叫端是否誤帶規則資料。Build 0 error 驗證通過。
提醒：Validator 只負責「擋掉不合法的組合」，不等於「自動清洗/忽略不該存在的資料」—— 兩者是不同職責。像這種「某開關關閉時，相關聯欄位應該被忽略而非驗證失敗」的情境， 必須在 Service／組裝 Request 的地方明確處理，不能只靠 Validator 補完整。

設計缺口v2 新增定期購方案 API 沒有回傳 rpd_pk，SMS 端只能回傳商品頁序號

範圍：跨兩站台——現象發生在 NineYi.Sms，根因在 nine1.regularpurchase.v2。前端呼叫 SMS 的 Api/RegularProduct/Create 新增成功後，預期拿到的應該是 新建立的定期購方案序號（rpd_pk），供後續 Edit／Get API 使用； 但目前 SMS 回給前端的 RegularProductCreateResponseEntity.ProductNo 其實只是呼叫端當初傳入的商品頁序號（原樣回填），完全不是 v2 新增後產生的方案序號。

根因追查（由 SMS 往下游追到 v2 三層）：

  • v2 RegularProductRepository.InsertAsync(RegularProductEntity entity) 的 INSERT SQL 沒有 RETURNING rpd_pk，方法簽章直接回傳 bool（只知道有沒有插入成功，插入後產生的 rpd_pk 直接被丟棄，沒有任何管道往上傳）。
  • v2 RegularProductService.AddProductAsync 回傳型別是 RegularProductResult<object?>，成功時只回 RegularProductResult<object?>.Success("儲存成功")， Data 恆為 null。
  • v2 RegularProductController.AddProductAsync 回傳 MessageApiResponseEntity<string>， Data = result.Message（就是一句「儲存成功」的字串，不是 pk）。
  • SMS RegularProductHttpClient.Create 把下游回應反序列化成 RegularShopSettingApiResponseEntity<object>， Data 型別是 object，本來就沒地方可以解析出 pk。
  • SMS RegularProductService.Create 最後回傳 new RegularProductCreateResponseEntity { ProductNo = entity.ProductNo }—— 直接回填 request 帶進來的商品頁序號，跟資料庫實際產生的 rpd_pk 完全無關。
正確修法（尚未動工，先記錄，使用者決定暫不改 v2）：
1) v2 InsertAsync 改用 INSERT ... RETURNING rpd_pk（Dapper ExecuteScalarAsync<long>），回傳新產生的 rpd_pk 而非 bool。
2) AddProductAsync 回傳型別由 RegularProductResult<object?> 改成攜帶 rpd_pk 的型別（例如 RegularProductResult<long> 或新增 ProductAddResponse { long PlanId }）。
3) Controller 把該 pk 放進 Data 回傳給 SMS。
4) SMS RegularProductHttpClient／ RegularProductCreateApiRequestEntity 對應的 Response 型別要能解析出該 pk， RegularProductService.Create 改成 RegularProductCreateResponseEntity.PlanId = 下游回傳的 rpd_pk （而不是 ProductNo），前端拿這個 PlanId 去打後續 Edit/Get API。
已知類似前例：v2 站台其他既有查詢（GetPagedListAsync、 RegularOrderService）都是用 PlanId 對應 rpd_pk／ rgo_rpd_pk 的命名慣例，未來補這個欄位時應沿用 PlanId 這個既有命名，不要另創新名詞。
除錯優先順序提醒：新增（Create）類型的 API 若前端後續需要用「新建立資源的 Id」 做編輯/查詢，務必在設計 Response 階段就確認整條鏈路（Repository Insert → Service → Controller → 上游 BFF）每一層都有把這個 Id 往外傳，不能只驗證「新增有沒有成功」， 而忽略「新增後產生的識別碼有沒有回得去」。此問題本次只發現、未修復（使用者決定暫緩 v2 端改動）。

盤點贈品清單必填檢查漏了 Type 前提條件

SMS RegularProductPromotionRuleEntityValidator 新增時，RegularProductPromotionGiftItemList 必填（至少 1 筆） 的規則原本沒有加任何 When 條件，等於不管 Type 是什麼都會要求要有贈品清單。

修正：加上 .When(i => i.Type == RegularProductPromotionTypeEnum.Gift)，只有活動類型是「贈品」時才要求贈品清單必填。 本次僅開放 Type=Gift 一種活動類型，這條件目前恆真， 但寫上去是為了未來若擴充其他活動類型（非贈品類）時，不會被這條規則誤擋。

提醒：巢狀規則的必填檢查要回頭確認「這個必填是不是有前提條件」， 不能因為目前資料只有一種可能值，就省略 When—— enum 值域未來擴充時，沒有 When 的規則會變成隱性 bug。

盤點Service/HttpClient 是否需要重複驗證 ShopId？——不需要，理由是分層各自負責不同事

盤點 RegularProductService.cs／ RegularProductHttpClient.cs 是否每個 Method 都要檢查 ShopId／SupplierId。 本次 API 沒有 SupplierId 概念，故只討論 ShopId。

分層目前作法驗證的是什麼需要嗎
RegularProductController.Create _userService.GetCurrentUser() + IsAuthenticated(shopId) 權限/認證：這個登入者能不能操作這個 ShopId 需要，且已存在
RegularProductService.Create if (shopId <= 0) throw 參數合法性：呼叫者傳進來的數值本身合不合法，跟呼叫者是誰無關 需要，且已存在
RegularProductHttpClient.Create 無驗證，直接組 request 送出 — 不需要：純傳輸層，且唯一呼叫端（Service）已經驗證過
結論：Controller 的權限驗證、Service 的參數防呆，兩者目的不同、互補而非重複， 都該留著。HttpClient 加驗證只是形式重複，不會攔到任何上層沒攔到的情況，違反 DRY， 且本專案其他既有 *HttpClient 類別也沒有這種二次驗證的先例。
判斷原則：遇到「這個分層要不要加驗證」的疑問時，先問「這一層驗證的目的跟 其他層是否相同」；如果是同一件事（例如都在檢查同一個數值合不合法），就該只留一層， 放在最靠近資料來源、最早能擋下的地方，其餘層不必重複。

盤點兩個「要不要調整」的疑問：TypeLite/Enums.ts 同步、HtmlCleanService XSS 防護

疑問一：新增/改名的 Enum、Entity 是否要同步更新 TypeLite.Net4.d.ts／Enums.ts？

結論：不需要。TypeLite.Net4.tt 是用明確的白名單 （.For<Namespace.ClassName>()）決定要產生哪些 C# 類別的 TS 定義， 不是自動掃描全部類別；本次改動的 RegularProductPromotionOutOfStockActionEnum／ RegularProductPromotionTriggerModeEnum／ RegularProductPromotionTypeEnum／ShippingCountModeEnum／ RegularProductCreateRequestEntity／RegularProductCreateResponseEntity／ RegularProductPromotionGiftItemEntity／RegularProductPromotionRuleEntity／ RegularProductCreateApiRequestEntity／RegularProductPromotionGiftItemApiEntity／ RegularProductPromotionRuleApiEntity 從一開始就沒有任何一個被 .For<>() 註冊過。原因是這批 Entity 是 Api/RegularProduct/Create 這支 BFF API 的 Request/Response DTO， 消費端是外部獨立的 OSM 前端專案，不是本 repo 自己的 Razor 頁面／內嵌 TS， 跟 TypeLite 產生鏈路完全無關。只有「本 repo 自己的 .cshtml 頁面內的 TS 會直接引用該類別」時，才需要加進 .tt 的 .For<>() 清單。

疑問二：RegularProductCreateRequestEntity 是否需要用 HtmlCleanService 防範 XSS？

結論：不需要。盤點既有用法（LocationService.Create/Update 對 CustomOpeningHoursContent 做 Clean()）， HtmlCleanService 是用在「會被存起來、之後可能被當 HTML 渲染到前台頁面」的 自由文字欄位。而本次新增的欄位裡，唯一的字串欄位只有 Title（方案名稱）， spec 明確定義它「不顯示於前台」，只是後台操作人員自己看的標籤，不會被任何頁面用 innerHTML 之類方式渲染；其餘欄位（SalepageId／ 日期／enum／int／bool）皆非字串，天生無 XSS 疑慮。 即使 Title 含 <script> 字樣，因為只會被當純文字顯示/儲存， 不會被瀏覽器解析成 HTML，沒有注入風險。

共通判斷原則：這兩個疑問看似不同，但判斷邏輯一致——先確認「這個機制的產生/觸發條件是什麼」 （TypeLite 是白名單制、HtmlCleanService 是給會被當 HTML 渲染的欄位用）， 再回頭比對「這次改動的東西符不符合那個觸發條件」，而不是看到規則名稱或警告訊息就照樣套用。 若未來 Title 被顯示在前台頁面且用 HTML 渲染方式呈現， 或這批 Entity 開始被本 repo 自己的 Razor 頁面引用，才需要重新評估這兩個結論。

補充：TypeLite.Net4.tt 這支 T4 樣板的執行意義與用途

  • 本質：這是一支 .tt（T4 Text Template）檔案， 搭配 Visual Studio 內建的 T4 文字樣板引擎，在設計階段（每次存檔/手動執行 Transform） 或建置後被執行一次，執行的是 C# 程式碼（樣板內用 <# #> 包起來），不是執行期程式碼、不會在網站執行時跑。
  • 做的事：透過 <#@ assembly name="$(TargetDir)NineYi.Sms.BL.BE.dll" #> 這類指令，載入本專案編譯後的 DLL（例如 NineYi.Sms.BL.BE.dll）， 再用 TypeLite 這套 library 透過 .NET Reflection 讀取白名單裡 .For<Namespace.ClassName>() 註冊過的 C# 類別／Enum 的欄位、型別、 列舉成員，自動產生對應的 TypeScript 介面／列舉定義，輸出成 TypeLite.Net4.d.ts（型別宣告檔）與 Enums.ts （由 manager.StartNewFile("Enums.ts") 另外拆出的列舉定義檔）。
  • 用途：讓本 repo 自己的 .cshtml 頁面內嵌的 TypeScript／JavaScript 程式碼，可以直接 import 這些自動產生的介面／列舉型別， 跟後端 C# Entity 的欄位名稱、型別、列舉值保持強型別同步， 避免前端 TS 手動謄打一份重複定義、日後後端改欄位卻忘記同步前端而出現執行期才發現的欄位對不上問題。
  • 因為是白名單機制：只有明確寫進 .For<>() 的類別才會被 Reflection 掃到、產生 TS 定義；沒被登記的類別（包含本次新增/改名的 RegularProduct* 系列）完全不會出現在產生結果裡， 也就不會有「異動 C# 卻沒同步 TS」的落差問題——因為打從一開始就沒有產生過對應的 TS 定義可言。

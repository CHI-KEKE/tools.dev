Root Cause Analysis · NineYi.Sms

單元測試診斷記錄

TranslationClientLocator 靜態初始化陷阱，如何讓三支毫不相干的測試同時 FAIL
專案：NineYi.Sms.BL.Services.Test 測試框架：xUnit + NSubstitute 日期：2026-08
問題現象

01 Cake Test With Coverage 出現 3 個 [FAIL]

在 NineYi.Sms.BL.Services.Test 專案的一次完整測試執行中，出現 3 個看似毫無關聯的測試失敗， 皆拋出相同型態的例外： 

System.TypeInitializationException :
  The type initializer for 'NineYi.Sms.Utilities.Extensions.CacheExtensions' threw an exception.
---- System.NullReferenceException : ITranslationClient instance is null.
失敗清單：
  • JooiiPromotionServiceTest.GetJooiiSettings_ShouldReturnDefaultResult_WhenSettingsAreNull
  • UserPermissionServiceTest.Test_DeleteUser_Success
  • NotificationServiceTest.Test_NotificationService_Create_Success

表面上這三個測試分屬 Jooii AI 行銷、使用者權限、推播通知三個完全不同的業務模組， 彼此的 Service、Repository、Mock 都沒有交集，卻在同一次測試執行中「集體陣亡」，這是最初讓人困惑的地方。

根因分析

02 .NET 型別初始化的「一次失敗、永久損毀」語意

追蹤 CacheExtensions.cs 原始碼後發現關鍵： 

public static class CacheExtensions
{
    private static bool _isCacheWithLocale;

    // 靜態欄位初始化：型別第一次被觸及時就會執行
    private static ITranslationClient _translationClient = TranslationClientLocator.GetInstance();

    static CacheExtensions() { /* ... */ }

    public static string AppendLocale(this string src) { /* 使用 _translationClient */ }
}

同樣的模式也出現在多語系自動產生的類別中，例如 Backend.Validators.SalePages： 

private static readonly ITranslationClient _TranslationClient = TranslationClientLocator.GetInstance();
關鍵機制： C# 的靜態建構式 / 靜態欄位初始化在同一個 AppDomain（也就是一次測試執行的 process）中只會執行一次。 若第一次觸及該型別時 TranslationClientLocator.GetInstance() 回傳 null（尚未 Register）， CLR 會拋出 TypeInitializationException，並將該型別狀態永久標記為初始化失敗。 之後任何程式碼——即使已經正確完成 mock 設定——只要再次存取這個型別，都會直接收到同一個被快取住的例外，不會重新嘗試初始化。

為什麼會「一顆老鼠屎壞了一鍋粥」

本專案的慣例是在每個測試類別建構子呼叫共用工具 CommonMocks.MockTranslationClientGetString()， 內部會呼叫 TranslationClientLocator.Register(mockedClient) 先行注入一個 NSubstitute 假物件： 

public sealed class CommonMocks
{
    private CommonMocks()
    {
        var mockedTranslationClient = Substitute.For<ITranslationClient>();
        mockedTranslationClient
            .GetString(Arg.Any<string>(), Arg.Any<string>(), Arg.Any<string>())
            .Returns(x => x.Args()[1]); // 回傳 key 本身，而非真正翻譯字串
        mockedTranslationClient.GetLocale().Returns("zh-TW");
        TranslationClientLocator.Register(mockedTranslationClient);
    }

    public static void MockTranslationClientGetString()
    {
        if (_instance != null) return;
        lock (Root) { _instance = new CommonMocks(); }
    }
}

問題在於：JooiiPromotionServiceTest.cs 與 StockServiceTest.cs 這兩個測試類別的建構子都漏掉了這一行呼叫（本專案其餘 180 餘個測試檔案都有）。 當 xUnit 依測試發現順序執行到這兩個類別、且是「本次 process 中第一個」觸及 CacheExtensions 或 Backend.Validators.SalePages 的測試時，就會讓該型別初始化失敗並被永久快取， 連帶拖累同一個 process 內、之後才執行、原本設定正確的其他測試。

為什麼需要多語系服務

03 例外訊息 / 快取 Key 本身就是多語系文案

這些 Service 之所以在單元測試中也需要 ITranslationClient，是因為 production 邏輯把多語系當成一般字串在使用，而不只是畫面顯示：

  • CacheExtensions.AppendLocale() — 快取 Key 需要加上目前語系（GetLocale()），確保不同語系不會共用到錯誤的快取內容。
  • StockService.UpdateSafetyStockDefault() — 驗證失敗時的例外訊息，是直接用 Translations.Backend.Validators.SalePages.CanBeInput1ToX 組出來的（「請輸入 1 ~ {0} 之間的數量」）， 而不是寫死的字串常數。

測試斷言（Assert.Equal）會拿「production 呼叫同一個多語系 API 組出的訊息」來比對， 因此測試環境必須先用 CommonMocks 把 ITranslationClient mock 起來， 讓 GetString 有一個可預期、不依賴外部翻譯伺服器的回傳值（實際上是直接回傳 key 本身）， 測試才能在離線環境下穩定、可重現地驗證邏輯。

診斷與修復過程

04 排查步驟

1. 檢視測試輸出，鎖定共同例外型態

三個 FAIL 的 Stack Trace 都指向 CacheExtensions..cctor() 與 TranslationClientLocator.GetInstance()，判斷這是同一根因造成的連鎖反應，而非三個獨立 bug。

2. 搜尋專案慣例，確認 mock 呼叫方式

以 MockTranslationClientGetString 為關鍵字搜尋，發現全專案 180 餘個測試檔案都有呼叫， 藉此比對出哪些測試檔案「漏掉了」這個慣例。

3. 逐一確認缺陷檔案

JooiiPromotionServiceTest.cs（新增的 AI 行銷測試）與後續回報的 StockServiceTest.cs（安全庫存預設值測試）皆確認建構子未呼叫 CommonMocks.MockTranslationClientGetString()。

4. 套用一致的修復手法

在兩個測試類別的建構子最前面加入 CommonMocks.MockTranslationClientGetString();， 並補上對應的 using NineYi.Sms.Translations.UnitTestTools;。

5. Build + 全量測試驗證

使用 xunit.console.exe 分別針對受影響類別、以及整個測試專案重新執行，確認不再出現 TypeInitializationException，且無其他新增失敗。

修改檔案清單

  • Test/BL.Services.Test.Xunit/JooiiPromotions/JooiiPromotionServiceTest.cs
  • Test/BL.Services.Test.Xunit/Stock/StockServiceTest.cs

修改內容皆相同：於建構子第一行加入 CommonMocks.MockTranslationClientGetString();，不觸碰任何業務邏輯或既有斷言。

結論與建議

06 心得與後續預防建議

  1. 症狀與根因不必然一一對應。 三個（後來變六個）互不相干的測試同時 FAIL，根因卻只有一個：新測試檔案漏寫一行既有慣例的 mock 呼叫。 關鍵在於辨識出「共同的例外型態 + 靜態初始化語意」，而不是逐一 debug 每支測試。
  2. 靜態欄位初始化搭配外部相依（Locator Pattern）具有隱藏風險。 TranslationClientLocator.GetInstance() 這種「型別載入時就綁死相依」的寫法， 會讓錯誤的影響範圍超出單一測試，波及同一 process 內所有之後執行的測試，且錯誤時機（哪個測試先跑到）帶有不確定性。
  3. 建議事項：
    • 可考慮建立一個 xUnit Collection Fixture / AssemblyFixture，在整個測試組件載入時就統一呼叫一次 CommonMocks.MockTranslationClientGetString()，避免依賴「每個測試類別建構子都要記得寫」這種容易遺漏的慣例。
    • Code Review checklist 可加入一項：新增使用到 Translations 相關靜態類別 / CacheExtensions 的測試， 必須確認建構子有呼叫 CommonMocks.MockTranslationClientGetString()。

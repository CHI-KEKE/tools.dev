STEP 02

設計骨架：讓 6 個測試不必重複寫 20 行 Arrange

AuditByRedisDataAsync 一路依賴 7 個外部服務，若每個測試都重新 mock 一次，會非常吵雜。因此先解決「共用 Happy Path」的問題。

建構子：把「正常路徑」都掛好

先讓所有依賴回傳「正常會發生的資料」，測試只需覆寫差異點

在測試類別建構子中，把 GetUniqueKeyAsync、Load<PayProcessContextEntity>、 GetTradesOrderSlaveIdListAsync、GetListAsync、GetRequestHeaders、 PutObjectAsync 全部先掛上「不出錯」的預設回應。

MemberCollectionAuditServiceTests.cs
public MemberCollectionAuditServiceTests()
{
    // 建構共用的正常路徑依賴，讓每個測試案例只需覆寫與該案例相關的行為
    _tradesOrderGroupRepository.GetUniqueKeyAsync(ShopId, OrderCode).Returns(UniqueKey);
    _userRedisDataService.Load<PayProcessContextEntity>(...).Returns(new PayProcessContextEntity());
    _tradesOrderGroupRepository.GetTradesOrderSlaveIdListAsync(ShopId, OrderCode)
        .Returns(new List<long> { 1 });
    _promotionHttpClient.GetRequestHeaders(ShopId).Returns(new Dictionary<string,string>());
    _amazonS3.PutObjectAsync(...).Returns(new PutObjectResponse { HttpStatusCode = HttpStatusCode.OK });
}
✓ 好處：每個測試只需要覆寫「真正影響該情境」的那一兩個 mock，其餘全部沿用共用設定，測試本體因此更聚焦、更好讀。
抽出資料建構的 Helper

SetupMemberCollectionIdList(...) —— 把「準備幾個客群 Id」變成一行呼叫

6 個測試裡有 4 個都需要「準備 N 筆 MemberCollectionId 並讓 GetPromotionMemberCollectionByTargetMemberTypeDefAsync 回傳對應資料」。 於是抽成一個 params string[] 的私有方法，避免每個測試重複寫同樣的 5 行組裝邏輯。

MemberCollectionAuditServiceTests.cs
private void SetupMemberCollectionIdList(params string[] ids)
{
    var list = ids.Select((id, i) => new PromotionEngine
    {
        PromotionEngine_Id = i + 1,
        PromotionEngine_MemberCollectionId = id
    }).ToList();

    _promotionEngineRepository
        .GetPromotionMemberCollectionByTargetMemberTypeDefAsync(ShopId, ..., Arg.Any<List<int>>())
        .Returns(list);
}
STEP 03

逐一把「風險點」寫成測試

測試案例不是隨機湊數，而是對應開發過程中每一個曾經被質疑、修正過的邏輯分支——確保未來不會悄悄回歸。

01
含 FIRST_PURCHASE 標籤驗證核心過濾邏輯：該筆 Id 不應出現在傳給 MemberMatch 的清單中
02
皆無 FIRST_PURCHASE 標籤反向驗證：正常情境不該被誤過濾，全部 Id 應完整送入 Match
03
下游查詢單筆失敗最關鍵案例——驗證失敗不會造成資料遺失，而是以「無標籤」保留參與比對
04
全部皆為首購客群驗證過濾後為空清單時，提早 return，不呼叫 Match、不寫入 S3
05
無任何客群相關活動驗證最前面的空清單守門邏輯，確認完全不觸發下游 API
06
payProcessContext 為 null驗證最上層的早期 return，避免對不存在的付款資訊繼續處理
最關鍵的一個測試怎麼寫出來

Case 03：用 .Throws() 模擬下游失敗，斷言「Id 沒有消失」

這個案例是整組測試的核心——直接對應開發過程中「呼叫失敗還是要 add to list」的正確性修正。 寫法上刻意讓兩個 Id 走不同路徑：一筆正常回應、一筆讓 mock 拋出例外，最後只斷言 兩者都出現在送進 MemberMatch 的清單裡。

MemberCollectionAuditServiceTests.cs
[Fact]
[Trait("Category", nameof(MemberCollectionAuditService.AuditByRedisDataAsync))]
public async Task AuditByRedisDataAsync_呼叫下游取得客群資訊失敗_該筆Id仍應保留於Match清單中()
{
    // Arrange
    SetupMemberCollectionIdList(normalId, failedId);
    _promotionHttpClient.GetMemberCollectionDataAsync(normalId, Arg.Any<...>())
        .Returns(new GetMemberCollectionsResponseEntity { CollectionId = normalId, CollectionTags = new() });
    _promotionHttpClient.GetMemberCollectionDataAsync(failedId, Arg.Any<...>())
        .Throws(new HttpRequestException("下游服務逾時"));

    // Act
    await sut.AuditByRedisDataAsync(ShopId, OrderCode, MemberId);

    // Assert — 下游查詢失敗不代表該客群為首購客群，仍須保留稽核
    await _promotionHttpClient.Received(1).MemberMatch(
        Arg.Is<MemberMatchRequestEntity>(x =>
            x.MemberCollectionIdList.Contains(normalId) &&
            x.MemberCollectionIdList.Contains(failedId)),
        Arg.Any<...>());
}
用「行為驗證」取代「回傳值斷言」

為什麼每個測試最後都是 Received(1) / DidNotReceive()，而不是檢查回傳值？

AuditByRedisDataAsync 是 Task（無回傳值）的稽核流程，真正的「結果」體現在它跟哪些依賴互動、傳了什麼參數。 因此測試策略統一採用 NSubstitute 的互動驗證（interaction verification）：

  • Received(1).MemberMatch(Arg.Is<...>(x => ...)) — 驗證傳入的客群清單內容是否正確
  • DidNotReceive().MemberMatch(...) — 驗證提早結束時真的沒有繼續往下呼叫
  • DidNotReceive().PutObjectAsync(...) — 連帶驗證早期 return 也不會誤觸發 S3 上傳
STEP 04

寫完不代表對：編譯、修錯、再驗證

測試程式碼本身也會犯錯。這一段記錄從「寫完」到「真正綠燈」之間，實際踩到的編譯問題與修正過程。

第一次 Build：CS1061

「'Task<T>' does not contain a definition for 'Throws'」

.Throws(new HttpRequestException(...)) 在 NSubstitute 裡其實是一個擴充方法， 預設的 using NSubstitute; 並不包含它——它被拆分在獨立的命名空間裡。

✗ 編譯失敗
using NSubstitute;
// 缺少 Throws 擴充方法所在的 namespace
✓ 補上正確的 using
using NSubstitute;
using NSubstitute.ExceptionExtensions;
✓ 補上 NSubstitute.ExceptionExtensions 後，測試專案重新編譯通過（0 Error）。

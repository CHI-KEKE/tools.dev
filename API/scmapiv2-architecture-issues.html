01

結構層問題 — 巨石與耦合

Architecture & Coupling
高

巨石單體（Monolith）過於肥大 Structure

121 個 Controller、258 個 Service 全部塞在同一個 WebSite / BL.Services 專案，橫跨會員、訂單、物流、行銷、金流、通路等完全不同的業務領域。
WebSite/WebSite/Controllers/** · BusinessLogic/Services/**
影響：任何一支 API 變更都要重新編譯、部署整站，回歸測試範圍被迫放大，故障也無法隔離——一支 API 拖慢 ThreadPool，其餘 120 支跟著遭殃。
高

單一 Repository 專案耦合 12 個資料庫 Data Coupling

DA.Repositories 直接引用 12 個不同資料庫專案，違反「一個服務只碰自己資料庫」的微服務原則。
DA.Repositories

影響：未來想把任何一個領域拆成獨立服務，都會被資料庫耦合綁死，是遷移新架構最大的技術障礙。
中

DI 註冊集中在單一巨型檔案 DI / God File

ServiceModule.cs 一支檔案就有 152 筆 RegisterType 註冊，每次新增服務都要改這支共用檔案。
// CrossLayer/Modules/BL/ServiceModule.cs（節錄）
builder.RegisterType<OmoKeyPromptsService>().As<IOmoKeyPromptsService>();
builder.RegisterType<CrmOrderService>().As<ICrmOrderService>();
// ... 共 152 筆 ...
CrossLayer/Modules/BL/ServiceModule.cs
影響：可讀性差、合併衝突機率高，也缺乏依領域分組的模組化註冊方式。
中

缺乏清楚的領域邊界（Bounded Context） DDD

專案結構是「技術分層」（Controllers / Services / Repositories）而非「領域分層」，BL.BE 共用實體被 13 個專案引用。
影響：容易演變成大泥球（Big Ball of Mud），改一個欄位可能波及多個看似無關的業務功能。
02

程式碼與執行期問題

Code Quality & Runtime Pattern
高

全面同步（Sync-only），無 async/await Runtime

掃描 BL.Services 完全沒有 async/await/Task<> 的正規使用；反而出現 Sync-over-Async 反模式。
// OmoKeyPromptsService.cs
keyPromptTasks.Add(Task.Run(() => {
  return keyPrompt.GetKeyPrompt(request);
}));
Task.WhenAll(keyPromptTasks).Wait();  // ⚠️ 阻塞等待
BusinessLogic/Services/OmoKeyPrompts/OmoKeyPromptsService.cs
影響：DB 逾時或慢查詢時會佔用大量 ThreadPool 執行緒，其他請求被迫排隊延遲，逾時風險被放大（已有實際 Production 錯誤案例佐證）。
中

索引資訊不受版本控管 Database

EF Fluent Mapping（CrmSalesOrderConfiguration.cs）只定義欄位對應，完全沒有 Index 相關設定；索引全部只存在 SQL Server，repo 內無法追蹤或審查。
DataAccess/CrmDB/Tables/CrmSalesOrderConfiguration.cs
影響：無法透過 Code Review 把關索引異動，實際已發生因缺乏合適複合索引導致 SQL 逾時（Execution Timeout Expired）的 Production 事件。
低

查詢後在記憶體中做迴圈勾稽 Performance

先 ToList() 撈出全部資料，再用 LINQ 迴圈逐筆比對正負向訂單，資料量大時有 O(n²) 風險。
BusinessLogic/Services/OmoKeyPrompts/GetMemberOmoOrderKeyPrompt.cs
03

跨切面關注點不一致

Cross-Cutting Concerns
中

驗證機制並存兩套，未集中管理 Auth

同時存在 ValidateTokenAttribute（t/ts/s 簽章）與 ValidateJWTAttribute（JWT），依 Controller 各自掛 Attribute，沒有統一管線。
Extensions/ActionFilters/ValidateTokenAttribute.cs · ValidateJWTAttribute.cs
影響：新 API 開發時容易選錯或漏掛驗證方式；稽核與安全檢視成本高。
低

統一輸出格式存在「例外白名單」 Consistency

UnifiedResultHandler 對 PDF 下載、金流 callback 等特定路徑直接略過包裝，格式不是真正 100% 統一。
Extensions/DelegatingHandlers/UnifiedResultHandler.cs
04

技術棧與維運問題

Tech Stack & DevOps
高

技術棧老舊 Tech Debt

.NET Framework 4.6.2（2016 年釋出）+ EntityFramework 5.0.0（2012 年釋出），無法容器化跑在 Linux 容器（無 Dockerfile）。
影響：缺乏新語言特性與長期安全更新，維運方式與公司新服務（如已採用 .NET 10 + Docker + K8s 的 nine1.regularpurchase.v2）世代脫節。
中

部署流程分裂、複雜 CI/CD

根目錄有 9 個獨立 Jenkinsfile（Build / Deploy / BlueGreenDeploy(Fallback) / FinishRelease / CreatePPBranch / MultiMarket(PP) 等）。
影響：部署邏輯分散在多套腳本，維運複雜度高，缺乏像 Helm values 統一管理多市場/多環境設定的做法。
05

建議優先順序

不搬遷也能先做的 vs. 需搭配架構搬遷
優先度項目建議做法
P0 SQL 索引補強 不需搬遷架構即可執行，成本低、效果立即，先解決已發生的 Production 逾時事件。
P0 移除 Sync-over-Async 反模式 將 Task.Run().Wait() 改為真正的 async/await，降低 ThreadPool 阻塞連鎖風險。
P1 依領域拆分獨立服務（Strangler Fig） 優先挑選耦合度低、獨立性高的模組（如定期購 RegularOrder），逐步搬到新架構，資料庫先共用、邏輯先分離。
P1 統一驗證機制 新架構統一改用單一驗證策略（如純 JWT + Gateway 層驗證），避免新舊兩套並存。
P2 DI 註冊模組化 依領域拆分 Autofac Module，取代單一 152 筆的 ServiceModule.cs。
P2 容器化 + 統一部署管線 比照新站台導入 Docker + Helm + GitLab CI，逐步汰換多套 Jenkinsfile。

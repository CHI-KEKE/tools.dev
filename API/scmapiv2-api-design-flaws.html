01

HTTP 動詞語意誤用

幾乎所有端點都是 POST，即使是查詢

查詢類 API 仍使用 POST，而非 GET HTTP Semantics

全站 121 個 Controller 中，只有 Health、Ops、Translation 三個用了 [HttpGet]，其餘（包含所有純查詢 API）一律用 [HttpPost]。
[HttpPost]
[Route("GetPermission")]
public LocationWizardPermissionEntity GetPermission(LocationBaseRequestEntity request)
{
  return this._locationService.GetLocationWizardPermissions(request.ShopId);
}

[HttpPost]
[Route("GetMemberBasicInfo")]
public MemberBasicInfoResponseEntity GetMemberBasicInfo(GetMemberBasicInfoRequestEntity request)
WebSite/Controllers/Apis/LocationController.cs · SalesOrderController.cs（GetList 也是 POST）
影響：失去 HTTP GET 天生的語意優勢——瀏覽器/CDN 快取、瀏覽器歷史記錄、可加書籤的查詢 URL、冪等性保證全都用不上；呼叫端也無法用標準工具（如瀏覽器直接開連結）測試查詢類 API。

完全沒有 PUT / DELETE / PATCH CRUD Semantics

掃描全部 Controller，找不到任何 [HttpPut]、[HttpDelete]、[HttpPatch]，更新/刪除操作全部用 POST + 自訂動詞路由名稱表示。
現行做法（RPC 風格）
POST /SalesOrder/UpdateNote
POST /SalesOrder/CancelOrder
POST /SalesOrder/UpdateShippingOrderCode
POST /Location/UpdateLocationEmployeePassword
REST 慣例（建議方向）
PATCH /sales-orders/{id}/note
POST  /sales-orders/{id}/cancel   (動作類保留POST合理)
PATCH /sales-orders/{id}/shipping-code
PUT   /locations/{id}/employee-password
影響：呼叫端無法從 HTTP Method 判斷操作是否為「更新」「刪除」，所有語意都得靠讀 URL 路徑名稱猜測，增加對接與維護成本。
02

路由與命名風格 — RPC 而非 Resource-Oriented

動詞在前 vs 名詞資源

路由以「動作命名」而非「資源命名」 Routing

路由設計走 RPC 風格：{RoutePrefix}/{動詞+受詞}，例如 SalesOrder/GetList、SalesOrder/ConfirmSalesOrderSlave、SalesOrder/CloseOrderReturn，而非 REST 慣例的「名詞資源 + HTTP 動詞」。
目前路由HTTP Method對應的 REST 慣例寫法
SalesOrder/GetListPOSTGET /sales-orders?...
SalesOrder/CancelOrderPOSTPOST /sales-orders/{id}/cancel
SalesOrder/UpdateNotePOSTPATCH /sales-orders/{id}
Location/GetMemberBasicInfoPOSTGET /locations/{id}/members/{memberId}
影響：路由清單等同於方法清單而非資源清單，隨著功能增加，端點數量線性膨脹（單一 Controller 內 20~90 個 Route 很常見），難以用 REST 慣例快速理解「這個資源能做哪些操作」。
03

狀態碼與錯誤語意扁平化

幾乎只用 200 / 400 / 500 三種

不使用標準 HTTP 狀態碼表達結果 Status Code

全站掃描不到一次 HttpStatusCode.NotFound（404）的使用；成功一律 200，失敗依例外分類落在 400 或 500，真正的語意改用回應 Body 裡的 Status: "Success"/"Failure" 字串欄位表達。
{
  "ErrorId": "",
  "Status": "Failure",    // ⚠️ 語意在 Body 裡，不是 HTTP Status
  "Data": null,
  "ErrorMessage": "找不到該筆訂單",
  "TimeStamp": "2026-07-27T16:00:00"
}
// 實際 HTTP Response 卻是 200 OK 或統一 400
影響：標準 HTTP Client / API Gateway / 監控系統（如依 Status Code 做告警）無法單靠 Status Code 判斷「資源不存在」「未授權」「驗證失敗」等差異，都得解析 Body 內容才知道真正結果，增加整合複雜度，也不利於标準化的 API Monitoring。
04

API 版本管理機制缺失

SwaggerConfig.cs

Swagger 版本號硬編碼，路由無版本區隔 Versioning

Solution 名稱是 NineYi.Scm.ApiV2（暗示存在 V1），但 Swagger 設定寫死 SingleApiVersion("v1", ...)，路由也沒有 /v2/xxx 這類版本區隔（少數 BatchUpload 例外走 v2/batchupload/）。
// App_Start/SwaggerConfig.cs
c.SingleApiVersion("v1", "NineYi.Scm.ApiV2.WebSite");
// MultipleApiVersions 相關程式碼被註解掉，從未真正啟用
App_Start/SwaggerConfig.cs
影響：沒有正式的版本演進機制，要改變既有 API 的 Contract（例如欄位型別、必填規則）時，只能直接修改既有端點，容易造成 Breaking Change 波及所有既有呼叫方，無法讓新舊版本並存讓客戶端逐步遷移。

Deprecated 端點沒有正式下架機制 API Lifecycle

程式碼中可見 CheckIsValidObsolete 等命名帶有 "Obsolete" 字樣的端點，代表已知過時卻仍留在正式路由裡繼續對外服務，缺乏 [Obsolete] 標記、Sunset Header 或版本化下架流程。
影響：呼叫方無從得知該用哪一支「現行」API，也沒有機制提醒被棄用的端點應該遷移，技術債只會持續累積不會被清理。
05

Request / Response 契約不一致

同一份 API 文件下，實際行為卻有例外

統一信封格式（Envelope）有硬編碼白名單例外 Contract

多數 API 走 { "Data": "..." } 信封格式，但 virtualpayment、PDF 下載、ops/healthcheck 等路徑會被 UnifiedResultHandler 硬編碼路徑字串排除，直接回傳原始格式。
影響：同一份 Swagger 文件下，實際上有兩種不同的 Request/Response 約定，呼叫端必須額外知道「這支 API 是不是特例」，容易出錯，且新增例外只能靠改程式碼裡的字串清單，沒有宣告式（如 Attribute 標記）的方式管理。

DTO 命名洩漏了內部分層術語 Naming

對外的 Request/Response 型別大量使用 XxxRequestEntity / XxxResultEntity 命名，"Entity" 一詞在多數團隊慣例中代表 DB 對應實體，卻被拿來當作 API 契約 DTO 的命名，容易讓人誤解這是資料庫實體直接暴露給外部。
影響：對新加入的工程師或第三方文件閱讀者而言，容易混淆「這是 API 契約」還是「這是資料庫結構」，增加理解成本。
06

改善方向建議

新站台可以直接採用的 API 設計原則
優先度項目建議做法
P0 新 API 一律走正確 HTTP 動詞 查詢用 GET（參數走 Query String，不強制帶 Body）、建立用 POST、整批更新用 PUT、部分更新用 PATCH、刪除用 DELETE。
P0 使用標準狀態碼表達結果 找不到資源回 404、未授權回 401/403、驗證失敗回 422、成功建立回 201，減少讓呼叫端只能靠解析 Body 判斷結果。
P1 路由改為資源導向 採用 /{resource}/{id}/{sub-resource} 結構，動作類（如 cancel、confirm）可保留為子路徑但語意仍要清楚。
P1 導入正式版本策略 透過 URL Path（/v2/...）或 Header 做版本區隔，讓新舊 Contract 可並存，逐步淘汰 Obsolete 端點並提供明確 Deprecation 時程。
P2 移除信封格式白名單 新架構直接用原生 JSON Body，不需要 Data 信封 + 白名單例外這種雙軌設計。
P2 DTO 命名脫離 Entity 字眼 對外契約改用 XxxRequest / XxxResponse，與資料庫 XxxEntity 明確區分。

# User Story 程式碼符合性檢核技能

此技能用於**比對需求與現況程式碼的一致性**，重點是：
1. 需求是否有被完整實作
2. 實作是否有證據可追溯
3. 是否存在功能/驗收缺口與風險

## 何時使用

當使用者需要以下任一情境時，應使用本技能：
- 「幫我看這版有沒有符合 User Story」
- 「請檢核 AC 是否都落地」
- 「PR 功能有沒有符合需求」
- 「列出需求落差與風險」
- 「驗收前做需求對照」

## 必要輸入

若資訊不足，先向使用者補齊：
- VSTS Work Item ID（必填，User Story）
- Azure DevOps 專案資訊（若執行環境需要）：organization、project
- 檢核範圍（分支、PR、資料夾或檔案）
- 是否需要包含測試與文件（預設：需要）
- 若涉及前端畫面或 wording：Figma 連結（fileKey、nodeId）

## VSTS ID 驅動規則（重要）

此技能預設採用「**先吃 VSTS ID，再做檢核**」：

1. 先接收使用者提供的 VSTS Work Item ID。
2. 透過 Azure DevOps 工具擷取 User Story 完整資訊。
3. 再依擷取結果萃取檢核點並進行程式碼比對。

### 必擷取欄位

- 標題（Title）
- 需求描述（Description）
- 驗收條件（Acceptance Criteria）
- 相關連結項目（Linked items，例如 Task/Bug/PR）

### 失敗備援

若無法成功擷取 Work Item（例如權限不足、ID 不存在、環境未連線）：
- 明確告知原因
- 請使用者貼上 User Story 內容與 AC
- 在報告中標記「需求來源：手動貼入（未由 VSTS 直取）」

## Figma 文案比對規則（前端需求時啟用）

當 User Story 或 AC 涉及前端畫面、欄位名稱、按鈕文案、提示訊息、錯誤訊息時：

1. 先擷取 Figma 指定節點內容（文字層與元件標籤）。
2. 整理為「預期文案清單」（頁面/區塊/文案鍵值）。
3. 再到程式碼中比對實際文案來源（前端程式碼、i18n 資源、常數檔）。

### Figma 失敗備援

若無法存取 Figma（連結無效、權限不足、nodeId 不完整）：
- 明確標示「設計證據不足」
- 請使用者提供設計截圖或文案清單
- 相關條目判定以「需釐清」或「部分符合」為主，不直接判定為完全符合

## 以後端為視角的 Figma 確認規則（後端需求時啟用）

當 User Story 或 AC 涉及後端 API 設計、狀態邏輯、錯誤處理，且有提供 Figma 連結時，應從後端視角解讀設計稿，以確保 API 與系統邏輯符合前端預期。

### 執行步驟

1. **解讀 Figma 流程與錯誤訊息**  
   擷取 Figma 指定節點的流程說明、欄位名稱及錯誤提示規則，理解前端依賴哪些 API 回傳值來驅動畫面狀態。

2. **整理「預期後端回傳資料清單」**  
   將流程與欄位邏輯轉化為結構化清單，格式如下：
   - 欄位名稱（fieldName）
   - 對應畫面狀態或情境
   - 預期資料型態 / 允許值
   - Figma 所標示的錯誤代碼或錯誤訊息

3. **比對程式碼一致性**  
   在指定範圍（Controller / Service / DTO）確認：
   - API 回傳欄位名稱與 Figma 清單一致
   - 狀態值（status / code）與 Figma 流程節點對應
   - 錯誤代碼與錯誤訊息與 Figma 標示一致
   - 不需比對按鈕文字或畫面文案，聚焦於資料與邏輯層

### 輸出附加欄位

在「需求對照表」中，後端 Figma 確認條目需額外填寫：
- **Figma 預期後端欄位/狀態/錯誤代碼**：從 Figma 萃取的預期值
- **程式碼實際值**：實作中對應的欄位、狀態、錯誤代碼
- **一致性判定**：一致 / 不一致 / 需釐清

### 後端 Figma 確認失敗備援

若無法存取 Figma 或節點缺乏足夠的 API 說明：
- 標示「後端 Figma 資料不足」
- 請使用者補充 API contract 或錯誤代碼規格
- 相關條目以「需釐清」判定，不視為完全符合

## 工作流程

1. **根據 VSTS ID 擷取 User Story**
   - 取得標題、描述、AC、相關連結項目
   - 若缺少 AC，需在報告列為「需釐清」並提示補件

2. **萃取需求檢核點**
   - 將 User Story 轉為可驗證條目（功能、驗收條件、例外/邊界）

3. **蒐集程式碼證據**
   - 在指定範圍搜尋實作、測試、設定、文件
   - 每個檢核點至少附一個可追溯證據（檔案/符號/測試）

4. **（條件式）蒐集 Figma 證據**
   - **前端文案視角**：僅在前端畫面/wording 需求時執行，將 Figma 預期文案與程式碼實際文案逐條比對
   - **後端資料視角**：當需求涉及後端 API 設計且有 Figma 連結時，依「以後端為視角的 Figma 確認規則」執行，整理預期後端回傳資料清單並比對程式碼一致性

5. **做符合性判定**
   - `符合`：有完整實作與證據
   - `部分符合`：有實作但不完整，或缺少測試/例外處理
   - `不符合`：找不到實作或與需求相反
   - `需釐清`：需求本身模糊，無法客觀判定

6. **輸出缺口與風險**
   - 針對每個「部分符合 / 不符合 / 需釐清」提出：
     - 缺口描述
     - 影響範圍
     - 建議修正方向（不直接改程式碼，除非使用者要求）

7. **彙總整體結論**
   - 提供總體符合率（可用條目數計算）
   - 給出驗收建議：可驗收 / 有條件驗收 / 不建議驗收

## 輸出格式

請**固定使用以下模板**：

# User Story 符合性檢核報告
## 1) 檢核摘要
- VSTS ID:
- User Story: 
- 需求來源: VSTS 直取 / 手動貼入
- 設計來源: Figma 直取 / 手動提供 / 不適用
- 檢核範圍: 
- 結論: 可驗收 / 有條件驗收 / 不建議驗收
- 條目統計: 符合 X、部分符合 Y、不符合 Z、需釐清 N

## 2) 需求對照表
| 檢核點 | 判定 | 程式碼證據 | 測試證據 | 設計/文案證據(Figma) | 說明 |
|---|---|---|---|---|---|
| AC-1 | 符合/部分符合/不符合/需釐清 | ... | ... | ... | ... |

## 3) 缺口與風險
- [優先級: 高/中/低] 缺口：...
  - 影響：...
  - 建議：...

## 4) 待確認問題
- 問題 1：...
- 問題 2：...

## 5) 後續建議
- 建議下一步 1
- 建議下一步 2

## 判定原則

- 沒有證據，不算符合。
- 只有主流程、沒有邊界條件與測試，最多判「部分符合」。
- 若需求文字與實作不一致，優先標記「需釐清」，並列出衝突點。

## 執行時行為

- 當使用者提供 VSTS ID 時，先做需求擷取，不要直接進入程式碼檢核。
- 若已成功擷取 VSTS 內容，後續分析應以該版本為主，不以猜測補齊 AC。
- 若使用者同時提供 VSTS ID 與手動需求文字，優先比對兩者差異並標示衝突。
- 若需求包含前端文案，先完成 Figma 擷取再做 wording 比對，不可省略。
- 每次輸出都要保留可追溯路徑：VSTS ID → 檢核點 → 程式碼證據 → 判定。

## 品質守則

- 用語精準、可追溯、可驗證。
- 避免主觀詞（例如「看起來可以」），改用證據導向描述。
- 若缺乏必要資訊，先提出 1-3 個關鍵釐清問題再下結論。

## 範例

**輸入：**
- User Story: 「作為營運，我希望可依關鍵字搜尋訂單，並可按狀態篩選」
- AC: 
  - AC1: 關鍵字支援訂單編號與收件人
  - AC2: 狀態篩選可多選
  - AC3: 查詢結果支援分頁

**輸出重點：**
- 逐條 AC 對應到 API/controller/service/repository 與測試
- 對缺漏（例如僅單選狀態）標記「部分符合」並說明影響

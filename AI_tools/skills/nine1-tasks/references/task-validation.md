# Task Validation — 7 維度驗證邏輯

---

## 驗證維度

| # | 維度 | 檢查重點 |
|---|------|---------|
| 1 | **需求覆蓋率** | 每個需求 → 至少對應一個任務 |
| 2 | **範圍邊界** | 任務遵守 Goals / Non-Goals |
| 3 | **驗收標準** | 所有 AC 已涵蓋且可測試 |
| 4 | **依賴一致性與平行安全** | 任務順序符合需求流，每個 `[P]` 對均無直接、傳遞、生產者-消費者合約依賴 |
| 5 | **完整性品質** | 所有任務段落均已填寫 |
| 6 | **任務大小** | 2-4 小時、功能單元（非純程式碼產出物） |
| 7 | **缺口識別** | 是否遺漏 DB Migration、測試、文件、監控任務 |

---

## 平行安全強制驗證

對每個 `[P]` 任務對，須確認：
- 無直接依賴
- 無傳遞依賴
- 無生產者-消費者合約關係
- 無共用合約/資源衝突

**若任意一項失敗 → 驗證結果為 `FAIL`，須移除或重新分組 `[P]` 標記，回 task-breakdown / parallel-analysis 重新規劃。**

## 驗證報告格式

```markdown
## 📋 任務拆解驗證報告

**分析日期：** YYYY-MM-DD | **任務總數：** {N} | **狀態：** {PASS / WARNINGS / FAIL}

### ✅ 通過項目
- 需求覆蓋率：100%
- 驗收標準：{N}/{M} 已涵蓋
- 依賴邏輯：順序正確
- 平行安全：所有 `[P]` 任務對均通過合約消費確認

### ⚠️ 警告
1. [AC-2] 效能需求缺少測試任務 → 建議新增「Task X：效能測試」
2. Task 3 缺少錯誤處理規格 → 更新任務說明

### ❌ 嚴重問題
1. Task 6「Redis 快取」違反 Non-Goals → 移除或取得明確核准
2. Task 4 標記 [P] 但消費 Task 3 新建的 `IPromotionService` → 移除 [P] 標記並重新分組

### 📊 覆蓋率摘要
| 維度 | 狀態 | 詳細 |
|------|------|------|
| 需求覆蓋 | ✅ 100% | 全部已涵蓋 |
| 任務大小 | ⚠️ 70% | 3/10 需調整粒度 |
| 平行安全 | ✅ Pass | 所有 [P] 對已驗證 |

### 🔧 必要行動
**必須修正：** 上述問題 1-2
**應新增：** 缺失關注點的任務
**選填：** 釐清記錄更新

### ❓ 需要使用者決定的項目
1. Task 6 快取問題：(A) 移除 (B) 核准 (C) 列為未來改善項目？
2. 任務粒度：(A) 合併 1-3 → 「資料層」 (B) 保持現狀？

**確認：修正問題後重新驗證、處理特定項目，或接受風險繼續？**
```

# Question Generation — 問題生成規則與多輪策略

---

## 問題生成規則

1. 只生成答案**會實質影響**架構、資料模型、任務分解或測試策略的問題
2. 跳過 Work Item 或現有留言中**已回答**的問題
3. 依 **Impact × Uncertainty** 分數排序（參見 `ambiguity-taxonomy.md`）
4. 每輪**最多 5 題**，**優先窮盡高影響分類的模糊點，再往次優分類推進**（深度優先，而非每類各取一題）
5. 每題必須可用：多選題（2-5 個選項）**或**簡答（≤5 字）回答
6. 每題**必須**提供推薦答案，附 1-2 句理由（繁體中文）

---

## 呈現格式

```markdown
## 🔍 關鍵需求釐清

我已識別出 {count} 個關鍵模糊點需要釐清：

---

### 問題 1: [類別英文 / 類別中文] - {問題標題}

**💡 推薦答案：{選項字母 or 簡答建議}**
**理由：** {1-2 句理由，繁體中文}

| 選項 | 說明 |
|-----|------|
| A | ... |
| B | ...（推薦） |
| 自訂 | 提供簡短答案（≤5 字） |

---

### 問題 N: [類別英文 / 類別中文] - {問題標題}

**💡 建議答案：{簡答建議}**
**理由：** {1-2 句理由，繁體中文}

**格式：** 簡短答案（≤5 字）

---

## 📝 回覆方式

**快速接受所有推薦：**
- 回答 "全部接受" 或 "yes to all" 或 "接受所有推薦"

**個別回答：**
- 格式範例：`1: A, 2: yes, 3: 使用 UnitOfWork, 4: B, 5: yes`

**需要重新說明某題？**
- 指定問題編號，例如："第 3 題不太懂"

**請提供您的回答：**
```

---

## 回答解析邏輯

| 輸入形式 | 處理方式 |
|---------|---------|
| `全部接受` / `yes to all` | 採用所有推薦答案，進入驗證確認 |
| `1: A, 2: yes, 3: 自訂文字` | 逐題解析，`yes`/`suggested` 採推薦答案 |
| 回答模糊 | 針對該題要求澄清（最多 2 次），2 次後採最接近選項 |
| 要求解釋某題 | 補充說明後，僅重新呈現該題 |

**記錄規則（寫入 VSTS 時）：**
- ✅ 記錄：`使用 httpOnly cookie`
- ❌ 不記錄：`選項 B`、`yes`、`接受建議`、`suggested`

## 多輪策略

每輪問答完成後，評估是否有剩餘高影響模糊點：

```python
remaining = [c for c in categories if c.status in ["Partial", "Missing"] and c.impact >= 7]

if remaining:
    prompt_continue()
else:
    proceed_to_arc42_validation()
```

**提示使用者（繁體中文）：**
```markdown
## 📄 本輪釐清完成

**本輪已釐清：** {N} 個問題
**剩餘潛在模糊點：** {M} 個

| 類別 | 狀態 | 影響程度 |
|-----|------|---------|
| ... | ⚠️ Partial | High |
| ... | ✅ Clear | - |

**是否需要繼續釐清？**
- **[Y]** 是，再提出最多 5 個問題
- **[N]** 否，進入 Arc42 驗證
- **[S]** 跳過驗證，直接進入規劃階段
```

**執行邏輯：**
- `[Y]` → 回 SKILL.md Step 3（Round +1）
- `[N]` → 繼續 Arc42 驗證
- `[S]` → 跳至最終摘要，剩餘類別標記 Deferred

## 推薦答案生成策略

生成推薦答案時考量：
1. **最佳實踐**：業界標準做法（OAuth 2.0、REST API 慣例、SOLID 原則）
2. **降低風險**：安全漏洞、效能瓶頸、維護負擔
3. **91APP 背景**：團隊對 .NET Framework 的既有經驗與既有架構模式
4. **務實原則**：平衡理想方案 vs. 實作複雜度 vs. 時程限制

理由範本：
```
"降低 {具體風險}，符合 {標準或最佳實踐}，並{91APP 背景情境}"
```

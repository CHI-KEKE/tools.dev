# 撰寫規範

這些規範是強制性的寫作準則，每次撰寫或優化文件都要套用，不需要每次重新詢問使用者。

## 1. 開場要白話好懂

文件開場（第一個章節）必須用白話描述情境，讓完全不熟悉這個主題的人也能懂大致狀況，不要一開始就丟專有名詞、系統元件名稱、狀態碼。

## 2. 視覺風格要主動確認，不要自己猜

動筆前用 `ask_user` 一次問清楚：這份文件的情境/主題是什麼（決定配色語意基調）、想從 5 種主題中選哪一種（可提案 2-3 個最相關的）、內容素材來源是既有分析或要從零開始。只有小幅微調時可跳過。

## 3. 風格定調後，全文保持一致

一旦決定視覺主題，所有章節都要延續同一套配色、字體、卡片樣式，不要每個章節各自發明新樣式。共用 `<style>` 只在檔案開頭定義一次。

## 4. 關鍵字與配色要配合情境語意

不要用「好看」當唯一標準，顏色要傳達語意並全文保持一致：
- 紅／磚紅色系：需要立即關注的危險、失敗、根因
- 琥珀／橘色系：待觀察、Pending、警示但非致命
- 綠色系：已解決、成功、結案
- 中性色：一般資訊性節點、流程步驟

`organic-glass-style`、`cozy-meadow-style`、`mysql-dolphin-style`、`blue-ghost-style` 例外：這四種是「分類裝飾語意」而非「風險分級語意」，不要套用紅/琥珀/綠的危險語意到它們的主色上。

## 5. 程式碼與專業術語要用 `<code>` 或 `` `code` `` 包起來

行文中的類別名稱、方法名稱、狀態碼、欄位名稱、SQL/程式片段關鍵字，一律要包起來，不要用粗體或裸露文字表示。

## 6. 情境分支要畫清楚

遇到程式邏輯有多個分支（if/else、switch、狀態機），必須把每個分支都寫出來，不能只寫最常見的那條路徑。複雜邏輯拆成多個小節，各自聚焦一個決策層級。

## 7. 敘述不要用節點代號

圖表或流程圖節點可以用代號，但圖表以外的說明文字（提示框、表格說明、段落描述）一律要用白話描述該節點的實際意義，不能直接引用代號。

## 8. 套用卡片模板時，不要為了填滿欄位而硬拆標題

`stage-tag` 這類短標籤欄位只能放真正獨立的簡短標記（例如 `STEP 1`）。標題本身沒有天然短標籤時，不要硬拆一半塞進兩個欄位，直接把完整標題放進主要欄位。

## 9. 文字內容一律不准使用破折號

不管是全形破折號「——」、單一個「—」，還是充當破折號語氣的半形連字號，一律要改用句號、逗號分句，或拆成新的一句話。

## 10. 長段落舉例、理由說明、開場情境導覽要拆解成多種呈現方式，不要擠成一整段文字

當一段說明包含多個實體（例如兩個各自獨立的資料列）、多個對照數字（例如多個 SkuId／庫存/結果）、多種分支結果、多個各自獨立的理由/論點、或是**開場情境導覽包含多種商業玩法與架構矛盾**時，不要把所有細節塞進同一個 `<p>` 或 Hero 的 `hh-desc` 大段落中，改用以下幾種方式依內容形態拆解，通常會同時搭配 2 種以上：

- **開場 Hero（`hh-desc`）精簡化 + 結構化拆解**：開場 Hero 的 `hh-desc` 應控制在 2～3 句俐落的引言（聚焦核心挑戰與文件主旨）。若開場涉及多種商業玩法（如組合商品 vs 加價購），應將玩法拆解為**並排卡片（卡片網格元件）**；若涉及「業務特徵 vs 底層資料結構限制」的矛盾與解法，應拆解為**結構化對照清單或警示框（callout + checklist）**，嚴禁把情境、例子、特徵、資料庫限制、解法全部擠在 `hh-desc` 裡。
- **小型關聯圖（ERD 元件）**：呈現誰跟誰透過哪個欄位關聯，取代用文字描述 A 透過某欄位指向 B。
- **卡片式並排對照（卡片網格元件）**：兩個或多個彼此獨立的實體（例如主件 vs 贈品、方案 A vs 方案 B、玩法一 vs 玩法二），各自一張卡片列出關鍵欄位或情境，取代用分號串接成一長句。
- **表格化明細**：多筆資料列的欄位對照（例如多個 SkuId 各自的規格／庫存／來源），用表格取代文字列舉。
- **結果分支清單**：多種輸入對應多種輸出結果（例如帶 A 會成功、帶 B 會被擋下、帶 C 會被擋下），拆成清單每行一種情境，取代擠在一句話裡的多個分號子句。
- **理由/論點清單**：說明為什麼這樣設計、為什麼不這樣做這類論述時，如果背後有兩個以上各自獨立的理由，先用一句話點出結論或問題，再逐條列出每個理由，每條理由聚焦一個角度，不要把所有理由寫成一串用逗號、句號連接的長句。
- **展開/收合詳情**：補充說明或次要細節（例如關聯欄位的底層邏輯）預設收合，避免預設畫面就是一大段文字，需要時才展開；獨立分析 `.html` 文件可用 `<details>` 標籤實作。

判斷方法：先數一數這段文字裡有幾個獨立的資料點（實體、欄位、數字、結果、理由/論點、商業玩法），如果超過 3 個以上還擠在同一句話或同一段落，就要挑選上述至少一種方式拆解；套用哪一種要看內容形態（開場玩法用卡片、架構矛盾用提示清單、關聯用 ERD、並列實體用卡片、多筆列表用表格、多種結果用清單、多個理由用條列清單、次要細節用收合），不是固定公式，也可以視內容複雜度同時套用多種。

## 11. 敘述不用第二人稱「你」

全文改用去人稱的客觀敘述，把主詞去掉直接描述動作或情境，或改成情境化主詞（使用者、系統、程式）。

## 12. 不要用「誤解／迷思」這類預設立場的字眼，也不要用「一句話理解」這類制式導讀語

補充釐清性內容時，不要用「常見誤解」「常見迷思」「錯誤觀念」這類預設讀者原本想法錯誤的措辭，這帶有評判語氣。改用中性的釐清型標題，直接描述要說明的對應關係或事實本身，例如「購物車與資料列的對應關係」「一台購物車對應的資料列數量」，讓內容本身呈現事實，不對讀者的既有認知做評價。同樣地，「一句話理解」「簡單來說」這類制式導讀語也不要用，如果要用比喻或摘要收尾，直接描述比喻本身即可（例如「貼紙比喻」），不需要額外的引導詞。

## 13. `display:flex` 的容器（`hl-checklist` 的 `<li>`、`hl-callout` 提示框等）只能有「圖示 + 單一內容容器」兩個直接子節點，不能讓內文的多個段落/清單直接當子節點

`display:flex` 只對容器的直接子節點生效。常見誤用有兩種情境：

- 清單元件的 `<li>` 內文若混排 `<strong>`／`<code>` 等行內標籤且 `<li>` 本身設定 `display:flex`，每個行內標籤與被切開的文字片段都會變成獨立 flex item，畫面上出現一條一條很窄的欄位、文字逐字換行的跑版效果。
- 提示框（`hl-callout`）如果同時放了圖示 `<span>` 加上多個內容子節點（例如一段 `<p>` 加一個 `<ul>` 再加一段 `<p>`），這些內容子節點會被當成多個獨立 flex item 並排成橫向欄位，而不是照順序上下堆疊，畫面上出現跑版的多欄並排效果。

修正方式：
- 清單元件需要 `::before` 當作勾選圖示時，`<li>` 改用 `position:relative` 搭配 `padding-left` 留出圖示空間，`::before` 改用 `position:absolute` 定位到左側，`<li>` 本身維持一般文字排版。
- 提示框內容如果不只一個子節點，一定要把圖示以外的所有內容包進一個 `<div class="hc-body">`，讓 flex 容器只看到「圖示 + hc-body」兩個直接子節點，`hc-body` 內部可以自由放多個 `<p>`／`<ul>`，套用 `flex:1` 讓它占滿剩餘寬度即可。

套用既有元件時如果內文需要混排這些標籤或塞入多個段落/清單，動筆前要先確認元件的容器有沒有這個問題，寫完後用瀏覽器或截圖確認排版正常，不能只看原始碼判斷。

## 14. 系統架構圖要符合責任與資料流語意

服務、API、快取、資料庫與錯誤追蹤文件，優先採用 C4 Container、C4 Dynamic Diagram 與資料流圖的分工：

- 系統邊界要能區分外部呼叫端、主要應用程式、支援服務與資料儲存。
- 箭頭要標示協定、API 路徑、資料名稱或分支條件。
- 靜態圖說明容器責任，動態圖說明執行順序，錯誤路徑獨立呈現。
- Cache Aside 必須畫出查詢、命中、未命中、持久化資料讀取與快取回填。
- 顏色與形狀要代表資料或責任類型，不用裝飾性方塊取代架構關係。

## 15. 並排內容必須先通過寬度檢查

截圖檢視顯示，三欄卡片若同時放入長句、中文、英文識別字與程式碼，容易產生文字擠壓。後續產出必須遵守：

- 完整句子與長說明預設使用單欄卡片。
- 並排卡片只放短標題、短摘要或單一數值，不把多個完整句子硬塞在同一列。
- 需要多欄時使用 `minmax(0, 1fr)`，並對長識別字設定 `overflow-wrap:anywhere`。
- 五個以上流程節點不可在一般桌面寬度硬排成單列，改用上下流程或分組流程。
- 完成 HTML 後，至少檢視一個包含長文字與 `<code>` 的章節截圖。若出現逐字換行、文字重疊、欄位過窄或橫向溢出，必須改成單欄或拆成多個區塊。

## 16. 參考架構圖的資料呈現方式

架構文件若包含 Redis Key，必須把 Key 的格式、每段的業務意義、命中與未命中行為分開呈現，不要只把 Key 放在節點名稱中。建議搭配：

- 一張容器責任圖。
- 一張有編號的執行順序圖。
- 一張資料流或快取分支圖。
- 一張 Key 與資料來源對照表。
- 一個獨立的錯誤路徑區塊。

參考方向可使用 C4 Model、Microsoft Cache Aside Pattern 與 AWS Architecture Reference。文件內應保留來源連結，讓圖示選擇與版面規則具備可追溯性。

## 17. Mermaid 語法採穩定寫法，避免語法衝突

實務上最常見的錯誤是 `Lexical error`，多半來自節點寫法混用造成語法邊界衝突。規則如下：

- 節點一律優先採 `id["label"]`。
- API 路徑要寫成 `B["/api/carts/create"]`，不要用 `B[/api/carts/create]`。
- 節點內避免 `<br/>`，需要補充文字時改短標籤或拆成第二張局部圖。
- 文字過長時先拆圖，不把超長句塞進單一節點。

## 18. 系統導引圖優先雙圖策略，不畫超長單鏈

需要先交代「目前討論點在系統中的位置」時，預設採兩張圖：

1. 系統邊界圖：外部呼叫端、核心系統、支援依賴分層。
2. 局部放大圖：只放本篇主題節點與其內部決策流。

若單張圖節點超過 6 個，或在一般寬度無法完整閱讀，就必須拆圖。完成後要實際開啟輸出文件確認 Mermaid 可正常渲染，且沒有 `Lexical error`。

## 19. Sequence Diagram 必須符合 UML 時序語意

標示為 `Sequence Diagram` 的圖，必須能讀出參與者、生命線、呼叫順序與回傳關係。不要用 CSS Grid 將節點名稱排成彩色方塊矩陣，也不要把所有元件塞成一條只有單向箭頭的長鏈。那種呈現屬於流程圖，不是互動時序圖。

### 必要元素

- 參與者由左至右排列。
- 生命線由參與者向下延伸，通常以垂直虛線表示。
- 時間由上往下。
- 主要呼叫使用水平實線箭頭。
- 回傳結果使用水平虛線箭頭。
- 執行期間可用 activation bar 表示。
- 成功與失敗路徑使用 `alt`、`opt` 或獨立分支框。

### 版面原則

- 參與者欄位固定，不使用會自動換列的排列方式推導時序。
- 箭頭文字要包含方法、協定、資料或條件。
- 節點超過可讀寬度時，拆成多張局部圖。
- 失敗路徑不能只靠紅色節點暗示，必須用文字與分支框說明觸發條件。

### 完成檢查

完成後要確認讀者能回答：誰先發起呼叫、哪個元件正在執行、回傳資料從哪裡來、讀取失敗後會去哪裡、哪個步驟才會保存新的基線。

## 20. 架構圖必須分離不同分析面向

一張架構圖只能回答一個主要問題，不得把元件拓撲、建置流程、環境矩陣、權限策略與執行生命週期全部塞在同一張圖中。產出部署文件時，至少依下列視角拆分：

- **系統邊界圖**：說明外部系統、主要服務、支援服務與資料來源的責任關係。
- **建置或部署流程圖**：說明 source、runner、artifact 與部署動作的先後順序。
- **環境矩陣**：說明 QA、Production、區域與 runner label，優先使用等尺寸表格或卡片，不用節點大小表達重要性。
- **單一主機執行拓撲**：說明 IIS、Windows Service、Task Scheduler、資料來源與通知服務的執行責任。

不同面向不得共用同一套顏色語意。例如紅色若代表 Production，就不能同時代表 Web、錯誤或外部系統。顏色應在同一張圖內只承擔一種語意，環境差異與元件類型應改用分區標題、邊界、標籤或表格表達。

部署目標若屬於同一層級，所有節點必須維持相同尺寸與排列規則。不得讓 `MYPROD`、Production 或任一單一環境因內容較長而被拉伸成大型節點，避免讀者誤以為該環境具有不同的架構責任或優先級。

架構圖優先使用 C4 Container、C4 Deployment 或清楚的分層資料流圖。每一層要有明確標題與邊界，並在圖下方補充閱讀順序，說明哪一層是流程、哪一層是部署目標、哪一層是 runtime 責任。

## 21. 先建立圖面語意契約，再開始排版

產出架構圖前，先列出這張圖唯一要回答的問題，以及每個顏色、形狀、邊界、箭頭與節點尺寸的固定語意。若無法用一句話描述圖面目的，代表內容仍然混合了多個面向，應先拆圖。

- Build flow 只描述 source、runner、artifact 與部署動作。
- Environment matrix 只描述環境、區域、runner label、觸發方式與授權政策。
- Runtime topology 只描述單一目標主機內的 Web、Worker、Task Scheduler、資料來源與通知服務。
- Component boundary 只描述責任範圍與依賴關係，不承擔 Production、QA 或錯誤狀態語意。

顏色在同一張圖內只能代表一個維度。若使用紅色表示 Production，Web、Monitor、錯誤與外部系統不得再共用紅色。若同一份文件需要表達多個維度，應改用分圖、泳道、標題、邊界或表格，不要用更多顏色補救。

同層級節點必須維持相同尺寸與相同內距。長名稱要換行或使用較短的顯示標籤，不能透過放大單一節點解決。環境差異應放在節點內的標籤與表格欄位，不能透過橢圓大小、卡片高度或視覺重量暗示重要性。

HTML 文件若使用自訂 CSS 表達架構圖，先完成語意分層，再建立 class。class 名稱應反映責任，例如 `build-boundary`、`environment-matrix`、`runtime-lane`，不要使用 `red-box`、`big-node` 這類只描述外觀的名稱。完成後至少分別檢視一張長文字章節與一張架構圖截圖。

## 22. 流程圖使用適合流程的視覺呈現

流程圖不應該只是多個並排卡片方格的集合。流程需要讓讀者清楚讀出順序、等待條件、決策分支、失敗出口與完成狀態，請依下列方式選擇版型：

- **垂直時間軸**：適合部署、建置、發布、檢查與回滾等有明確先後順序的流程。
- **泳道**：適合表達 GitHub Actions、self hosted runner、Windows Server、IIS、Worker 與外部服務之間的責任交接。
- **決策閘門**：適合表達等待停止、驗證成功、權限通過、檔案存在等條件，分支要以文字標示 `Yes`、`No` 或實際條件。
- **分層流程**：適合將控制平面、artifact 交接、主機部署與 runtime 驗證分成上下區段。
- **等尺寸矩陣**：只適合表達多個同層級環境或平行部署目標，不用來表示流程順序。

卡片網格只適合獨立概念、依賴摘要、方案比較與短摘要。流程節點若含有完整句子、命令、長路徑或多行說明，預設改用單欄垂直排列。並排區塊只保留給真正的平行分支或兩方比較。若截圖看起來像一堆卡片，而不是能由上到下讀出的流程，必須重新選擇版型。

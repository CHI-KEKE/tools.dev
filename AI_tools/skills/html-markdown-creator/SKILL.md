# HTML + Markdown 側欄式分析文件產生器

## 概觀

產生兩份檔案：一份是有側欄章節導覽的獨立 `.html` 分析文件（左側可點選章節清單，右側一次只顯示被選中的那個章節），另一份是文字內容完全對應的純 `-pure.md` Markdown 版本。兩份檔案內容一致，只是呈現形式不同。

## 工作流程

### 步驟 1：確認情境與素材

先確認這份文件要分析的主題/程式碼/機制是什麼，以及素材來源（既有分析結果、要從程式碼重新探索、或使用者口述的內容）。如果主題本身還不清楚，先完成該主題的分析或探索，再進入撰寫階段。

### 步驟 2：詢問視覺主題

參考 `references/themes-overview.md` 的主題總覽表，依情境基調提案 2-3 個最相關的主題，用 `ask_user` 讓使用者選擇。主題包括 `warm-paper-style`（中性知識型）、`mysql-dolphin-style`（資料庫/後端）、`organic-glass-style`（自然分類）、`cozy-meadow-style`（溫馨生活）、`case-file-style`（風險分級/事件回顧）、`blue-ghost-style`（斑馬線幽靈藍風，可愛詼諧調性）、`harbor-ledger-style`（治理型日誌風）、`system-architecture-style`（系統架構圖風，適合服務／部署／API 拓撲說明）。

### 步驟 3：規劃章節

把內容拆成數個獨立章節（建議 5-10 章），每章聚焦一個面向。章節清單就是側欄導覽的項目，第一章開場必須白話描述情境（見 `references/writing-rules.md` 第 1 條）。

### 步驟 4：組裝側欄骨架

讀取 `assets/sidebar-layout-template.html` 取得完整的 `.doc-shell` / `.doc-sidebar` / `.doc-content` 骨架 HTML/CSS/JS，複製到輸出文件。依規劃的章節數量複製 `.doc-nav-item` 與對應的 `.doc-section`，`data-target` 要對應 section 的 `id`。第一個 nav item 與第一個 section 要帶 `active` class，其餘不要帶。

### 步驟 5：套用選定主題並填入內容

讀取 `assets/themes/` 下選定主題的完整檔案（例如 `assets/themes/warm-paper-style.html`），把該主題檔開頭註解列出的 `--doc-*` 變數值填入骨架的 `:root` 區塊，並把主題檔的 `<style>`（去掉重複的 `:root` 宣告）與元件 HTML 一併複製進輸出文件。每個 `.doc-section` 內部直接套用該主題原本的卡片/區塊 class 撰寫章節內容。

### 步驟 6：架構圖與版面可讀性設計

若文件主題涉及服務、API、快取、資料庫或錯誤追蹤，優先採用業界常見的 C4 Container、C4 Dynamic Diagram 與資料流圖做法：

- 用明確的系統邊界包住同一責任範圍，外部呼叫端、內部容器、支援系統與資料儲存分層呈現。
- 每條箭頭標註協定、API 路徑、資料名稱或命中條件，不使用沒有語意的單色連線。
- 靜態架構圖呈現容器責任，動態流程圖呈現執行順序，錯誤路徑另行標示，不把所有資訊塞進同一張圖。
- 快取流程採 Cache Aside 表達，至少區分查詢、命中、未命中、讀取持久化資料與回填快取。
- 資料庫、快取、外部服務與失敗節點使用一致且有意義的形狀或顏色，不使用裝飾性彩色方塊取代架構語意。
- 開場導引圖優先採「系統邊界圖 + 討論節點放大圖」雙圖策略，不要把完整流程畫成超長單鏈。
- Mermaid 節點優先使用 `id["label"]`；避免 `[/api/path]` 這類易衝突形狀語法與節點內 `<br/>`，降低 `Lexical error` 風險。

版面必須以可讀性優先：

- 長段落、程式碼、Key、API 路徑與長類別名稱不可放在狹窄的並排欄位。
- 含有完整句子的卡片預設採單欄上下排列。只有短標題、短標籤或數值摘要才適合並排。
- `grid` 類卡片若任一欄會容納長文字，預設使用單欄。若確實需要多欄，必須設定合理最小寬度、`minmax(0, 1fr)` 與 `overflow-wrap:anywhere`。
- 流程節點若超過三個，優先改成上下順序或分組後的兩段流程，不讓五個以上節點在一般視窗寬度硬塞同一列。
- HTML 文件完成後必須以瀏覽器或截圖檢視至少一個長文字章節，確認中文、英文、識別字與表格沒有重疊、逐字換行或橫向擠壓。

### 步驟 6.1：Sequence Diagram 必須使用互動時序語意

若章節標示為 `Sequence Diagram`，不得只用 CSS Grid 將元件名稱排成方塊與箭頭。這種呈現屬於流程圖，無法清楚表示參與者之間的呼叫關係。

標準畫法應包含：

- 參與者由左至右排列。
- 每個參與者下方有垂直虛線生命線。
- 時間由上往下流動。
- 呼叫使用水平實線箭頭，回傳使用虛線箭頭。
- 需要表達執行期間時，加入 activation bar。
- 成功與失敗路徑使用 `alt`、`opt` 或明確的分支區塊。
- 每條訊息箭頭都標示方法、協定、資料或分支條件。

若使用純 HTML/CSS 繪製，應以固定參與者欄位與水平訊息線模擬 UML 時序。避免使用會自動換列的 Grid，避免三種顏色的節點交錯排列造成流程誤讀。參與者過多時，拆成成功路徑與錯誤路徑兩張局部圖。

Sequence Diagram 章節至少要補充圖面閱讀方式、成功路徑、失敗路徑與圖例，讓讀者能分辨呼叫、回傳、執行期間與例外處理。

### 步驟 7：撰寫內容並自我檢查

依 `references/writing-rules.md` 的規則撰寫全文，寫完後逐條自我檢查，特別注意：全文不能出現破折號（全形「——」、半形「—」或當破折號用的連字號）、不能用第二人稱「你」、不能用「常見誤解」「一句話理解」這類預設立場或制式導讀語、程式碼與專有名詞要包在 `<code>` 標籤內、圖表節點代號不能直接出現在敘述文字中、長段落舉例／理由說明／開場情境導覽若包含超過 3 個獨立資料點要拆解成卡片、提示框、ERD、表格、清單或收合詳情、清單元件若混排 `<strong>`／`<code>` 不能用 `display:flex` 排版、提示框有多個內容節點時要用單一內容容器包住。若包含 `Sequence Diagram`，另須檢查參與者、生命線、水平訊息箭頭、回傳箭頭與成功／失敗分支是否清楚。可用 PowerShell 或其他文字搜尋確認禁用字詞，並實際檢視渲染結果確認清單、提示框與架構圖排版正常。

另外，若文件包含 Mermaid，必須實際開啟輸出檔確認圖表可被渲染，沒有 `Lexical error`。不接受只看原始碼就結案。

### 步驟 8：輸出純 Markdown 對應版本

以相同章節順序，將 HTML 版本的文字內容（不含 HTML 標籤與樣式）整理成一份純 Markdown 檔案，檔名為 `<主檔名>-pure.md`，與 `.html` 檔放在同一目錄。純 Markdown 版本只是文字內容的對應版本，不需要側欄導覽結構。

### 步驟 9：檔案輸出位置

除非使用者指定其他路徑，兩份檔案都輸出到使用者指定的資料夾；若資料夾不存在則先建立。完成後告知使用者兩份檔案的完整路徑。

## 重要備註

- 輸出的 `.html` 是獨立檔案，不會經過 Hexo 的 pandoc 渲染，因此不受 pandoc 對 `.md` 檔案的特殊限制（例如 div/span 必須同一行、`<pre>` 內不能有空行等）約束，可以正常縮排撰寫 HTML。
- 這些 pandoc 限制只適用於步驟 7 產出的 `-pure.md`（或未來如果要把內容嵌回 Hexo 文章時）。純 Markdown 版本本身內容單純（標題、段落、清單、程式碼區塊），一般不會觸發這些限制，但若使用者要求把內容嵌入既有 Hexo 文章，需另外參考 `hexo-article-creator` 技能的 `references/hexo-conventions.md`。
- 主題檔與側欄骨架的完整內容都放在 `assets/`，動筆前務必實際讀取檔案內容當作抄寫來源，不要憑印象重寫 CSS/HTML，避免樣式跑掉或漏掉細節。

# common-dotnet-testing-generate-unit-tests workflow details

## Prerequisites

### Tech Stack (Dynamic Detection — NEVER Hardcode Versions)

This skill supports the following test framework combination:

| Component | Description |
|-----------|-------------|
| **Test Framework** | xUnit (version detected from test project) |
| **Mock Framework** | NSubstitute (version detected from test project) |
| **Assertion Library** | FluentAssertions (version detected from test project) |
| **Build Tool** | MSBuild (net-framework) or dotnet build (dotnet-cli) |
| **Test Runner** | xunit.console.exe / VSTest.Console.exe (net-framework) or dotnet test (dotnet-cli) |
| **Package Manager** | packages.config + NuGet (net-framework) or SDK-style csproj (dotnet-cli) |

> ⚠️ **MUST**: All package versions MUST be detected from the test project's `packages.config` or `.csproj`.
> **Never assume fixed versions.** Different projects may use NSubstitute 2.x or 5.x, FluentAssertions 4.x or 6.x —
> generated test code must be compatible with the detected versions.

### Platform Detection

Use `repoContext.verificationProfile` to determine:
- `net-framework` → MSBuild build, xunit.console.exe / VSTest.Console.exe test runner
- `dotnet-cli` → `dotnet build` + `dotnet test`

## Execution Flow (4 Steps)

### Step 1: Identify Changes Under Test

Analyze all changed `.cs` files and filter to business logic that needs unit tests:

```powershell
# Get all changed .cs files (uncommitted working tree changes)
git diff --name-only HEAD -- '*.cs'
git diff --cached --name-only HEAD -- '*.cs'
```

**Filter Rules:**

✅ **Include** (generate tests):
- Service classes under `BLV2/` (core business logic layer)
- Service classes under `BL/`
- Processors / Handlers / Helpers with significant business logic
- New or modified public methods (exclude format-only / comment-only changes)

❌ **Exclude** (do not generate tests):
- `*Entity.cs`, `*Dto.cs`, `*ViewModel.cs` (data structures)
- `*Config*.cs`, `*Constant*.cs` (configuration / constants)
- `*Migration*.cs` (database migrations)
- `*AutoGenerated*`, `*.Designer.cs` (auto-generated)
- Test projects themselves (`*.Test*` directories)
- Methods that already have corresponding tests (optional check)

**Output**: Target list `List<(FilePath, ClassName, MethodName)>`

### Step 2: Locate Test Project & Analyze Dependencies

For each target Service class:

1. **Locate the corresponding test project**:
   - Follow naming conventions: `{ProjectName}.Test.Xunit` > `{ProjectName}.Test` > nearest test project
   - Common mappings:
     - `BLV2/SomeService.cs` → `BLV2.Test.Xunit/` or `BLV2.Test/`
     - `WebAPI/SomeController.cs` → `WebAPI.Test.Xunit/`

2. **Detect test project package versions** (⚠️ Critical step — MUST NOT skip):

   **packages.config projects** (.NET Framework):
   ```xml
   <!-- Read packages.config to extract actual versions -->
   <package id="xunit" version="2.4.0" />
   <package id="NSubstitute" version="2.0.3" />
   <package id="FluentAssertions" version="4.19.4" />
   ```

   **SDK-style csproj projects** (.NET Core):
   ```xml
   <!-- Read .csproj to extract PackageReference versions -->
   <PackageReference Include="xunit" Version="2.9.3" />
   <PackageReference Include="NSubstitute" Version="5.3.0" />
   <PackageReference Include="FluentAssertions" Version="6.12.0" />
   ```

   **Required detection results** (store in `testProjectContext`):

   | Field | Description | Example |
   |-------|-------------|---------|
   | `xunitVersion` | xUnit major version | `2` |
   | `nsubstituteVersion` | NSubstitute major version | `2` or `5` |
   | `fluentAssertionsVersion` | FluentAssertions major version | `4` or `6` |
   | `packageManager` | Package management style | `packages.config` or `PackageReference` |

   **Version differences that affect code generation**:

   | Package | Lower versions (common in .NET Framework) | Higher versions (common in .NET Core) |
   |---------|-------------------------------------------|---------------------------------------|
   | NSubstitute ≤ 3.x | `using NSubstitute.ExceptionExtensions;` required | Same, but richer API |
   | NSubstitute ≥ 4.x | — | Supports `Arg.Do<T>()`, `Configure()`, etc. |
   | FluentAssertions ≤ 5.x | `using FluentAssertions;` | — |
   | FluentAssertions ≥ 6.x | — | Same namespace, enhanced API |

3. **Analyze target methods**:
   - Read the full source code of the Service class
   - Extract: constructor (injected dependencies), target method signatures, method body logic
   - Identify: conditional branches (if/else/switch), exception handling, return types

4. **Check for existing test files**:
   - If `{ServiceName}Tests.cs` already exists, add new methods to it (avoid duplicate classes)
   - If it does not exist, create a new test file

### Step 3: Generate Test Code

Follow these conventions when generating tests:

#### Naming Conventions

```text
Test class:  {ServiceName}Tests
Test method: {MethodName}_{Scenario}_{ExpectedBehavior}
```

- Scenario and expected behavior use **Traditional Chinese (zh-TW)** for test report readability
- Use `[Trait("Category", nameof(Service.Method))]` for categorization

#### Test Structure（AAA Pattern）

```csharp
using System;
using System.Collections.Generic;
using FluentAssertions;
using NSubstitute;
using NSubstitute.ExceptionExtensions;
using NSubstitute.ReturnsExtensions;
using Xunit;

namespace {TestProjectNamespace}.{SubFolder}
{
    public class {ServiceName}Tests
    {
        //// 依賴的 Mock 物件
        private readonly ISomeDependency _someDependency;
        private readonly IAnotherDependency _anotherDependency;

        public {ServiceName}Tests()
        {
            //// Arrange — 建立所有 Mock 依賴
            this._someDependency = Substitute.For<ISomeDependency>();
            this._anotherDependency = Substitute.For<IAnotherDependency>();
        }

        [Fact]
        [Trait("Category", nameof({ServiceName}.{MethodName}))]
        public void {MethodName}_正常輸入_應回傳預期結果()
        {
            // Arrange
            var sut = this.GetSystemUnderTest();
            this._someDependency.GetData(Arg.Any<int>())
                .Returns(expectedData);

            // Act
            var actual = sut.{MethodName}(input);

            // Assert
            actual.Should().NotBeNull();
            actual.SomeProperty.Should().Be(expectedValue);
        }

        [Fact]
        [Trait("Category", nameof({ServiceName}.{MethodName}))]
        public void {MethodName}_輸入null_應拋出ArgumentNullException()
        {
            // Arrange
            var sut = this.GetSystemUnderTest();

            // Act
            Action act = () => sut.{MethodName}(null);

            // Assert
            act.Should().Throw<ArgumentNullException>();
        }

        /// <summary>
        /// 建立待測系統實例
        /// </summary>
        private {ServiceName} GetSystemUnderTest()
        {
            return new {ServiceName}(
                this._someDependency,
                this._anotherDependency);
        }
    }
}
```

#### Required Scenarios

Each target method must have at least the following tests (adjust based on method logic):

| Type | Description | Priority |
|------|-------------|----------|
| **Happy path** | Valid input → expected output | P0 (required) |
| **Null/empty handling** | null input → exception or default return | P0 (required) |
| **Conditional branches** | Each if/else/switch branch | P1 (important) |
| **Exception scenarios** | Dependency throws exception | P1 (important) |
| **Boundary values** | 0, empty collection, max values, etc. | P2 (recommended) |

#### Async and concurrency testing principles
- async unit test:
    - ✅ Match the test style to the target repository and SUT contract:
        - If SUT is synchronous, write synchronous tests by default.
        - If SUT is asynchronous (`Task`/`Task<T>`/`ValueTask`), use `async`/`await` for tests that execute those async paths.
        - Do not force every test in the same class to be async if a specific test scenario is purely synchronous.
    - ✅ For multi-repo usage (both .NET Framework and .NET/Core), follow the project’s actual async model instead of forcing one style globally.
    - ❌ Do not introduce async wrappers or `Task.Run` in tests just to make synchronous code look async.
    - ❌ Do not use fire-and-forget in tests (for example, calling async methods without `await`).
- race condition test:
    - ✅ Add race/concurrency tests only when there is shared state, parallel side effects, or explicit idempotency requirements.
    - ✅ Proactively evaluate concurrency tests when shared state exists (e.g., static state, singleton state, in-memory cache, dedup/retry paths), even if the main business flow looks deterministic.
    - ❌ Simply testing an async repository/API method with `await` does not automatically require a race condition test.
    - ❌ If the scenario is deterministic single-thread business flow, do not add concurrency tests by default.

# Shared Static State Isolation for Unit Tests

* Treat all mutable `static` state as shared process-wide test state, including static helpers, caches, config holders, context accessors, dictionaries, lists, country/market/tenant/culture/timezone settings, and feature flags.
* Any test that depends on mutable static state must explicitly set the required value in Arrange and restore the original value after the test.
* Restore must be guaranteed by `try/finally`, `IDisposable` scope, `IAsyncDisposable`, or an equivalent cleanup mechanism.
* Prefer reusable scoped helpers when changing static state, so each test can automatically restore the original value without duplicating cleanup logic.
* Constructor, `IClassFixture`, and `CollectionFixture` can prepare default test setup, but they cannot replace per-test setup and restore for mutable static state.
* Do not rely on current CI execution order, single-thread execution, or test runner behavior. Tests must be deterministic under both sequential and parallel execution.
* When multiple tests mutate the same static resource, place all related test classes in the same xUnit Collection using the exact same collection name.
* xUnit Collection serialization is required for shared static mutation, but it does not replace per-test setup and restore.
* For multi-market, multi-country, tenant, culture, timezone, or feature-flag scenarios, prefer `Theory`; each data row must isolate its own setup and restore.
* For new or safely refactorable code, prefer replacing static dependencies with DI seams. For legacy code, keep static usage but enforce strict setup and restore.
* If the static value cannot be restored through a public API, use an existing reset API, test-only reset mechanism, or scoped reflection fallback, and keep cleanup in `finally`, `Dispose`, or equivalent cleanup logic.
* Never generate tests that depend on execution order, previous test side effects, or un-restored static state.

#### FluentAssertions Common Assertions

```csharp
result.Should().NotBeNull();
result.Should().Be(expected);
result.Should().BeEquivalentTo(expected);
result.Should().BeEmpty();
result.Should().HaveCount(3);
result.Should().Contain(x => x.Id == 1);
action.Should().Throw<SomeException>();

//// Boolean comparison — per repo convention, use == false
result.IsValid.Should().Be(false);   // ✅ Matches repo convention
result.IsValid.Should().BeFalse();   // ✅ FluentAssertions style (also acceptable)
```

#### NSubstitute Common Patterns (adjust based on detected version)

```csharp
//// Create mock
var mock = Substitute.For<IService>();

//// Set return value
mock.GetData(Arg.Any<int>()).Returns(expectedData);
mock.GetDataAsync(Arg.Any<int>()).Returns(Task.FromResult(expectedData));

//// Set null return (requires using NSubstitute.ReturnsExtensions;)
mock.GetData(Arg.Any<int>()).ReturnsNull();

//// Set exception throw (requires using NSubstitute.ExceptionExtensions;)
mock.GetData(Arg.Any<int>()).Throws(new Exception("error"));

//// Verify calls
mock.Received(1).GetData(Arg.Any<int>());
mock.DidNotReceive().Delete(Arg.Any<int>());

//// ⚠️ The following APIs are ONLY available in NSubstitute ≥ 4.x:
//// - Arg.Do<T>(), Configure(), When().Do(), etc.
//// If testProjectContext.nsubstituteVersion < 4, do NOT use these APIs.
```

### Step 4: Compile Verification

Select the appropriate build method based on `repoContext.verificationProfile`:

#### .NET Framework (net-framework profile)

```powershell
# Use cached paths from repoContext
& "$($repoContext.msbuildPath)" `
    "$testProjectPath" `
    /t:Build `
    /p:Configuration=Debug `
    /verbosity:minimal `
    /nologo
```

On build failure: analyze error → fix generated test code → rebuild (max 3 attempts)

#### .NET Core (dotnet-cli profile)

```powershell
dotnet build "$testProjectPath" --configuration Debug --verbosity minimal --nologo
```

On build failure: analyze error → fix generated test code → rebuild (max 3 attempts)

#### Common Build Failures & Fixes

| Error | Common Cause | Auto-Fix Strategy |
|-------|-------------|-------------------|
| CS0246 | Missing using directive | Add corresponding namespace |
| CS1061 | Method/property not found | Check method signature, fix name |
| CS0029 | Type mismatch | Fix Assert or Returns type |
| CS0103 | Undefined variable | Add to Arrange section |

## Behavioral Rules

**DO:**
- Follow existing test project code style (reference tests under `BLV2.Test.Xunit/`)
- Use `this.GetSystemUnderTest()` to create SUT instances
- Use `[Trait("Category", nameof(...))]` for test categorization
- Use `////` inline comments to explain complex logic
- Ensure all generated tests compile successfully

**DON'T:**
- NEVER modify production code (generate test code only)
- NEVER assume package versions — MUST detect from `packages.config` or `.csproj`
- NEVER use APIs beyond the detected version (e.g., NSubstitute 2.x cannot use `Arg.Do<T>()`)
- NEVER generate code that fails to compile (if build fails, fix before outputting)
- NEVER generate tests for Entity/DTO/ViewModel classes

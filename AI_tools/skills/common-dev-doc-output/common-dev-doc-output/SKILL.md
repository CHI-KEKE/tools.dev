# Nine1 Dev Doc Output

產生 `nine1-implement-flow` 開發循環中的兩種強制 Markdown 文件，並以瀏覽器開啟請使用者確認。

## 何時使用

| 時機 | 文件類型 | 用途 |
|------|----------|------|
| Review Approved → 進入 Implementation 之前 | `dev-plan` | 讓使用者確認開發計畫後才允許實作 |
| Implementation 完成 → 進入 Close 結案之前 | `dev-complete` | 讓使用者確認交付內容後才允許結案 |

## 命名規則

```
docs/dev-plan-{任務名稱}-{YYYYMMDD}.md
docs/dev-complete-{任務名稱}-{YYYYMMDD}.md
```

- 任務名稱：取需求或功能的英文 kebab-case 短名，例如 `coupon-batch-issue`
- 日期：當天日期，格式 `YYYYMMDD`

---

## Procedure A：產生 dev-plan（開發計畫文件）

### 步驟

1. **收集必要資訊**（從當前對話 context 萃取，不足時向使用者補問）：
   - 任務名稱
   - VSTS 單號（若有）
   - 需求摘要
   - 實作範圍（In Scope）
   - 排除範圍（Out of Scope）
   - 逐步執行計畫（含各步驟的成功條件）
   - 已識別風險與緩解方式
   - 預計驗證命令（build / test / run）

2. **套用 dev-plan 模板**（見下方），填入收集到的資訊。

3. **建立目錄與寫出檔案**：
   - 確認 `docs/` 目錄存在（若不存在則建立）
   - 寫出 `docs/dev-plan-{name}-{date}.md`

4. **以瀏覽器開啟該檔案**。

5. **輸出等待確認訊息**：
   > 📄 開發計畫已產生：`docs/dev-plan-{name}-{date}.md`
   > 請確認以上開發計畫，**是否開始實作？**（回覆「確認」後才會開始修改程式碼）

6. **等待使用者明確回覆**，收到確認前禁止進入 Implementation。

## Procedure B：產生 dev-complete（完成說明書）

### 步驟

1. **收集必要資訊**（從 Implementation 執行結果萃取）：
   - 任務名稱（與 dev-plan 一致）
   - VSTS 單號（若有）與同步狀態
   - 已交付功能摘要
   - 修改的檔案清單與各檔案的變更重點
   - 已執行驗證項目與結果（Pass / Failed / Partial）
   - API 測試腳本路徑（若為 API 專案）
   - 剩餘風險
   - 建議後續行動

2. **套用 dev-complete 模板**（見下方），填入收集到的資訊。

3. **寫出檔案**：
   - 寫出 `docs/dev-complete-{name}-{date}.md`

4. **以瀏覽器開啟該檔案**。

5. **輸出等待確認訊息**：
   > 📄 開發完成說明書已產生：`docs/dev-complete-{name}-{date}.md`
   > 請確認以上開發完成內容，**是否無誤？**（確認後正式結案）

6. **等待使用者明確回覆**，收到確認前禁止宣告結案。

## 重要規則

- **禁止**在文件寫出前就宣告進入下一階段。
- **禁止**在使用者確認前就開始實作或結案。
- 若使用者不確認或要求修改，依其反饋修正計畫後重新產生文件。
- 文件必須寫到 `docs/` 資料夾；若 workspace 沒有 `docs/` 目錄則先建立。
- 日期使用當天實際日期（格式 `YYYYMMDD`）。

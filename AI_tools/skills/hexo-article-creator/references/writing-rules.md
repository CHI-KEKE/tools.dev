# 撰寫規範（來自與 Allen 多次文章優化的討論結論）

這些規範是強制性的寫作準則，每次撰寫或優化 Hexo 文章都要套用，不需要每次重新詢問。

## 1. 開場要白話好懂，不用分受眾

文章開場（通常是第一個 tab／第一段）**必須用白話描述情境**，讓完全不熟悉這個主題的人也能懂大致狀況。
- 不要一開始就丟一堆專有名詞、系統元件名稱、狀態碼
- 不需要區分「給工程師看」還是「給主管看」兩個版本——白話開場對所有讀者都適用，細節留給後面段落展開
- 錯誤示範：「當 PaymentMiddleWareRefundRequestGrouping 觸發 RefundRequestFinishJob 後...」
- 正確示範：「退款卡住的原因主要有兩種：一種是商家錢包餘額不夠，另一種是資料庫查詢逾時。」

## 2. 視覺風格要主動討論，不要自己猜

寫作前，針對「風格方向」與「文章情境／主題」一起問清楚（可合併成同一輪的多個問題），而不是先做一版再被打回票。至少要確認：
- 這篇文章的情境／主題是什麼？（例如：金流異常分析、架構設計、事件回顧）→ 決定配色語意基調（見第 4 點）
- 想要偏向哪種視覺方向？可以給 2-3 個具體風格提案讓對方選，或詢問是否有心中已有的畫面（例如「病歷表」「終端機」「儀表板卡片」）
- 是否需要客製 HTML/CSS，還是用 Hexo 內建 `{% note %}` 等 tag 就足夠

## 3. 風格定調後，全文保持一致

一旦決定了視覺語言（配色、字體、卡片樣式），**同一篇文章的所有段落都要延續同一套視覺系統**，不要每個 tab 各自發明新樣式。
- 共用的 CSS 只在第一個 tab 定義一次（渲染引擎會讓全文共用）
- 新增元件（時間軸、決策卡片、對照表）時，配色與圓角、陰影、字體都要沿用已定調的變數／色票
- 可參考 `assets/components/` 內建立好的元件範例，依情境調整內容，但不要改變色系與字體基調

## 4. 關鍵字與配色要配合情境語意

不要用「好看/好記」當唯一標準，要讓顏色本身傳達語意，並在全文保持一致的對應關係：
- 紅／磚紅色系：需要立即關注的危險、失敗、根因
- 琥珀／橘色系：待觀察、Pending、警示但非致命
- 綠色系：已解決、成功、結案
- 中性色（墨綠、藍灰）：一般資訊性節點、流程步驟

決定配色前，先確認文章情境（例如金流錯誤分析適合暖色警示系統；架構設計文可能更適合冷色專業感），再套用上述語意慣例。

例外：若文章情境屬於品牌／自然／生態／永續／科普類的裝飾性介紹（非事件回顧、非故障排查），可改用 `organic-glass-style.html` 的自然色階（綠/棕/沙金），此時配色代表「自然分類」而非風險程度，不需要套用紅/琥珀/綠的危險語意。若文章情境是輕鬆詼諧、生活隨筆、新手導覽類（非事件回顧、非故障排查），可改用 `blue-ghost-style.html` 的天空藍/珊瑚橙色階，同樣是「可愛分類」裝飾語意而非風險程度。

## 5. 程式碼與專業術語要用 `<code>` 或 markdown code span 包起來

行文中提到的類別名稱、方法名稱、狀態碼、欄位名稱、SQL/程式片段關鍵字，一律用 `` `code` `` （純 Markdown 段落）或 `<code>...</code>`（HTML 段落內）包起來，不要用**粗體**或裸露文字表示。

## 6. 情境分支要畫清楚，流程圖不要只畫一條龍

遇到程式邏輯有多個分支（if/else、switch、狀態機），**必須保留文章範圍內有證據的分支**，不能只畫「最常見的那條路徑」；未知處標待確認，不補造成功或錯誤路徑。
- 用 mermaid flowchart 的 `-->|"條件文字"|` 標示每個分岔的判斷條件
- 如果一張圖過於複雜（超過 15-20 個節點），拆成多張圖，各自聚焦一個決策層級（例如：入口分派 → 內部判斷 → 結果分派）
- 程式分析圖附上必要的來源對照；只有已知時才列檔案與行號，不為了填表編造證據。

## 7. 文案敘述不要用節點代號，要用看得懂的白話描述

mermaid 圖表節點內部可以用 `A/B1/D2` 這種座標式代號（圖表語法需要），**但圖表以外的說明文字（提示框、表格說明、段落描述）一律要用白話描述該節點的實際意義**，不能直接引用代號。
- 錯誤示範：「C1、D1 兩條路徑 refund 都只是本地組出來的假回應」
- 正確示範：「『RefundQuery 查詢本身就失敗』與『狀態不是已結算』這兩條路徑，refund 都只是本地端自己組出來的假回應」

## 8. 套用卡片/元件模板時，不要為了填滿欄位而硬拆標題

`assets/components/` 內的卡片模板（如 stage-card 的 `stage-tag` + `stage-name` 雙欄位）是設計給「固定格式短標籤 + 完整標題」的組合使用，**`stage-tag` 只能放真正獨立的簡短標記**（例如 `STEP 1`、`STAGE 2`、`STEP 1-2` 這種序號/階段編號），**不能把一個完整標題硬生生攔腰砍成兩段去湊兩個欄位**。

- 判斷方法：先看這個標題本身是否「天生」帶有一個獨立的短標籤（像 STEP N）。如果沒有，就不要發明一個假的標籤，直接把完整標題放進 `stage-name`，省略 `stage-tag`（或整個 span 不寫）。
- 錯誤示範：標題「為什麼是 70 種？」被拆成 `<span class="stage-tag">為什麼</span><span class="stage-name">是 70 種？</span>`，導致視覺上斷成兩截、語意不連貫。
- 錯誤示範：標題「排列 vs 組合」被拆成 `<span class="stage-tag">排列 vs</span><span class="stage-name">組合</span>`。
- 正確示範：沒有天然短標籤時，直接 `<div class="stage-head"><span class="stage-name">為什麼是 70 種？</span></div>`。
- 正確示範：有天然短標籤時，`<div class="stage-head"><span class="stage-tag">STEP 1</span><span class="stage-name">提出零假設</span></div>`。
- 套用任何雙欄位／多欄位的卡片元件前，都要用這個原則自我檢查：每個欄位放進去的內容，單獨拿出來看是否仍然是一句完整、有意義的文字，而不是一個句子被硬切的殘句。

## 9. 文字內容一律不准使用破折號

全文（包含一般段落、卡片描述、提示框文字、標題）都**不准使用破折號**，不管是全形破折號「——」、單一個「—」，還是用來充當破折號語氣的半形連字號「-」（例如「白話開場對所有讀者都適用-細節留給後面段落展開」這種寫法也不行）。
- 需要語氣停頓、補充說明時，改用句號、逗號分句，或另外拆成新的一句話。
- 需要條列對比或並列項目時，改用頓號、分號，或直接拆成項目符號列表。
- 錯誤示範：「白話開場對所有讀者都適用——細節留給後面段落展開」
- 正確示範：「白話開場對所有讀者都適用，細節留給後面段落展開。」
- 錯誤示範：「不要發明一個假的標籤——直接把完整標題放進 `stage-name`」
- 正確示範：「不要發明一個假的標籤，直接把完整標題放進 `stage-name`」
- 這條規則不需要每次跟使用者確認，屬於強制套用的規範；完成後自我檢查時要額外掃一次全文有沒有殘留「——」或語意上被當破折號使用的「-」。

## 10. 長段落舉例、理由說明、開場情境導覽要拆解成多種呈現方式，不要擠成一整段文字

當一段說明包含多個實體（例如兩個各自獨立的資料列）、多個對照數字（例如多個 SkuId／庫存/結果）、多種分支結果、多個各自獨立的理由/論點、或是**開場情境導覽包含多種商業玩法與架構矛盾**時，**不要把所有細節塞進同一個 `<p>` 或 Hero 的 `hh-desc` 大段落中**，改用以下幾種方式依內容形態拆解，通常會同時搭配 2 種以上：

- **開場 Hero（`hh-desc`）精簡化 + 結構化拆解**：開場 Hero 的 `hh-desc` 應控制在 2～3 句俐落的引言（聚焦核心挑戰與文章主旨）。若開場涉及多種商業玩法（如組合商品 vs 加價購），應將玩法拆解為**並排卡片（`hl-card-grid`）**；若涉及「業務特徵 vs 底層資料結構限制」的矛盾與解法，應拆解為**結構化對照清單或提示框（`hl-callout` + `hl-checklist`）**，嚴禁把情境、例子、特徵、資料庫限制、解法全部擠在 `hh-desc` 裡。
- **小型關聯圖（`hl-erd` 或同類 ERD 元件）**：呈現「誰跟誰透過哪個欄位關聯」，取代用文字描述「A 透過某欄位指向 B」。
- **卡片式並排對照（`hl-card-grid` 或同類卡片元件）**：兩個或多個彼此獨立的實體（例如主件 vs 贈品、方案 A vs 方案 B、玩法一 vs 玩法二），各自一張卡片列出關鍵欄位或情境，取代用分號串接成一長句。
- **表格化明細（`hl-table` 或同類表格元件）**：多筆資料列的欄位對照（例如多個 SkuId 各自的規格／庫存／來源），用表格取代文字列舉。
- **結果分支清單（`hl-checklist` 或同類清單元件）**：多種輸入對應多種輸出結果（例如「帶 A 會成功／帶 B 會被擋下／帶 C 會被擋下」），拆成清單每行一種情境，取代擠在一句話裡的多個分號子句。
- **理由/論點清單（`hl-checklist` 或無序清單）**：說明「為什麼這樣設計」「為什麼不這樣做」這類論述時，如果背後有兩個以上各自獨立的理由，先用一句話點出結論或問題，再逐條列出每個理由，每條理由聚焦一個角度，不要把所有理由寫成一串用逗號、句號連接的長句。
- **展開/收合詳情（`details.ml-detail` 或同類漸進式揭露元件）**：補充說明或次要細節（例如關聯欄位的底層邏輯）預設收合，避免預設畫面就是一大段文字，需要時才展開。

判斷方法：先數一數這段文字裡有幾個「獨立的資料點」（實體、欄位、數字、結果、理由/論點、商業玩法），如果超過 3 個以上還擠在同一句話或同一段落，就要挑選上述至少一種方式拆解；套用哪一種要看內容形態（開場玩法用卡片、架構矛盾用提示清單、關聯用 ERD、並列實體用卡片、多筆列表用表格、多種結果用清單、多個理由用條列清單、次要細節用收合），不是固定公式，也可以視內容複雜度同時套用多種。

## 11. 敘述不用第二人稱「你」，改用去人稱的客觀敘述

全文（一般段落、Hero 開場敘述、卡片/提示框描述）**一律不使用「你」這種第二人稱視角**，改成客觀、去人稱的敘述方式，讓文字讀起來像在描述一個情境或事實，而不是對讀者本人說話。
- 需要表達「使用者的動作」時，把主詞去掉直接描述動作或情境本身，或改成情境化的主詞（例如「使用者」「程式」「系統」），不要用「你」。
- 錯誤示範：「所以你會在工作管理員看到 `Memory 13.8 / 16 GB`」
- 正確示範：「所以會在工作管理員看到 `Memory 13.8 / 16 GB`」
- 錯誤示範：「如果你正在編輯一份還沒儲存的文件」
- 正確示範：「假設正在編輯一份還沒儲存的文件」
- 錯誤示範：「它只是告訴你要找哪個地方」
- 正確示範：「它只是標示出要找的地方」
- 這條規則不需要每次跟使用者確認，屬於強制套用的規範；完成後自我檢查時要額外掃一次全文有沒有殘留「你」字。

## 12. 禁止使用預設立場、替讀者下判斷的用詞

全文（一般段落、callout、卡片描述）**禁止使用任何預先替讀者認知下判斷、暗示「多數人本來就這樣以為/誤解」的字眼**，例如「很多人都以為」「常見誤解」「一般人以為」「大家常常誤會」「你可能會以為」「普遍的迷思」之類的開頭語。這類用詞是在替讀者的既有認知打分數，容易顯得說教或預設讀者無知，也不是每次都成立的事實陳述。
- 需要指出一個容易被忽略、跟直覺不同的地方時，直接描述事實本身或情境本身，不要先扣一頂「大家都誤會」的帽子。
- 錯誤示範：「常見誤解：即使整段邏輯用 `BEGIN` 與 `COMMIT` 包起來，也不代表兩筆轉帳彼此不會互相干擾。」
- 正確示範：「即使整段邏輯用 `BEGIN` 與 `COMMIT` 包起來，也不代表兩筆轉帳彼此不會互相干擾。」
- 錯誤示範：「很多人都以為 NoSQL 完全沒有 transaction。」
- 正確示範：「NoSQL 沒有 transaction，這個說法已經不成立。」
- 這條規則不需要每次跟使用者確認，屬於強制套用的規範；完成後自我檢查時要額外掃一次全文有沒有殘留「很多人都以為」「常見誤解」「一般人以為」「你可能會以為」等預設立場的開頭語，若有就要拿掉，直接改成描述事實或情境本身。

## 13. 不要用「一句話理解」「簡單來說」這類制式導讀語


段落或 callout 要收斂成摘要、比喻時，不要加「一句話理解」「簡單來說」「白話一點說」這類制式導讀語當開頭，直接描述比喻或摘要本身即可。
- 錯誤示範：「一句話理解：可以把這張表想像成一疊分組貼紙。」
- 正確示範：「貼紙比喻：可以把這張表想像成一疊分組貼紙。」（或直接省略前綴，只留比喻本身）
- 這條規則不需要每次跟使用者確認，完成後自我檢查時要額外掃一次全文有沒有殘留「一句話理解」「簡單來說」「白話一點說」等制式導讀語。

## 14. Sequence Diagram 必須符合 UML 時序語意

若文章使用 `Sequence Diagram` 描述服務互動，必須採用 UML 時序語意。參與者由左至右排列，生命線垂直向下延伸，時間由上往下流動，呼叫使用水平實線箭頭，回傳使用虛線箭頭。成功與失敗路徑使用 `alt`、`opt` 或獨立分支框清楚區隔，不使用 CSS Grid 方塊交錯排列或單一路徑長鏈取代互動時序。

## 15. 架構圖先分離分析面向，再選擇圖形

一張架構圖只能回答一個主要問題。不要把元件責任、建置流程、部署環境、授權政策與 runtime 拓撲全部塞進同一張圖。技術文章至少依下列視角分開：

- **系統邊界圖**：說明外部呼叫端、主要服務、支援服務與資料來源的責任關係。
- **建置或部署流程圖**：說明 source、runner、artifact 與部署動作的順序。
- **環境矩陣**：說明環境名稱、區域、runner label、觸發方式與授權條件，優先使用等尺寸表格或卡片。
- **單一主機 runtime 拓撲**：說明 Web、Windows Service、Task Scheduler、資料來源與通知服務在一台主機上的責任。

不同分析面向不得共用同一套顏色語意。若紅色代表 Production，就不能同時代表 Web、錯誤或外部系統。元件類型應使用邊界、標題、形狀或中性色表達，環境政策應使用獨立卡片或表格表達。

同層級的環境或部署目標必須使用相同尺寸、相同排列規則與相同資訊層級。不得讓某個 Production 環境因名稱較長或內容較多而被畫成大型節點，避免讀者誤判其架構責任或優先級。

部署與拓撲文章優先使用 C4 Container、C4 Deployment、泳道、分層資料流或矩陣表格。每張圖都要有明確標題，圖下方補充閱讀順序與圖形語意。若同一張圖需要同時放入流程、環境與 runtime，應先拆成多張局部圖，再用文字說明彼此關係。

## 16. 流程使用流程視覺，不要把每一步都畫成卡片

流程圖的主要任務是讓讀者讀出先後順序、等待條件、分支與完成狀態。流程內容不得預設套用並排卡片網格。依流程形態選擇視覺：

- 有明確先後順序的部署、建置或操作流程，優先使用垂直時間軸、編號步驟線或上下分段流程。
- 有不同責任範圍的流程，使用泳道或分層邊界區分 GitHub Actions、self hosted runner、Windows Server、IIS 與外部服務。
- 有成功與失敗條件的流程，使用決策閘門、分支區塊或條件標籤，不能只靠紅綠色卡片暗示分支。
- 有多個平行部署目標的流程，使用等尺寸環境矩陣或平行泳道，不要把每個環境畫成不同大小的節點。
- 只有彼此獨立的概念、依賴類別、方案比較或摘要資訊才適合使用卡片網格。

流程節點若包含完整句子、長路徑、命令或多行說明，預設採單欄垂直排列。並排區塊只保留給真正的平行分支、兩方比較或短摘要。完成後要檢查圖面是否能從上到下讀出流程，若讀者需要在多個方格之間猜箭頭方向，必須改成時間軸、泳道或決策圖。


## 17. 圖表選用與證據邊界

圖型與層級選用以 [圖表選用與表達規範](diagram-selection.md) 為準，範例見 [圖表範例](diagram-examples.md)。State Diagram 不預設改成 flowchart，ERD 不等於 Class Diagram，C4 Container 不等於 Docker container。所有圖的關係、順序、分支與數值都需有來源；示範、提案與實際實作必須區分。

## 18. 不加入與文章內容無關的詞句

正文、圖說、卡片與提示框只保留能幫助理解文章主題的資訊，不加入版面操作提示、製作過程說明或交付驗證紀錄。例如「窄螢幕可左右捲動。」「手機版請橫向滑動」「為控制圖寬」「已完成響應式排版」不應出現在一般技術文章內容中。這類製作與驗證資訊需要交代時，放在交付回覆。

- 圖說保留圖例、箭頭語意、資料範圍與證據限制等有助理解內容的說明。
- 捲動、響應式樣式、鍵盤操作與必要的無障礙標籤仍應正常運作；移除提示文字不等於移除功能。
- 若文章主題本身就是介紹介面操作、響應式設計或驗證流程，相關敘述屬於主題內容，可以保留；有意義的按鈕與展開標籤也不屬於多餘詞句。
- 完成後掃描全文與對應純文字版，移除同類無關詞句，不只搜尋上述固定範例。

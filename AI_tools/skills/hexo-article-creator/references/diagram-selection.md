# 圖表選用與表達規範

此文件處理「選哪一種圖、畫到哪一層、圖中能宣稱什麼」。先讀本文件，再按所選類型讀 [圖表範例](diagram-examples.md) 對應段落。無須每篇文章放入所有圖形。

## 1. 先定義問題與證據

動筆前，用一句話寫下這張圖要回答的問題，再確認範圍、來源與讀者需要看見的關係。不同視角分圖；已存在且能清楚回答問題的圖可以保留，不因它是 Mermaid 就跳過可讀性檢查。

- 圖的節點、連線、順序、分支、基數及部署實例數，必須能對應提供的程式碼、設定、schema、trace 或需求。
- 區分「目前實作」「觀察到的單次事件」「設計提案」；推測與待確認處用文字註記，不畫成已證實的路徑。
- 只畫與本文問題有關、已知的成功與錯誤分支。沒有證據，不補造 HTTP 狀態碼、回傳包裝、佇列 ACK、重試次數、逾時秒數、資料回填或補償行為。
- 未知處不代表必須停止工作。先完成已知部分，列出會影響結論的缺口；圖下注明省略範圍與證據限制。
- 程式分析文章可附精簡的元件／來源對照表；沒有原始碼行號時提供已知來源，不編造檔案路徑或行號。

## 2. 選圖對照表

| 核心問題 | 優先選用 | 不適合拿來替代的內容 |
| --- | --- | --- |
| 系統服務誰、與哪些外部系統互動？ | 系統情境／邊界圖 | 內部方法執行順序 |
| 軟體由哪些應用程式與資料儲存組成？ | C4 Container 視圖 | Docker 實例與主機分布 |
| 單一應用程式內有哪些責任元件？ | Component／元件關係圖 | 全部類別與每次方法呼叫 |
| 一次請求由誰呼叫誰、回傳什麼？ | Sequence Diagram | 物理部署位置 |
| 條件成立或不成立後各走哪條路？ | Flowchart／決策流程圖 | 狀態本身的生命週期 |
| 工作如何跨角色或系統交接？ | 泳道圖 | 嚴格的訊息時序細節 |
| 資料從哪裡來、怎麼轉換、寫到哪裡？ | 資料流圖 | 把所有箭頭都當成同步呼叫 |
| 訂單、任務、付款有哪些狀態轉換？ | State Diagram | 一次執行的 log 時間順序 |
| 實體之間如何關聯、是否必須存在？ | ERD | API 呼叫或物件繼承 |
| 類別或介面如何實作、依賴、組合？ | Class Diagram | 資料庫 FK 與資料基數 |
| 服務實例在哪些主機／區域執行？ | Deployment／runtime 拓撲圖 | source 到 artifact 的建置流程 |
| 原始碼如何變成產物並部署？ | 建置流程圖／泳道圖 | 部署完成後的 runtime 網路 |
| 事故在什麼時間發生哪些事件？ | 事件時間軸／時間表 | 狀態機或未證實的因果鏈 |
| 各環境、設定或方案有哪些差異？ | 矩陣表格 | 有先後順序的流程 |

短清單或兩句話已能解釋的內容，不必加圖。卡片網格用於獨立概念、方案與摘要，不能拿來代替順序、分支、交接或時序。

## 3. 結構視角：邊界、Container、Component

- **系統情境**：一個核心系統、相關使用者及外部系統，連線寫明互動目的。
- **Container**：呈現一個系統內的應用程式及資料儲存，標示責任與已知技術。這裡的 Container 不等同 Docker container。[C4 Container 說明](https://c4model.com/diagrams/container)
- **Component**：放大單一 Container 的內部責任元件，例如 Controller、協調服務與 Repository；不要把這些元件誤稱為獨立 Container。[C4 Component 說明](https://c4model.com/diagrams/component)
- **Code／Class**：只有介面實作、依賴或型別結構與文章問題直接相關時才畫，不必把完整類別清單塞進架構圖。
- 跨層級引用以外部節點或局部放大圖交代，不在同一群平級節點混放使用者、整個系統、方法與主機。
- 使用 `flowchart` 與 `subgraph` 表達上述視角時，可稱「系統關係示意」或「Container 視圖」；沒有遵循相應範圍與標記時，不宣稱是嚴格的 C4 圖。

## 4. Sequence Diagram：互動時序

### 基本語意

參與者橫向排列，生命線向下延伸，時間由上往下。同步請求慣用 `->>`，回傳慣用 `-->>`；非同步訊息可用 `-)`，並標明事件名稱。線條外觀本身不能證明應用程式是否等待。[Mermaid 時序圖語法](https://mermaid.js.org/syntax/sequenceDiagram.html)

| 情境 | 表達方式 | 必須交代的限制 |
| --- | --- | --- |
| 同步請求／回應 | 分開畫呼叫與回傳，必要時加 activation | activation 表示執行範圍，不是實測耗時或鎖定時間 |
| 互斥條件 | `alt`／`else` | 條件應清楚互斥；HIT 不可串接到 MISS |
| 可選動作 | `opt` | 用在條件成立才執行的單一區塊，不代替 if／else |
| 重複執行 | `loop` | 描述迭代條件；只有已知上限才寫次數 |
| 真正並行 | `par`／`and` | 兩個獨立服務不代表呼叫一定平行，需有實作證據 |
| 中止剩餘流程 | `break` | 標明中止條件，不在中止分支內又接上成功回傳 |
| 非同步事件 | Producer、Queue／Topic、Consumer 分列 | 「訊息已入列」不等於「業務已完成」 |
| 重試 | `loop` 加上成功／失敗分支，必要時拆圖 | 標明由誰重試、何時停止；延遲、退避與次數未知就不填值 |
| 逾時 | 等待端的本地事件或註記，再畫其後續處置 | 逾時不代表遠端取消或失敗，無回應時不要偽造一條回傳 |
| 補償 | 已證實的反向業務動作另畫訊息 | 不把跨服務補償標成資料庫 rollback |

此表為技能的建模慣例；可執行範例見 [時序與非同步範例](diagram-examples.md)。

### 非同步與重試的細節

需要時區分「接收確認」「業務完成」「事件通知」。若採拉取佇列，畫 Consumer 的拉取與回應；若是推送，才畫 Queue 主動交付。重送、冪等鍵、死信佇列與 ACK 時點都必須有證據。C# `async`／`await` 不自動等於 fire-and-forget；呼叫端等待結果的互動仍需畫清楚。

重試與補償讓單圖過寬或巢狀過深時，拆為主請求、訊息消費、失敗處置等局部圖，保持同一組元件名稱。不要將所有實作細節擠進一張圖，也不要為了縮圖而合併實際上不同的責任。

## 5. 決策流程與泳道

- Flowchart 的處理節點寫動作，決策節點寫問題，分支邊標條件或結果；兩條路徑只有真的共用後續步驟才匯合。
- 泳道依責任者分組，交接線標輸入或交付物。相同責任者保持同一條泳道，不能任意按配色換欄。
- 為相容既有 Hexo Mermaid，可用 `flowchart` 的 `subgraph` 表達責任分區；這是泳道式示意，不是正式 BPMN，也不能保證 `subgraph` 在跨區連線後仍維持指定排列。
- 操作或部署流程偏向由上往下閱讀。需要精確比較跨服務呼叫與等待時，改用 Sequence Diagram。

## 6. 資料流、ERD 與 Class

**資料流圖**：節點區分來源、轉換處理與儲存；邊標資料名稱、格式或識別值。讀取與寫入方向分開，快取與永久來源分開，控制命令與資料流不要使用未解釋的同一套箭頭。僅用 flowchart 示意時，圖例說明箭頭代表資料移動而非執行時序。範例見 [資料轉換](diagram-examples.md)。

**ERD**：先說明是邏輯模型或實體資料表。依 schema／約束確認主鍵、外鍵、關聯方向、是否可為零與一對多基數；只標已確認的欄位。`||`、`o|`、`|{`、`o{` 等符號須與圖例及實際關係一致。不能只憑欄位同名就推定 FK；文件型資料也不應被捏造成關聯式表格。[Mermaid ERD 語法](https://mermaid.js.org/syntax/entityRelationshipDiagram.html)

**Class Diagram**：聚焦介面、實作、繼承或依賴，省略無關屬性與方法。組合關係意味著所有權／生命週期的語意，不是任何「持有一個欄位」都必然適合畫組合；證據不足時用一般關聯或依賴。不要與 ERD 的儲存關聯混用。

## 7. State Diagram

- 一張圖描述一種實體的生命週期，例如 Task；不要把「讀 Redis」這類操作當成狀態。
- 邊描述「事件 [條件] / 動作」，初始／終止節點只在已知生命週期上使用。
- 分清「Failed 可重試」與「終止失敗」；錯誤狀態不一定是終止狀態。
- 要表達巢狀狀態或並行區域時，先確認實作真的有相應語意；不用 state diagram 暗示不存在的並發行為。
- 一筆 trace 只證明一次走過的路徑，不能代表完整狀態機；不足部分標待確認。[Mermaid 狀態圖語法](https://mermaid.js.org/syntax/stateDiagram.html)

## 8. Deployment、建置流程與環境矩陣

Deployment 表達指定環境下的服務實例如何落在主機、程序、容器或區域。以邊界表達包含關係，網路連線標示已知協定／方向。節點數、副本數、網段、port 及負載平衡器不憑慣例補造。[C4 Deployment 說明](https://c4model.com/diagrams/deployment)

建置流程另畫 source → build → artifact → deploy，與部署完成後的 runtime 分開。QA／Production 設定差異用相同欄位矩陣；不同環境若拓撲不同，再畫各自的部署圖，不用節點大小表示重要程度。

## 9. 時間軸與文章組圖

事故時間軸以可追溯的時間、時區、觀察事件與來源為主，可用 Markdown 時間表或現有垂直時間軸元件。沒有時間就用有序步驟，不編造精確日期或持續時間。事件先後不等於因果；並行或順序未定的觀察要明講。

| 文章主題 | 可採用的組合，依內容取捨 |
| --- | --- |
| 購物車／API | 系統邊界或元件圖＋主請求時序；快取或錯誤分支需要時另拆 |
| NMQ／背景任務 | Producer／Queue／Consumer 時序＋任務狀態圖；事故分析再加時間表 |
| 資料同步／ETL | 資料流＋欄位對照；需要說明儲存關聯時加 ERD |
| CI/CD／部署 | 建置泳道＋環境矩陣；runtime 拓撲另圖 |
| 重構／模組設計 | 元件圖或 Class Diagram；只有需要對比時才畫前後兩版 |

## 10. 渲染、可讀性與完成條件

1. 先確認站點實際載入的 Mermaid 版本與插件。此技能的範例採用既有站點 Mermaid 10.8.0 可用的基本語法；官網新版本功能不表示本機已支援。
2. 優先使用站點正常文章的 Mermaid 包裝方式。若 fenced block 與主題自動渲染衝突，驗證主題內建 tag 作為替代；不要全站升級或移除 tabs 來逃避問題。
3. 在每張圖附近寫明標題、閱讀方向、關鍵結論與必要圖例。名稱跨圖一致；縮短 participant 顯示名時，旁邊對照完整元件名稱。
4. 不用固定圖數或節點數當驗收。資訊過密時按責任、場景或層級拆圖；兩張圖若只重複同一件事，應合併或刪除冗餘。
5. 用顏色輔助分類，不單靠顏色表達成功／失敗、環境或分支。正常架構節點採中性色；錯誤用紅色時不能同時把 Production 也定義成紅色。
6. 檢查標籤、中文、長識別字、箭頭與圖例的實際大小，不能把大圖縮成難讀的小字。手機可在圖內捲動，但必須能讀到全部資訊。
7. 選圖與語法檢查通過後，依 [建置與線上驗證](build-and-verify.md) 檢查實際 Hexo、每個 tab、深色切換、SVG marker、長分頁與正式網站。單獨語法解析成功不是畫面驗證。

官方文件是語法與層級的依據；本文件的選圖對照、拆圖判斷及實例是技能的實務建議，不是要求每篇文章遵循同一種版型。

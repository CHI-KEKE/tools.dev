# Hexo Article Creator

## Overview

建立或優化 Allen 的 Hexo 部落格文章（`source/_posts/**/*.md`）。核心是「先問清楚方向，再一次寫對」——多次實戰得出的教訓是：視覺風格和情境語意如果沒有先問，寫出來的初稿很容易被打回票重改。這個 skill 把該問的問題、該遵守的寫作規範、以及已經驗證過的視覺元件都準備好，減少來回修改次數。

## 工作流程

### Step 1：一次問清楚方向（動筆前必做）

在開始寫初稿或大幅改版前，用 `ask_user` 一次問完以下幾類問題（可分成 2-3 輪、每輪多個獨立問題，但不要邊寫邊補問）：

1. **情境／主題**：這篇文章的主題／情境是什麼？（例如：金流異常分析、架構設計說明、事件回顧）—— 這會決定配色語意基調
2. **視覺方向**：想要偏向哪種風格？可以主動提案 2-3 個具體方向（例如「病歷表」「終端機日誌風」「簡潔儀表板卡片」），或詢問對方心中是否已有想像的畫面；也要確認是否需要客製 HTML/CSS，還是 Hexo 內建 `{% note %}` tag 就夠
3. **內容深度**：是否已經有素材來源（HTML 報告、程式碼分析、既有草稿），還是要從零開始訪談內容

只有小幅度的單段落微調（例如「這段改個顏色」）時可以跳過這輪提問，直接動手。

若是優化既有文章（而非全新創作），先讀取整份 `.md`，掌握目前已定調的視覺風格（配色、字體、卡片樣式），確保新增/修改的段落延續同一套風格，不需要重新問視覺方向。

### Step 2：套用寫作規範

文章正文、圖說與提示框不得加入與主題無關的版面操作提示或製作說明，例如「窄螢幕可左右捲動。」；具體判斷與例外見 `references/writing-rules.md` 第 18 點。

寫作與優化時一律遵守 `references/writing-rules.md` 內的寫作規範（開場白話化、風格一致性、配色語意、`<code>` 包裹術語、分支要畫清楚、不用節點代號、不准使用破折號、長段落舉例要拆解成多種呈現方式、不用第二人稱「你」、禁止「很多人都以為」「常見誤解」等預設立場用詞、禁止「一句話理解」等制式導讀語等）。這些規範不需要每次跟使用者確認，直接套用。

### Step 3：套用 Hexo 慣例

Frontmatter 格式、`{% tabs %}` 分頁語法、渲染引擎對原始 HTML 的透傳行為、以及何時該用內建 tag plugin vs 自訂 HTML，見 `references/hexo-conventions.md`。

**⚠ 不要套用 `html-markdown-creator` 那套「左側章節導覽、右側單章節顯示」的側欄式版面**（`doc-shell` / `doc-sidebar` / `doc-nav-item` / 自訂 `<script>` 切換 active section）。那是給獨立 `.html` 分析文件用的版面，不是 Hexo 文章的慣例。Hexo 文章若有多個段落需要分頁瀏覽，一律用 Hexo 內建的 `{% tabs %}` 分頁語法（見上方 Frontmatter 慣例），不要在 `.md` 裡另外寫一份自訂側欄 JS。如果是把既有的側欄式 HTML 分析文件（`html-markdown-creator` 產出的成果）搬進 Hexo 文章，動筆前要先把左側導覽拆掉，改成一般章節標題（`<h2>`／`wp-section-head` 之類的區塊標題）依序往下排列，或視段落數量拆進 `{% tabs %}` 的多個 tab，而不是原封不動保留 `doc-shell` 那套 JS 切換機制。

判斷依據：
- `html-markdown-creator`（獨立 `.html` + `-pure.md`）→ 要做左側導覽側欄，因為輸出的是脫離 Hexo 的獨立文件，讀者是直接開啟該 HTML 檔案瀏覽整份分析文件，左側導覽能讓長文件快速跳章節。
- `hexo-article-creator`（`source/_posts/**/*.md`）→ 不要做左側導覽側欄，Hexo 文章本身會在部落格主題（Butterfly）裡有自己的頁面導覽、目錄（`toc`）與版面，額外塞一份自訂側欄 JS 容易跟主題版面衝突、也不符合這個 blog 既有文章的排版慣例；多段落需求一律改用 `{% tabs %}`。

### Step 5.1：Sequence Diagram 與進階互動

服務互動用橫向參與者、向下生命線與水平訊息表達時間順序；需要時加 activation。互斥、可選、迴圈、並行及中止分別使用 `alt`、`opt`、`loop`、`par`、`break`，使用前確認實作支持對應語意。

### Step 7：產生／同步純文字版（-pure.md）

**每次完整處理完一篇文章本身（新寫完或大幅優化完）之後，都要順手產生一份對應的純文字版 Markdown**，不需要使用者額外要求：

- 檔名規則：跟原檔同資料夾、同檔名加上 `-pure` 後綴。例如 `Capacity.md` → `capacity-pure.md`（沿用原檔的小寫/命名習慣即可，副檔名維持 `.md`）。
- 內容規則：
  - Frontmatter 照抄原文章的（title、date、categories 等），不要另外發明。
  - 移除 `{% tabs %}`／`<!-- tab -->`／`<style>`／所有自訂 `<div>`、`<span>` HTML 元件，改用最單純的 Markdown 語法呈現同樣的資訊：每個 tab 標題改成 `##` 二級標題；卡片/步驟流程/橫幅內的標題＋說明，改成有序或無序清單（`1. 標題：說明` 或 `- 標題：說明`）；純裝飾用的圖示、葉子表情符號、色塊不需要保留。
  - **文字內容本身（標題文字、說明文字、正文段落）必須跟正式版一字不差**，只是拿掉 HTML 外殼，不要在轉換過程中順手改寫用詞或精簡內容。
  - `` `code` `` 術語標記維持 Markdown 反引號寫法。
- **同步規則**：往後只要正式版文章的文字內容有任何修改（不管是使用者要求的小改動，還是後續優化），只要文字有變動，就要同步更新對應的 `-pure.md`，讓兩份檔案的文字內容隨時保持一致；如果只是調整視覺樣式（換配色、換元件、CSS 微調）而文字沒變，`-pure.md` 不需要重新產生。
- 完成後可跑一次 `hexo generate` 確認 `-pure.md` 也能正常產生頁面，且顯示的是完整內容而非殘留任何 HTML 標籤文字。
### Step 8：建置、部署與線上畫面驗證

文章完成後，必須讀取並執行 [建置與線上驗證流程](references/build-and-verify.md)。本機 `hexo generate` 成功只代表建置完成；已授權發布的工作，必須接著執行指定專案的 `hd`、等待該次 GitHub Pages 發布成功，再由 agent 自己開啟正式網址、切換每個 tab 並查看截圖。不能把請使用者刷新或自行查看當成驗證。

- 保留原有 tabs 與文章格式；以實際專案的主題、插件與渲染器驗證。
- 依 Step 7 同步純文字版後再建置；只有樣式變動時不需重寫文字版。
- 使用者要求 `hd` 或已授權部署時，延續授權完成流程，不重複詢問；只要求草稿或本機預覽時，完成本機驗證並明確標示尚未部署。
- 正式網址、最新版本識別、逐分頁截圖、桌面／手機／深色模式結果都需有實際證據。
- 發現問題時，在本次文章範圍內修正、重新建置與部署，再驗證受影響畫面；失敗或受阻不得回報全部完成。

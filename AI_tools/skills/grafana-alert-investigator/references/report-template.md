# 調查報告輸出格式

固定分三段：**現象 / 根因 / 建議**。依案件類型（API 類 / Worker 類）補充對應統計表。開始寫報告前，若調查過程中出現「判斷分岔」（例如：無法確定是系統性問題還是個案、或需要進一步查更長時間範圍才能下結論），**先跟使用者確認方向，不要自行假設後直接產出結論**。

## 通用開頭
簡述是否已透過 MCP 實際連線查證（列出用了哪些 datasource/context），非憑空推測。

## API/Ingress 類報告結構

```
## 現象
- 告警規則與 PromQL（附上分子/分母條件）
- 觸發時間窗、最低點數值、目前是否已恢復

## 根因
- 統計表：依 Status Code 分組
  | Status | 總筆數 | 發生原因 |
- 統計表：依 IP/來源分組
  | IP | 筆數 | 對應 UserId | 時間範圍 | 行為模式 |
- 代表性 log 追蹤鏈（trace id 關聯出的關鍵錯誤訊息）
- 明確結論：是否為特定來源、個案資料問題、還是系統性問題

## 建議
- 具體行動建議（例如：通知對應團隊、調整告警閾值、前端調整輪詢邏輯等）
```

## Worker/Container 類報告結構

```
## 現象
- 告警內容摘要（container/pod/namespace、重啟或資源數值）

## 根因
- Pod 現況（是否 not_found、目前 Restarts/Ready 狀態）
- Deployment revision/image 比對（是否為版本更新造成汰換）
- 資源使用狀況表：
  | Pod | CPU 使用 | Memory 使用 | Limit | 佔比 |
- 若為 OOM/CrashLoop：exception/OOMKilled 證據

## 建議
- 具體行動建議（例如：確認是否為預期發版、調整 resource limit、修復程式錯誤等）
```

## 語氣與用詞
- 使用臺灣繁體中文，語氣專業但精簡
- 每個結論都要附上查證依據（工具查到的具體數值/訊息），避免空泛推測
- 若某些面向因工具限制無法查證（如 datasource 找不到、log 已過期），需誠實說明，不要假裝已查證

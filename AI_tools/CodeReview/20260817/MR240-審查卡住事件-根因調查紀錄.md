### 2.4 為什麼 Pod 在 06:04:32 就被刪除，日誌卻撐到 06:05:52 才結束？

因為容器有 **graceful termination（terminationGracePeriodSeconds）**：Pod 收到終止信號（SIGTERM）後不會立刻被砍掉，Kubernetes 會給它一段緩衝時間讓程式自行完成手上的工作（或至少嘗試優雅關閉）。這段期間該 Pod 仍在處理原本進行中的背景審查任務，因此：

- **06:04:32**：K8s 標記該 Pod「縮容 → 停止容器 → 刪除」（進入 Terminating 狀態）
- **06:04:32 ~ 06:05:52（約 80 秒）**：Pod 進入 grace period，程式繼續跑完手上的 Dify 呼叫，陸續留下第 4 個檔案的審查日誌
- **grace period 結束後**：Pod 被強制終止（SIGKILL），此時背景審查任務（`Task.Run` 內尚未跑完的第 5、6 個檔案 + 最終彙整發布留言的步驟）**直接消失，沒有機會被記錄成任何錯誤或例外**

## 3. 根因結論

**MR #240 卡在「執行中」沒有下文，根因是：**

> TWQA 環境在這次審查進行「中途」，剛好發生了一次應用程式版本部署（Argo Rollouts 的 Canary → Promotion 流程），把正在執行這次背景審查任務的舊版 Pod 汰換掉了。而目前的審查流程是以 **`Task.Run` fire-and-forget** 方式在背景執行、**沒有任何持久化機制**（不會寫入資料庫或訊息佇列），一旦承載該任務的 Pod 被終止，任務就會直接消失，不會有其他 Pod 接手，也不會產生任何 Error 等級的日誌。

這**不是** Dify API 出錯、也**不是**程式邏輯 bug 造成的例外，而是**服務基礎架構層面「背景工作不具持久性 / 不耐部署中斷」**的問題，這次剛好被一次版本發布撞上而觸發。

## 4. 風險與建議

### 風險
只要「有 PR 正在跑審查」的時間點，剛好遇到：
- TWQA 環境部署新版本（Rolling Update / Canary Promotion）
- 或 Pod 因任何原因被 K8s 重啟、驅逐（HPA 縮容、節點維護、OOM 等）

就有機率複現一模一樣的「卡住不完成」現象，且**完全不會有任何 Error log**，難以主動察覺，只能靠使用者回報或人工比對時間軸才能發現。

### 建議修復方向

| 優先度 | 建議 | 說明 |
|---|---|---|
| 短期 | 部署時避開有審查任務正在執行的時段，或提高 `terminationGracePeriodSeconds` 並搭配 `preStop hook`，讓 Pod 收到 SIGTERM 後有更充分時間跑完既有任務 | 治標，降低發生機率，無法根除 |
| 短期 | Rollout 設定加入 Canary 分析步驟（目前是 `Canary analysis was skipped`），避免一偵測到新版就立即全量 Promotion，可搭配流量緩步切換降低影響範圍 | 降低「舊 Pod 被瞬間全部砍光」的機率 |
| 長期 | 將 fire-and-forget 的 `Task.Run` 背景審查，改為**持久化背景工作**（例如寫入資料庫/訊息佇列，由獨立 Background Worker 消費並支援斷點續傳或重試） | 根治：即使 Pod 被終止，任務仍可被其他 Pod 接手繼續執行，不會憑空消失 |
| 長期 | 針對「審查開始後超過 X 分鐘仍未產出最終留言」增加監控告警（例如比對 `PostInProgressCommentAsync` 與 `PostComments` 的配對是否都有結案） | 及早發現同類問題，不需要等使用者回報 |

Linter 留言聚合機制說明

多個 Bot × 多個檔案，最終在 PR 留下幾則留言？

1
核心結論
四個關鍵問題的直接答案
一個檔案一則留言？
❌ 否

所有檔案的結果混入同一個 priority bucket，不分開發文

一個 Bot 一則留言？
❌ 否

6 個 Bot 的結果全部合併進 High / Medium / Low 桶

最終幾則留言？
最多 4 則

有幾個 priority 就幾則，所有 Bot × 所有檔案全聚合

PR 層級 or Inline？
PR 層級

不是貼在 diff 特定行旁邊，是一般的 PR comment

3
兩條 Cache 路徑
靜態規則 vs AI 規則走不同的 cache key
路徑 A — 舊機制

_pending_issues

給非 AI 靜態規則使用（CrossDbContextJoinRule、NineYiDatabasesSPJoinRule 等）。所有靜態規則的結果聚合成一則留言，標題「# 🤖 Linter 檢查報告」。留言文字可包含 Line 123，但仍是 PR 層級文字，不是真 inline comment。

路徑 B — 新機制

_priority_issues

給 AI 規則使用，由 PushAiPriorityMessages() 寫入。所有 Bot × 所有檔案依 priority 分桶，有幾個 bucket 有資料就發幾則，最多 4 則。

Bucket標題
🔴 HighAI Code Review - 高優先
🟡 MediumAI Code Review - 中優先
🟢 LowAI Code Review - 低優先
🤖 UnknownAI Code Review
4
Bitbucket 特殊處理：倒序發文
Bitbucket 留言區由新到舊顯示（最新留言在最上面），因此 Linter 倒序發文：

發文順序：Unknown → Low → Medium → High
顯示結果：High（最上）→ Medium → Low → Unknown（最下）

GitLab / GitHub 由舊到新顯示，所以正序發（High → Medium → Low → Unknown）。

Linter vs V2 留言機制對比
面向LinterV2
AI 結果分組 依 Priority 最多 4 則 全部聚合 1 則
跨 Bot 聚合 ✅ 同 priority bucket 合併 ✅ 全部合併 + <details> 折疊
跨檔案聚合 ✅ 同 priority bucket 合併 ✅ 全部合併，按 file/rule 分層
是否為 Inline Comment ❌ PR 層級文字留言 ❌ PR 層級（PostReviewCommentAsync 已寫但未接入）
平台發文差異 Bitbucket 倒序，GitLab/GitHub 正序 無差異，永遠 1 則

03

整體設計架構與模組總覽

專案採 Clean Architecture 分層，程式碼放在 src/ 下三個資料夾：Web（呈現層）、BusinessLogic（應用層 + 領域層）、DataAccess（基礎設施層）。下圖僅呈現目前實際運作中的模組與彼此的依賴關係。

圖中由上而下依序是：外部平台呼叫進來 → 呈現層（WebhookController / BitbucketController 接收請求）→ 應用層（CodeReviewService 決定審查怎麼跑，規則來自右側 appsettings.json）→ 領域層（ReviewSeverity 定義嚴重度分級）→ 基礎設施層（反向實作應用層介面，負責真正對外溝通）→ 最底部則是實際往外呼叫的目的地（Bitbucket/GitHub/GitLab API、Dify AI）。全程只有垂直方向的依賴，沒有跨層交叉呼叫，目前規則設定尚未使用資料庫。

04

API 層架構

NineYi.Ai.CodeReview.Api 底下的 Controllers 目前只有兩支，職責完全不同，分別對應兩個獨立需求：Webhook（AI 主動審查）與Bitbucket API 代理（被動轉發）。以下聚焦說明這兩者的用途與由來。

🪝WebhookControllerAI 主動審查

接收 GitHub / GitLab / Bitbucket 的 PR/MR 事件，觸發本服務自己的 Dify AI Code Review 流程（詳見「核心審查流程」）。

為什麼要用 Webhook 這種即時事件驅動的方式，而不是排程或人工觸發？

  • PR/MR 一有新異動就能即時觸發審查，開發者不用等待或手動觸發
  • 集中在一個服務裡，方便團隊即時調整維護審查規則與邏輯
  • 可完整監控每次執行的狀況與歷程（log、TraceId），出狀況時能快速追查
  • 能觀察 Dify API 呼叫的費用，掌握 AI 審查的成本狀況

🔌BitbucketController純 API 代理站台

不含任何 AI 審查邏輯，單純把 diff / comment / diffstat / file-content / commits / src-tree / pull-requests 等請求原樣轉打 Bitbucket API 並回傳結果。

為什麼需要一個「代理站台」？ 舊站台 Linter（負責靜態規則的 Code Review）原本會自己直接打 Bitbucket API，但自 2026 年 6 月中旬起，Linter 直接呼叫 Bitbucket API 開始穩定出現 SSL 連線失敗的錯誤：

🧯 Linter 直打 Bitbucket API 的實際錯誤訊息：
18:06:30 ❌ Unexpected Error: [Bitbucket] Diff API 取得 GitDiff 失敗 - URL: https://api.bitbucket.org/2.0/repositories/nineyi/nineyi.webstore.mobilewebmall/diff/... , StatusCode: 0, ResponseStatus: Error, ErrorMessage: The SSL connection could not be established, see inner exception. Authentication failed, see inner exception., ErrorException: The SSL connection could not be established, see inner exception. Authentication failed, see inner exception., InnerException: The SSL connection could not be established, see inner exception.

因此改由 AI Code Review（本服務）代替 Linter 出面呼叫 Bitbucket API：Linter 改成呼叫本服務的 BitbucketController，再由本服務轉打 Bitbucket，繞開 Linter 端直連 Bitbucket 時的 SSL 交握 / 驗證失敗問題。也就是說，Bitbucket 這條路線是「代理」而非「AI 審查」，與 Webhook 那條「AI 主動審查」的路線是兩件獨立的事，只是恰好都掛在同一個 API 專案底下。

05

審查流程

Webhook 進入後採 Fire-and-Forget 模式：驗證通過立即回 200，實際審查在背景獨立 DI Scope 執行，避免平台因等待逾時而重試。

STEP 1接收 Webhook
GitHub / GitLab / Bitbucket
→
STEP 2ShouldProcess 過濾
僅處理 open/synchronize/reopen 等事件
→
STEP 3Signature 驗證
HMAC-SHA256 / Token 比對
→
STEP 4組裝 Command
StartCodeReviewCommand + TraceId
STEP 5背景執行 Review
CodeReviewService.StartAsync
→
STEP 6取得 Diff + 套用規則
依 appsettings.json 設定的規則過濾檔案
→
STEP 7呼叫 Dify AI 分析
取得 Must/Should/May 建議
→
STEP 8回貼結果至原平台
留言 / LGTM（尚未落地寫入資料庫）
💡 為什麼略過事件也回 200？ 若回傳 4xx，GitHub / GitLab / Bitbucket 會誤判服務異常並持續重試 Webhook；因此無需處理的事件一律回 200 { "message": "Event skipped" }，並不進行 review。
06

Webhook 端點與觸發條件

平台Endpoint事件識別 Header觸發 Action簽章驗證
GitHub POST /api/webhook/github X-GitHub-Event: pull_request opened / synchronize / reopened HMAC-SHA256（X-Hub-Signature-256，常數時間比對）
GitLab POST /api/webhook/gitlab X-Gitlab-Event: Merge Request Hook open / update / reopen Token 直接比對（X-Gitlab-Token）
Bitbucket POST /api/webhook/bitbucket X-Event-Key: pullrequest:created/updated state = OPEN 無（Bitbucket Cloud 未提供內建簽章）

兩種 Secret 未設定時皆「直接放行」以方便本機開發測試；正式環境透過 _N1SECRETS__* 環境變數（AWS Secrets Manager）注入。詳細規格見 docs/webhook-readme.md。

規則設計與嚴重度分級

📋 目前實際運作方式：appsettings.json 設定規則

CodeReviewService 實際讀取的是 CodeReviewConfig（RuleEntry 清單），也就是規則直接寫在設定檔中，於程式啟動時載入，並非透過資料庫管理。

Domain.Entities.Rule（Security/CodeStyle/Performance/BestPractice/Documentation/Testing/Custom 分類）是另外設計的資料庫實體，目前未被審查流程使用。

🚦 ReviewSeverity 嚴重度（已實際運作）

數值越小、優先級越高，決定是否需要發布留言：

Must資安、崩潰、嚴重邏輯錯誤 — 必須修正
Should效能隱患、不良設計、維護性問題 — 應予改善
May優化建議、更優寫法 — 僅供參考，不發留言（近期新增：即使只剩 May 也保留 comment 以利確認已檢查）

待實作項目

以下為團隊接下來規劃要討論、設計或實作的方向，尚未動工，先列出範疇與現況供團隊對齊。

📈Grafana 告警設計

拉出 Repo、Token、PR 三者的關係，設計對應的 Grafana Alert 方式（例如：特定 Repo 審查失敗率過高、Token 即將過期、PR 審查耗時異常等），提升問題可觀測性與提前預警能力。

🔑HotTables 串接實作

串接 Google Sheet API，即時取得 Excel 上維護的「危險 / 高影響資料表清單（HotTables）」，當 PR 的 diff 異動到清單中較危險或影響較大的資料表時，主動提醒發 PR 的人多加留意，取代目前僅有 Domain 設計、未串接的狀態。

🔀Linter 轉移

將舊站台 Linter 呼叫 AI Code Review 的目標，全數改打 AI Code Review V2；並將 Linter 原本負責的靜態規則邏輯，逐步搬移到 AI Code Review 中實作，最終讓 Linter 可以退場。

目前搬移現況：

平台搬移狀態
Bitbucket主要使用站台皆已搬移完成
GitLab已搬移 PaymentMiddleware、LivebuyApi、LivebuyWorker
GitHub已搬移 LivebuyApi

尚未搬移、待處理：DB Repo（用來改 Stored Procedure）、DB Operation Repo（用來發 SQL 語法改資料）這兩個重要 Repo 目前都還沒搬移。這兩者的審查對象是 SQL 而非一般程式碼 diff，需要額外串接 diff-raw API 才能取得原始異動內容進行審查。

🗂️規則清單維護方法

目前規則寫死在 appsettings.json，若要新增 / 調整某個 Repo 的規則，就得改設定檔並重新跑一次 Pipeline 才能生效，維護成本偏高。需要討論是否有更容易調整、免重新部署的存放方式，例如：

存放於 S3（啟動或定時讀取最新版本）、存放於 Secrets Manager / Parameter Store、或其他集中式設定服務，讓規則異動不需要綁定程式碼發版流程。

NineYi.Ai.CodeReview · Implementation Blueprint

SimpleReview
實作規劃書

在既有 Webhook-based Code Review 架構上，新增一支同步式、供 Copilot CLI / CI 直接呼叫的 POST /api/review/diff 端點。本文件記錄命名/架構決策、分層實作計畫、 共用邏輯抽出方式（RuleMatcher）與風險控管——尚未動手實作程式碼。

i.

背景與現況落差

先前分析的 DirectReviewController / IRuleRepository（DB 驅動規則）等程式碼， 在目前這版程式庫中已不存在。現況已改為：

項目現況
規則來源設定檔驅動：CodeReviewConfig.Rules（List<RuleEntry>），對應 _N1CONFIG:CodeReview
Dify 呼叫方式目前只有 ReviewCodeAsync，內部已經是打 Dify Chat API（/v1/chat-messages，與 DifySettings.ApiEndpoint 預設值一致），但輸入/輸出資料契約綁死「單一檔案、逐行回貼 PR 留言」場景（非另一支 Workflow API，先前規劃書誤植已更正）
Webhook 流程PullRequestReviewService.StartAsync 已有完整「依 repo 找 Rule → 逐檔呼叫 Dify → 回貼 Git 平台」邏輯，規則比對邏輯目前是其內部 private 方法

因此這次是從目前架構出發新增功能，而非修改舊的 DirectReview 程式碼。

ii.

設計決策

CONTROLLER 命名
ReviewController
路由 api/review，比照既有 WebhookController（一個 Controller、多個 Action）模式，未來新增審查相關端點不必再開新 Controller。
ACTION 命名
POST /api/review/diff
語意對應 body 裡的 diffContent；避免 direct 與 Controller 語意重複，也避免 quick/full 各開一個 Action 導致 Action 隨審查尺度增加而膨脹。
taskingFlow 型別
enum ReviewScope { Quick, Full }
字串改為強型別，避免打錯字、Swagger 可自動列出合法值；未來加 Deep 只需加一個 enum 值。
Rule 依 SCOPE 篩選
RuleEntry.ApplicableScopes
List<ReviewScope>，空清單＝僅 Full 適用（保守預設），Quick 需明確加入白名單（如 ["Quick","Full"]）才會被觸發；只需異動想納入 Quick 的 Rule，其餘既有 Rule 不用動。
規則比對邏輯
抽出共用 IRuleMatcher
Webhook 流程與新 Diff Review 流程共用同一套「依 repo/scope/file pattern 找 Rule」邏輯，避免兩邊分岔維護。
Dify 呼叫方式
新增 ChatReviewAsync
端點沒有換，一樣是 /v1/chat-messages。新增理由是資料契約不同：ReviewCodeAsync 綁死單一檔名＋單檔 diff 輸入，並把 answer 切成 [MUST]/[SHOULD]/[MAY] 結構化 Comment（供回貼 PR 行內留言）；新方法要送整段多檔 diff＋context，且直接回傳原始 answer 文字，不做標籤切割。
兩個核心 SERVICE 命名
CodeReviewService（新）／PullRequestReviewService（既有改名）
「Code Review」是最通用的核心領域動作，新的 Diff 審查最貼近這個通用動作，接手這個名字；既有服務除了審查程式碼還背負 PR 實體的抓取／比對／回貼留言／DB 寫入等副作用，屬於「操作 PR 實體」的特化應用，改名為 PullRequestReviewService 更精準——強調操作對象而非 Webhook 這個觸發管道，未來即使改成手動重跑也不用再改名。
iii.

分層實作計畫

Domain

基礎型別

  • 新增 Domain/Enums/ReviewScopeEnum.cs：enum ReviewScope { Quick = 1, Full = 2 }
  • Application/Config/RuleEntry.cs 新增 ApplicableScopes（List<ReviewScope>）。語意：空清單＝僅 Full 適用，需明確加入 Quick 才會在快速審查時觸發
  • Domain/Interfaces/IDifyService.cs 新增 ChatReviewAsync 方法 + DifyChatReviewRequest / DifyChatReviewResult DTO — 同一支 /v1/chat-messages，差異在輸入（整段多檔 diff＋context）與輸出（原始 answer 文字，不做 MUST/SHOULD/MAY 切割）
Application · Refactor

既有服務改名 + 抽出共用 RuleMatcher

💬 命名討論結論：維持 IRuleMatcher 不拆分、不改名。它同時承擔「依 repo+scope 篩選規則清單」（組合式決策）與「單一檔名對 pattern 的布林比對」（純粹 matcher）兩種粒度，要求在介面上補齊 XML 註解說明各方法職責邊界。本階段額外新增改名任務：ICodeReviewService/CodeReviewService → IPullRequestReviewService/PullRequestReviewService，把「CodeReviewService」名字讓給新的 Diff Review 服務，是本規劃書唯一牽動既有生產程式碼命名的異動（規模與本 session 稍早的 GitPlatformType→GitPlatformTypeEnum 重構相當），建議與 RuleMatcher 抽取同一個 PR 完成。
  • 改名 ICodeReviewService/CodeReviewService → IPullRequestReviewService/PullRequestReviewService（方法簽章不變）
  • Api/Controllers/WebhookController.cs 建構子注入型別同步改為 IPullRequestReviewService
  • Application/DependencyInjection.cs 註冊型別同步改為 AddScoped<IPullRequestReviewService, PullRequestReviewService>()
  • 新增 IRuleMatcher：GetApplicableRules(repoFullName, scope?)、IsFilePatternMatch(...)（皆補上 XML 文件註解）
  • 新增 RuleMatcher：搬移 PullRequestReviewService 現有的 GetApplicableRules / IsRepoMatch / IsFrontendRule / ExcludeFrontendRulesForNmqRepo / IsFilePatternMatch；scope 篩選邏輯：null→不篩選（Webhook 相容），Full→空清單或包含 Full 皆可，Quick→必須明確包含 Quick
  • PullRequestReviewService 改注入 IRuleMatcher，移除搬走的 private 方法
  • DI 註冊：AddSingleton<IRuleMatcher, RuleMatcher>()
⚠ 改名牽動既有生產程式碼（介面、DI 註冊、Controller 注入），加上 RuleMatcher 抽取皆屬「搬移/改名不改邏輯」，但仍需迴歸驗證 Webhook 流程行為完全一致，並確認無日誌監控/儀表板告警綁死舊類別名稱
Application

Diff Review 服務與 DTO

💬 命名與分層討論結論：獨立為 ICodeReviewService/CodeReviewService（接手核心領域名字），不合併進 PullRequestReviewService、也不省略此層讓 Controller 直接呼叫 IDifyService。對照實際程式碼，PullRequestReviewService.ExecuteReviewAsync 的 PR Title Gate／抓 diff／回貼 PR 等步驟 Diff Review 完全用不到，合併不會共用到任何程式碼；「Code Review」是通用核心動作，「PullRequest」則強調操作 PR 實體的特化副作用，兩者是「通用能力 vs 特化應用」的命名分工，不是構詞對稱遊戲。本階段只定義 ReviewAsync 一個方法，未來擴充方法待實際需求出現再評估（YAGNI）。
  • 新增 Application/DTOs/DiffReviewDto.cs：DiffReviewRequest / ReviewContext / FileFullContent / DiffReviewResponse / DiffReviewAnswer
  • 新增 ICodeReviewService / CodeReviewService：驗證必填 → 透過 IRuleMatcher 找 Rule → 組 ContextSummary → 平行呼叫 ChatReviewAsync → 彙整回傳
Infrastructure

Dify Chat API 實作

  • DifyService.cs 實作 ChatReviewAsync：POST 至同一支 {ApiEndpoint}（/v1/chat-messages，與 ReviewCodeAsync 相同端點），直接回傳原始 answer 文字（不做結構化切割）
  • 沿用現有 ReviewCodeAsync 的 HttpClient / 認證 / 錯誤處理 / 耗時量測慣例
Api

Controller 與 DI 註冊

  • 新增 Api/Controllers/ReviewController.cs：[Route("api/[controller]")]，[HttpPost("diff")]
  • DI 註冊：AddScoped<ICodeReviewService, CodeReviewService>()
iv.

設定檔調整

實際設定檔位於 config/settings.json 的 _N1CONFIG:CodeReview:Rules，目前共 23 條 Rule，全部預設 ApplyToRepos: ["*"]。 Quick 檔位採白名單制：只有明確加上 ApplicableScopes 且包含 "Quick" 的 Rule，才會在 Scope=Quick 時被觸發；未標記的 Rule 空清單視為「僅 Full 適用」。

本次只需異動 2 條 Rule（StandardBackend、CustomRuleBackend），其餘 21 條完全不用修改：

config/settings.json 
{
  "Name": "StandardBackend",
  "DifyApiKey": "app-ZiyaCPCjqiTaN8YEAsMTZU8e",
  "FilePatterns": "*.cs",
  "ApplyToRepos": ["*"],
  "IsActive": true,
  "IsFrontendRule": false,
  "ApplicableScopes": ["Quick", "Full"]
},
{
  "Name": "CustomRuleBackend",
  "DifyApiKey": "app-CzdjFhacdnhKZ9z3vGZdL9DL",
  "FilePatterns": "*.cs",
  "ApplyToRepos": ["*"],
  "IsActive": true,
  "IsFrontendRule": false,
  "ApplicableScopes": ["Quick", "Full"]
}
✓

其餘 21 條（Exception、InfoSecurity、CodeMentorPro、Performance、FrontendStandard、NMQ 等）維持原樣、不加 ApplicableScopes：依新語意只在 Scope=Full（或 Webhook 流程，不受此篩選影響）時套用，Quick 模式下不會被觸發，對應「Quick 只跑兩條核心規則」的設計目標。

⚠

若未來想調整 Quick 涵蓋的 Rule，只需要在對應 Rule 上加/改 ApplicableScopes，不用動程式碼。

v.

測試計畫

類型內容
單元測試RuleMatcher：依 repo/scope/file pattern 篩選是否正確；NMQ 前端規則排除邏輯是否維持原行為
單元測試CodeReviewService：必填欄位驗證、找不到 Rule 時回傳訊息、多 Rule 平行呼叫彙整、單一 Rule 失敗不影響其他結果
迴歸驗證重構 PullRequestReviewService 後，用既有測試案例或手動觸發一次 PR 確認行為一致
整合測試實際呼叫 POST /api/review/diff：找不到 repo（400）、找不到符合 scope 的 Rule（400）、正常成功（200）、Dify 逾時/失敗（單一 Rule 失敗但整體仍 200）
vi.

待辦拆解（依相依順序）

  1. ReviewScopeEnum + RuleEntry.ApplicableScopes

vii.

風險與注意事項

▲

重構風險：Phase 1 動到既有 Webhook 流程使用的私有方法，雖是搬移不改邏輯，仍需迴歸驗證，避免影響現行生產中的 Webhook 審查功能。

▲

既有服務改名風險：CodeReviewService→PullRequestReviewService 是本規劃書唯一牽動既有生產程式碼命名的異動，需完整檢查是否有日誌監控關鍵字、儀表板告警規則、或其他未被 grep 到的文字引用綁死舊類別名稱；建議與 RuleMatcher 抽取合併在同一個 PR 送出，一次性完成迴歸驗證。

⚠

Dify Chat API 額度／逾時：多 Rule 平行呼叫會同時消耗多個 Dify App 額度，需確認現有 DifySettings（timeout、重試策略）是否需要針對 Chat API 另外調整。

⚠

ApplicableScopes 預設語意：務必清楚記載「空清單＝僅 Full 適用，Quick 需明確白名單」，避免設定檔維護者誤以為空清單代表「全部 scope 皆適用」而誤觸發 Quick。

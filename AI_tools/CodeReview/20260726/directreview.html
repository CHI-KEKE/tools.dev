API 規格書

同步式 diff 審查端點——不透過 Webhook、不落地資料庫、不與 Git 平台互動。 專為 Copilot CLI / CI Script 設計的輕量審查通道，本文件涵蓋請求／回應規格、 與既有 Webhook 流程的差異比較，以及 taskingFlow 命名優化提案。

i.

這支 API 是什麼

DirectReviewController 是既有「Webhook-based Code Review」流程之外，另外提供的一條 輕量、同步、無狀態審查通道。呼叫端直接把整段 diff 內容 POST 給 Server， Server 依 repositoryName 查出對應的審查規則（Rule），平行呼叫每條規則對應的 Dify Chat App，等全部回應完成後彙整成清單，一次性同步回傳。 

Client (Copilot CLI / CI)
      │  diff + repoName + taskingFlow
      ▼
DirectReviewController  (POST /api/review/direct)
      ▼
DirectReviewService.ReviewAsync()
      │
      ├─ 1. 依 RepositoryName + TaskingFlow 查詢 Rules   (IRuleRepository)
      ├─ 2. 組 ContextSummary（branch / workItem / author / 完整檔案內容）
      ├─ 3. 對每條 Rule 平行呼叫 Dify Chat API            (IDifyService.ChatReviewAsync)
      └─ 4. Task.WhenAll 彙整 → DirectReviewResponse
      ▼
回傳 JSON 結果給呼叫端（不寫 DB、不回貼 PR comment）
ii.

與既有 Webhook 流程的差異

兩者共用「Rules 資料來源」與「Dify 服務物件」，但沒有共用核心審查邏輯——彼此是兩條互不影響的程式碼路徑。

面向Webhook 流程Direct Review
觸發方式Git 平台 Webhook（PR 建立/更新）呼叫端主動 POST diff
Dify APIWorkflow API，逐檔案呼叫Chat API，整段 diff 一次呼叫
執行順序序列處理平行（Task.WhenAll）
Git 平台互動取檔案清單、回貼 comment無
Hot Keyword 掃描有無
資料庫寫入ReviewLog / FileLog / UsageLog / Statistics無
回傳內容結構化 Comment（行號/嚴重度/分類）純文字 Answer

Request 規格

DirectReviewRequest

欄位型別必填說明
repositoryNamestring必填Repository 名稱，支援 FullName / Name / 結尾比對。例如 nine1.live.buy

欄位型別說明

authorstring?提交者 email
fullFileContentsarray異動檔案的完整內容，提供完整 method 上下文

iv.

taskingFlow — 審查規則的「檔位」

用來決定「這次呼叫要跑哪一組 Rule」，而不是跑該 Repository 底下全部的 Rule。 底層對應 Rule.FlowTags（逗號分隔字串）；FlowTags 為空的 Rule 視為所有流程皆適用，永遠會被納入。

⚠

命名問題：現況值為 review-only / full，兩者不是同一維度的對稱詞（full 的反義應是「精簡」而非「只做審查」），呼叫端得回頭查註解才能理解涵蓋範圍。

提案：改用 quick / full

Quick

quick

快速檢查，只跑核心必要規則。對應現有 review-only：Custom + Standard 兩個 Dify App。

取代： review-only
Full

full

完整審查，跑所有適用此 Repository 的規則。與現況完全相同，不需變動任何資料。

沿用： full（無需異動）
✓

選擇理由： ① 對稱好懂，不用查文件就能猜出行為差異　② full 沿用現值，相容性高　③ 可延伸為 quick → full → deep 等更多檔位。

📌 本文件僅為設計提案，尚未變更程式碼。若確認採用，需同步調整 DirectReviewRequest.TaskingFlow 預設值、Rule.FlowTags 既有資料， 與 IRuleRepository.GetByRepositoryNameAndFlowAsync 的比對邏輯及相關註解。

v.

Response 規格

200 OK：至少一個 Rule 成功　·　400 Bad Request：參數錯誤或找不到 Rules　·　500：未預期例外

DirectReviewResponse

欄位型別說明
isSuccessbool只要有任一 Rule 成功即為 true
answersarray每條 Rule 的審查結果
totalDurationMsint全部平行呼叫的總耗時（毫秒）
errorMessagestring?錯誤訊息（找不到 Rule / 參數錯誤 / 例外）

answers[] — DirectReviewAnswer

欄位型別說明
reviewerstring對應 Rule.Name
answerstringDify Chat App 回答原文；失敗時為 [ERROR] ...
isSuccessbool該 Rule 呼叫是否成功
durationMsint該 Rule 呼叫耗時
response.json 
{
  "isSuccess": true,
  "answers": [
    {
      "reviewer": "Custom Rule",
      "answer": "整體變更看起來合理，建議在 MyService.cs 第 42 行加上 null 檢查。",
      "isSuccess": true,
      "durationMs": 3120
    },
    {
      "reviewer": "Standard Rule",
      "answer": "[ERROR] Dify API timeout",
      "isSuccess": false,
      "durationMs": 15000
    }
  ],
  "totalDurationMs": 15020,
  "errorMessage": null
}

重點整理

  1. 接收：一段 diff 字串 + repositoryName（+ 可選的 taskingFlow、context）。
  2. 查規則：依 repositoryName（+ taskingFlow 篩選）找出對應的 Dify Rule 清單。
  3. 平行呼叫：對每條 Rule 同時打各自的 Dify Chat App，不是依序一個個打。
  4. 彙整回傳：等所有呼叫結束，把每條 Rule 的純文字回答彙整成清單一次回傳，全程不寫資料庫、不與 Git 平台互動。

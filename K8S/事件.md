

## Requests vs Limits

| 欄位         | 意思                  | 影響                                    |
| ---------- | ------------------- | ------------------------------------- |
| `requests` | Scheduler 調度時看的最低需求 | 若不夠放 → Pod Pending                    |
| `limits`   | 實際執行時允許的最大資源        | 超過限制 → Pod 內程式被 throttled 或 OOMKilled |


```yaml
resources:
  requests:
    cpu: "2"
  limits:
    cpu: "3.5"
```

這代表：

Scheduler 認為這個 Pod 只要 2 Core 就能啟動 → 能排進 Node
但執行時最多可用 3.5 Core → K8s runtime 用 cgroups 限制 CPU 使用上限

所以如果你設定 requests: 3.5，就表示「要保證 3.5 才能啟動」，如果你只是想允許它高峰時能用到 3.5


K8s 會透過 Linux 的 cgroups（control groups） 來限制容器的資源使用量。所以超過 limit 時，不是「軟限制」，而是系統層面直接干預。


## CPU 超過限制 → Throttled（被限速）

Throttling = 限速。代表容器「試圖」用超過 limit 的 CPU，但系統幫你踩煞車。


假設設定
```yaml
limits:
  cpu: "1"
```
意思是這個 Pod 最多能用「1 個 CPU 核心」的時間量


但如果你的程式很忙（例如在跑 heavy loop），容器會試圖吃更多 CPU，這時 Linux cgroups 會強制讓這個 container 暫時停下來（sleep 一下），等時間片過了再放行

結果就是，程式沒有被殺掉，但「效能下降」（被限速），log、metrics 會看到 throttled 次數增加

| 情境                    | 說明                |
| --------------------- | ----------------- |
| 程式瞬間爆 CPU（例如壓測、GC、加密） | 嘗試吃超過 limit       |
| 設定 limit 太低           | K8s 幫你硬性壓制 CPU 時間 |
| 在單核 node 裡跑多個高負載 Pod  | 爭用 CPU            |


## 記憶體超過限制 → OOMKilled（被記憶體殺掉）

OOMKilled = Out Of Memory Killed。代表容器用了超過它能用的記憶體上限，被系統殺死

```yaml
limits:
  memory: "512Mi"
```

但程式吃太多記憶體，容器的記憶體會一路衝上去，直到超過 512Mi，這時 Linux cgroups 偵測到容器超過限制，系統直接執行 OOM Killer（Out-of-Memory Killer），把這個容器「整個殺掉」

Pod 狀態變成 CrashLoopBackOff，kubectl describe pod 會看到

Last State: Terminated
Reason: OOMKilled
Exit Code: 137

🧩 常見徵兆

Pod 頻繁重啟 (CrashLoopBackOff)
事件訊息裡有 OOMKilled
Node 的記憶體壓力高

## 為什麼 CPU 不直接殺掉、Memory 會

CPU 是可分時（Time-shared）的資源 → 你用太多可以「延後執行」
Memory 是不可分割的資源 → 沒空間就只能「殺掉某人」


所以：

CPU 超出 limit → 降速（Throttle）
Memory 超出 limit → 死亡（OOMKilled）


Kubernetes 在每個 Pod 的容器外面包了一層「cgroup」







## 自動調度策略與實際流量不匹配

Kubernetes 在自動調度與資源彈性調整時，若未精確設定服務的容忍度與負載容量，會導致短暫服務中斷或性能下降

- 機器回收 (Node Reclaim)：當雲服務商或叢集管理機制回收節點時，該節點上的 Pod 需要被重新分配到其他節點。這是常見但會引起短暫不穩的情況。

- PDB（Pod Disruption Budget）設計問題：PDB 是為了防止太多 Pod 同時被中斷，但原先設為 50%，表示允許有一半的 Pod 被中斷。對於高流量、高依賴的服務（如 SPL），這樣的彈性太寬鬆，可能在高峰期導致容量不足。

- 健康檢查失敗的影響：新 Pod 啟動時若健康檢查未過，就不會被加進流量池（不會接收請求）。這會讓實際可用 Pod 數更少，加劇負載集中與錯誤率上升。

- 手動干預的必要性：當系統自動調度策略與實際流量不匹配時，人為暫時鎖住資源（例如調高 PDB）是務實作法，可避免雪崩效應。


假設一個微服務 spl-service 在 Kubernetes 上運行，有 4 個 Pod

- 原設定：minAvailable: 2（PDB = 50%）
- 流量情況：平均 RPS = 1500（約每 Pod 負載 375 RPS）
- 事件：其中一個節點被回收，K8s 重新啟動一個 Pod
- 問題：新 Pod 啟動中（未 ready），只剩 2 個能工作 → 每 Pod 承受 750 RPS → 出現 4xx/5xx 錯誤
- 解法：將 PDB 改成 minAvailable: 4（100%），確保不會再同時停掉 Pod，避免在高負載時容量不足。


這樣的分析與調整可以應用在：

高可用服務的部署策略設計 — 特別是金融、遊戲、影音串流等對延遲敏感的服務
Kubernetes 彈性伸縮與容錯優化 — 針對 PDB、HPA（自動擴縮）與健康檢查設定做平衡調整
SRE / DevOps 的 Incident 分析與調整 — 當出現高錯誤率時，判斷是資源不足還是配置策略問題
Capacity Planning（容量規劃） — 決定最少需多少 Pod 才能承載高峰流量，並根據實際負載調整保護閾值

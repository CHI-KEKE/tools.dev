



## 2. Kubernetes 三個基本角色

### 1. Node（節點 / 工作者）🖥️

可以是一台實體機器（例如你自己的伺服器）或是雲端的虛擬機器（例如 AWS EC2）。每個 Node 都是 Kubernetes 的「工人」，負責執行應用程式。有時也叫作 Minion（奴隸），因為它聽從主控 Master（Control Plane）的指令。

<br>

**🔧 功能**：
- 幫忙執行 Pod（容器群）
- 管理 CPU、記憶體等資源
- 提供網路、磁碟空間

<br>

### 2. Pod（膠囊 / 容器群）

是 Kubernetes 中「最小的可部署單位」。

<br>

一個 Pod 裡面可以裝一個或多個 Container（但大部分情況是一個）。

<br>

**🧠 為什麼需要 Pod？**

因為直接用 Container（容器）太難管理網路，K8S 幫你用 Pod 把容器「包裝起來」變成一個整體。Docker 會幫這個 container 分配一個獨立 IP，每個 container 都在自己的網路空間中運作（network namespace）。

<br>

你要讓 container A 去找 container B，必須：
- 知道對方的 IP 或名稱
- 自己處理 port mapping、防火牆等

<br>

**🌐 Pod 的特性**：

裡面的容器會共用：
- 同一個 IP 地址
- 同一個網路空間
- 同一個儲存空間（Volume）

<br>

容器彼此就像住在同一個房間，可以用 localhost 互相講話，速度又快又安全。

<br>

### 3. Container（容器）🚢

裡面跑的就是你真正寫好的應用程式，例如：
- Node.js 後端
- MySQL 資料庫
- Python 機器學習模型

<br>

通常用 Docker 建立容器映像（image），再部署到 Pod 中

<br>

**📦 一個容器 = 一個微服務**

每個 Container 就像一台微型電腦，跑著某個功能，例如會員服務、購物車服務、資料庫等。

<br>

### 架構示意圖

```
Kubernetes 節點(Node)
 ├── Pod A
 │    ├── 容器：Node.js API
 │    └── 容器：Sidecar 日誌收集器
 ├── Pod B
 │    └── 容器：MySQL 資料庫
 └── Pod C
      └── 容器：Redis 快取服務
```

<br>

### 元件對照表

| 元件 | 說明 | 類比 |
|------|------|------|
| Node | 實際跑應用程式的機器 | 工廠地點 |
| Pod | 把容器包在一起的基本單位 | 一間機房、一個房間 |
| Container | 應用程式運作的實體 | 機器、冷氣、伺服器 |

<br>






## Node 節點架構

### AWS 環境中的 Node 概念

在 AWS 上，Rancher 所管理的 Kubernetes 叢集通常架在 EKS（Elastic Kubernetes Service）上，而每個 Node（節點）通常就是一台 EC2 instance。

<br>

### Kubernetes 元件與 AWS 對應關係

| Kubernetes 元件 | AWS 實體對應 | 功能說明 |
|-----------------|--------------|----------|
| **Node** | 一台 EC2 | 用來執行 Pod。是叢集的運算單位。 |
| **Pod** | Container 群組 | 實際運行服務的容器（例如你的 C# 微服務）。 |
| **Deployment** | Pod 管理器 | 控制要啟動幾個 Pod、版本滾動更新等。 |
| **HPA** | Pod 數量調節器 | 根據負載自動改變 Deployment 的 replicas。 |
| **Cluster Autoscaler (CA)** | Node 管理器 | 當 Node 資源不足時，自動新增 EC2。 |

<br>

### 實際架構範例

**3 台 Node = 3 台 EC2**

每台 EC2 上可能同時跑 10～30 個 Pod（依你設定的 CPU/Memory Request 而定）

<br>

**資源分布示意圖**：
```
EC2-1 (Node-1)          EC2-2 (Node-2)          EC2-3 (Node-3)
├── Pod: Web API        ├── Pod: Worker         ├── Pod: Database
├── Pod: Cache          ├── Pod: Queue          ├── Pod: Monitor  
├── Pod: Logger         ├── Pod: Scheduler      ├── Pod: Backup
└── ... (共 15 個 Pod)   └── ... (共 12 個 Pod)   └── ... (共 18 個 Pod)
```

## 擴展 (Scaling)

如果今天你的網站從 100 人暴增到 10,000 人同時上線，K8s 可以自動啟動更多容器（Pods）來分擔負載。這稱為 Horizontal Pod Autoscaler (HPA)

## 調度 (Scheduling)

K8s 有一個「Scheduler」元件，會根據每台機器（Node）的 CPU、記憶體使用量、節點標籤、親和性規則等，自動決定要把新的 Pod 放在哪一台機器上


## Rolling Update

當你更新服務版本（例如從 v1 → v2）時，K8s 會自動

- 逐步替換舊版本的 Pod
- 監控新版本的健康狀態
- 若發現問題 → 自動 Rollback（回滾） 到舊版本

這個過程完全由 K8s 控制器（Deployment Controller）完成


## 資源的邏輯隔離 (Namespace)

Kubernetes 中的 Namespace 就像是「資料中心裡的虛擬區域」。每個 Namespace 內的資源（Pod、Service、ConfigMap 等）彼此獨立、互不干擾
不同團隊、專案、環境（dev/staging/prod）分開使用,避免名稱衝突。可搭配 ResourceQuota 管控「每個團隊最多能用多少 CPU/Memory」

## 提供硬體資源的有效利用 (Resource Request/Limit)

K8s 允許每個 Pod 宣告自己：Request（至少需要多少資源）& Limit（最多能用多少資源）, Scheduler 會依照 Request 來安排它在哪裡運行，而 Limit 則防止單一應用吃光整台機器


## 提供 Service Discovery 與負載平衡 (Service)

在 Kubernetes 中, Pod 會不斷啟動與消失（因為更新、擴容、崩潰重啟）, 它們的 IP 是動態的，不穩定, 所以 K8s 提供了 Service 概念

- 為一組 Pod 建立一個固定的「虛擬 IP（ClusterIP）」
- 自動做 負載平衡 (Load Balancing)
- 提供 DNS 名稱解析（Service Discovery）


## 支援多種儲存媒介 (Storage)

容器本身是短命的（Pod 被刪除，資料也會不見），因此 K8s 提供了持久化儲存機制：PersistentVolume (PV) 與 PersistentVolumeClaim (PVC)
支援的儲存來源包含：

- 本地磁碟（hostPath）
- NFS
- AWS EBS、GCP PD、Azure Disk
- Ceph、GlusterFS 等分散式儲存

甚至雲端資料庫、S3 gateway, 應用可以「聲明」要一塊 10GB 的持久磁碟，K8s 會自動掛上去。這樣 Pod 重啟時資料不會遺失。

## 自我修復 (Self-Healing)

K8s 控制器會持續監控系統的健康狀態

- Pod crash → 自動重啟
- Node 掛掉 → 把 Pod 重新排程到其他 Node
- Probe（健康檢查）失敗 → 暫停流量導入或重啟 Pod

這稱為 LivenessProbe / ReadinessProbe / StartupProbe。


## 高度的功能擴展性 (CRD & Operator)

K8s 不僅能管理「Pod」這種內建資源，還允許你「自己定義新型態的資源」，這稱為 CRD（Custom Resource Definition）


```yaml
apiVersion: mycompany.com/v1
kind: PaymentGateway
metadata:
  name: stripe
spec:
  apiKey: "xxxxx"
```

而 Operator 則是「幫你管理這些自訂資源邏輯的控制器」。它可以自動

- 建立資料庫叢集
- 備份/還原
- 更新版本

CRD 是「新的資料結構」，Operator 是「幫你維護它的機器人」, 這讓 K8s 不只是一個容器管理系統，更是一個「可延伸的自動化平台」。




## 控制平面的任務

控制平面是一組協同運作的服務，用來：

對外提供 Kubernetes API（讓 kubectl、Operator、CI/CD、Controller 與應用互動）。

對內 保存叢集狀態（宣告的期望狀態 vs 真實環境），並持續 調諧（reconcile） 到目標。

針對叢集事件做出反應：排程 Pod、重建失敗的物件、調整副本數、更新節點/路由等。

不會執行你的應用容器（應用在 工作節點/Worker nodes 上跑）。

一句話：你在 YAML/kubectl apply 宣告「我想要怎樣」，控制平面確保「世界變成你想要的樣子」。


## 事件資料流（從宣告到容器起來）

你用 kubectl/CI 送出 YAML → 打到 API Server。

API Server 通過認證/授權、Admission，驗證物件，並寫入 etcd（唯一真實資料源）。

Controller Manager 讀取 etcd 中的目標狀態（例如 Deployment replicas=3），發現不一致就建立/修復 ReplicaSet / Pod 等。

Scheduler 看見「待排程的 Pod（沒有 nodeName）」→ 根據資源/策略選擇 最佳節點，把決策寫回 API Server。

被選中的節點上 kubelet 監聽到有新 Pod 指派 → 透過 Container Runtime（containerd/CRI-O） 實際拉映像、啟容器。

kube-proxy 負責把 Service 的虛擬 IP（ClusterIP）與真實 Pod 端點串起來，處理叢集內部負載平衡與連線規則。

元件持續回報心跳、狀態到 API Server → 狀態再存進 etcd → 形成閉環。

## API Server（kube-apiserver）

角色：叢集的「大門」與「唯一入口」。所有讀寫都經它；所有控制器、kubelet、使用者都跟它對話。

職責

認證（Authentication）：X.509 憑證、Bearer Token、OIDC 等。

授權（Authorization）：RBAC/ABAC，誰可以對哪些資源做哪些動作。

Admission：Validating/Mutating Webhook（如自動加上 sidecar、資源配額檢查）。

資料一致性：把最終狀態寫入 etcd。

HA 作法：多台 API Server 前加負載平衡；它們都是「無狀態」，關鍵狀態在 etcd。

常見問題

高延遲/429：QPS 過高或 Admission Webhook 變慢。

401/403：認證/授權設定不對（看 kubectl auth can-i）。


## etcd（分散式 Key-Value 儲存）

角色：叢集 唯一真實資料源（Source of Truth）。所有 Kubernetes 物件都存這裡。

特性：使用 Raft 共識；需要 奇數個節點 組成叢集以確保選主與一致性。

關鍵建議

磁碟 IOPS 與網路延遲 直接影響全叢集反應速度。

加密：磁碟與「機密欄位」的 at-rest encryption（如 Secret）。

定期備份/快照，演練還原流程。

常見問題

叢集大時，物件太多/事件風暴 → etcd 壓力升高、API 變慢。

主從失聯或 Quorum 不足 → 叢集「無法寫入」狀態。


## Controller Manager（kube-controller-manager）

角色：「調諧迴圈」的大本營，裡面有很多 控制器（Controllers）。

常見控制器

Deployment/ReplicaSet Controller：確保副本數達標；Pod 掛了就補。

Node Controller：節點心跳偵測、標記 NotReady、觸發遷移。

Endpoint/ServiceAccount/Token Controller：維護服務端點、憑證、Token 等。

HorizontalPodAutoscaler（HPA）：依指標（CPU/自定義 Metrics）縮放。

工作方式：Watch etcd → 發現「期望 vs 現況」不一致 → 呼叫 API 建立/更新資源。

HA：多副本 + Leader Election，僅一個是主執行者，其它待命。


## Cloud Controller Manager（cloud-controller-manager，可選）

角色：把 Kubernetes 與雲商 API 整合（EKS/GKE/AKS 單獨運行或由平台代管）。

職責

節點生命週期：發現/移除雲端 VM → 對應成 Kubernetes Node。

路由/負載平衡器：當建立 Service type=LoadBalancer 時，呼叫雲商 API 建立 LB、綁定節點。

持久磁碟（部份情境）：對接雲端磁碟生命週期（更多是 CSI 插件負責）。

重點：沒有雲端就不需要；在雲上它讓 kubectl 的宣告自動變成雲資源。


## Scheduler（kube-scheduler）

角色：決定 Pod 跑在哪個節點。

流程

過濾（Predicates）：資源可用量、NodeSelector/affinity、污點/容忍、PVC 可綁定性等。

打分（Scoring）：拓撲分散、資源利用率、優先級/搶佔（Preemption）等。

綁定（Bind）：把選中的 nodeName 寫回 API Server。

常見問題

Pod 卡在 Pending：資源不足、PVC 無法綁定、親和/污點規則互相衝突。

高延遲：極大量待排程 Pod 或外部延伸調度器（coscheduling）表現不佳。


## kubelet（每個節點上）

角色：該節點的「代理人」與「執行官」。

職責

持續向 API Server 報告 Node/Pod 狀態、資源使用與心跳。

依指派 創建/刪除 Pod：透過 CRI 呼叫 containerd/CRI-O 拉映像與啟容器。

監控容器存活（liveness/readiness/startup probes）。

配合 CNI/CSI 完成網路與存儲掛載。

常見問題

映像拉不下來、Probe 失敗導致重啟、節點 NotReady、磁碟滿（image GC 失效）。


## kube-proxy（每個節點上）

角色：讓 Service 能把流量導到後端 Pod。

工作模式

早期 iptables / 現今多用 IPVS：在節點層建立轉發規則；新 Pod 變動時即時更新後端列表。

限制與替代

大型叢集或高連線場景，會採用 eBPF-based CNI（如 Cilium） 讓資料平面更高效並替代 kube-proxy。

常見問題

服務解析不到/不通：端點未更新、NetworkPolicy/CNI 設定、NodePort/LB 規則異常。


## 什麼在控制平面、什麼在工作節點？

控制平面：API Server、etcd、Controller Manager、Scheduler、（可能）Cloud Controller Manager。

工作節點：kubelet、kube-proxy、Container Runtime（containerd/CRI-O）、你的 Pods。

不是控制平面但常見：CoreDNS（Pod 形式）、Metrics Server、Ingress Controller、CNI/CSI 外掛。




## Kubernetes Pod 調度與服務穩定性調整 (因為會變成不收pod 所以成本會增加)


https://91app.slack.com/archives/G06A3GDC7/p1762312910118499


在 SG（新加坡）區的機器節點回收時，Kubernetes 會自動將原本在該節點上的 Pod 重新分配（reschedule）到其他節點


- 節點回收 → Pod 被重排，SG 區有一台節點（Node）被系統回收。原本在該節點上的一個 SPL Pod 被移動（reschedule）到另一台機器。
- 新 Pod 啟動但健康檢查未通過，新啟動的 Pod 尚未通過健康檢查（Readiness probe）。因此 尚未接收外部流量。
- 當下只剩 2 顆 Pod 在對外服務，原本的 Pod 共 3 顆，其中 1 顆被重排、1 顆新啟動但未就緒。實際能工作的只有 2 顆 Pod。因此，觀察到的 4xx、5xx 錯誤 很可能是這兩顆負載過高時產生的。
- 流量仍高達 1500 RPS，SPL 的常態請求量約在 1200~1500 RPS。經觀察，若低於 3 顆 Pod 時，系統就會不穩定（出現錯誤率上升）。

## PDB（Pod Disruption Budget）調整

原先 PDB 設定為：
maxUnavailable: 50%

➜ 意思是最多可以同時中斷一半的 Pod（例如 4 顆中可同時停 2 顆）。在高流量情況下，這樣的設定會導致「剩餘可服務的 Pod 數太少」。


因此目前手動調整為：
minAvailable: 100%

➜ 表示「在任何時候都必須保持所有 Pod 都運作中」，避免因節點調度或自動更新而導致 Pod 同時被收掉。


✅ 調整目的「確保服務穩定性，避免 Pod 被誤收導致流量瞬斷。」


透過將 PDB 調整為 minAvailable: 100%，可以保證：

- Kubernetes 不會在同一時間終止任何一顆 Pod；
- 在高流量情況下，所有 Pod 都能持續服務；
- 避免因節點回收或滾動更新造成的瞬間容量下降。

📈 建議後續行動

- 確認 Readiness 失敗的原因（如探針設定、啟動時間、依賴服務）。
- 考慮增加 Pod 數量或調整 HPA（以支撐 1500+ RPS）。
- 長期可微調 PDB 為 minAvailable: 80~90%，在確保穩定的前提下仍保留部分滾動更新彈性。
